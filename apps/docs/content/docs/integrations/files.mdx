---
title: Move files between tools
description: Capture file bytes from tool results once and let the agent move them by fileId to upload URLs, download links, and the sandbox.
---

Agents often need to take a file from one tool and give it to another: an email attachment to an
upload URL, a sandbox report to an email, an MCP export to cloud storage. Yolk does this with a
claim check ([ADR 0009](https://github.com/magoz/yolk-sdk/blob/main/docs/adr/0009-file-claim-check.md)):
tool resolution stores the bytes once, the model and code mode scripts only see a short `fileId`,
and file tools turn the `fileId` back into bytes or a link where it is needed. Bytes never pass
through the model, scripts, the tool ledger, or the transcript.

## Install

```bash
pnpm add @yolk-sdk/files@canary @yolk-sdk/agent@canary effect@4.0.5
```

Available from `0.1.0-canary.114`. The package is runtime-neutral (Web Crypto, no Node builtins).

## How it works

1. A tool returns bytes as a `FilePart` (`filePartFromBytes` from `@yolk-sdk/agent/protocol`).
   Connector actions with `fileOutput` (`gmail.get_attachment`, `outlook.get_attachment`,
   `email.get_attachment`) and MCP embedded resource blobs already do.
2. `resolveTools(modules, context, { files: { store } })` stores the bytes before the ledger sees
   the result. The model sees a label such as `[file file_…: Faktura_225.pdf, application/pdf, 89 KB]`
   and `ToolResult.files` lists the descriptors.
3. The agent passes the `fileId` to a tool that needs the file.

Without `files`, over `maxFileBytes` (default 100 MiB), or when storing fails, the bytes become a
`[file not captured (reason): …]` label: base64 never falls through to the model. Inline images,
documents and audio the model views keep their source and also get a stored copy and a label.

## Store

Fragment; your app supplies `r2ObjectStorage`, `workspaceId` and `sessionId`:

```ts
import { makeObjectStorageFileStore } from '@yolk-sdk/files'

const store = makeObjectStorageFileStore({
  storage: r2ObjectStorage, // your ObjectStorageApi: put, head, get, signGet, deletePrefix
  scope: `${workspaceId}/${sessionId}` // host-derived, never from the model
})
```

Keys are `files/<scope>/<fileId>`, with the name and sha256 in object metadata: no database. The
`fileId` is derived from the scope and the content hash, so replays and duplicates write nothing,
and a `fileId` from another scope never resolves. `deleteScopeFiles({ storage, scope })` removes a
scope's files, for example with its session. Scope segments are `/`-separated and use only
`A-Z a-z 0-9 . _ -` (no `.` or `..` segments); the store throws for an invalid scope, so check
untrusted values with `isValidFileScope`.

## Tools

Fragment; your app supplies `modules`, `context`, the transport and the sandbox:

```ts
import { Effect } from 'effect'
import { resolveTools } from '@yolk-sdk/agent/tools'
import { makeFileToolModule } from '@yolk-sdk/files'

const toolSet = Effect.gen(function* () {
  return yield* resolveTools(
    [...modules, makeFileToolModule({ store, transport: guardedUploadTransport, sandbox })],
    context,
    { files: { store } }
  )
})
```

| Tool                | Input                        | Does                                                                         |
| ------------------- | ---------------------------- | ---------------------------------------------------------------------------- |
| `file_upload`       | `{ fileId, url, headers? }`  | `PUT`s the file to an https URL, for example a presigned upload URL          |
| `file_url`          | `{ fileId, ttlMinutes? }`    | Signs a temporary download link (default one hour, at most seven days)       |
| `file_to_sandbox`   | `{ fileId, path? }`          | Copies the file into the sandbox workspace (default `files/<fileId>/<name>`) |
| `file_from_sandbox` | `{ path, name?, mimeType? }` | Turns a workspace file into a `fileId`                                       |

All four are `write` tools without approval. `file_upload` exists only with a
`FileUploadTransportApi`, and the sandbox tools only with a sandbox that has `writeFile`/`readFile`
(the `@yolk-sdk/sandbox` Vercel layer has them). `file_upload` results and errors name the
destination host, never the URL. A network failure during an upload is an unknown outcome: the
agent is told to check the destination before retrying.

`makeFileToolModule` also takes `maxTransferBytes` (default 50 MiB: `file_upload` and the sandbox
tools read the whole file into memory, so a captured file larger than this cannot be transferred),
`defaultUrlTtlSeconds` (default one hour, clamped to one minute to seven days) and `isEnabled`.

## From a code mode script

Nested calls that captured files resolve `files: [{ fileId, name, mimeType, size }]`, so one script
moves a Gmail attachment to an MCP server's presigned upload URL (script fragment; the IDs come
from earlier calls):

```js
const attachment = await tools['gmail.get_attachment']({ messageId, attachmentId, filename })
const file = attachment.files[0]
const upload = await tools.mcp_afloat_create_receipt_upload({
  contentLength: file.size,
  contentType: file.mimeType
})
await tools.file_upload({ fileId: file.fileId, url: upload.url, headers: upload.headers })
```

## Your app owns

- the `ObjectStorageApi` over private storage and the scope (give a subagent a store bound to the
  same scope to share files);
- which surfaces get `files` and the file module (for example not automatic continuations);
- a guarded `FileUploadTransportApi`: public addresses only (checked on the resolved IP), TLS
  verified, no redirects, no cookies or ambient credentials, no logging of the URL. An unguarded
  transport allows SSRF;
- claiming and ledgering the `write` tools, retention, and download UI.

Connector sinks such as Gmail draft attachments do not take `fileId`s yet; attach files through
your own tools until they do.
