## Afloat

Use Afloat when you want to turn a host-owned Afloat API key into remote MCP connection data.
The connector returns the canonical endpoint and required MCP `2026-07-28` protocol version. Keep
`afloat.mcp_auth` server-side; hosts should discover tools through `@yolk-sdk/mcp/client` and own
agent access, approval, and file-handling policy.

| Action id         | What it does                                                       |
| ----------------- | ------------------------------------------------------------------ |
| `afloat.mcp_auth` | builds Afloat remote MCP server URL, protocol version, and API key |

## Figma

Use Figma when you want to turn host-owned Figma OAuth credentials into remote MCP auth data.

Return optional `refreshToken`, `clientId`, and `clientSecret` from the host's runtime
`OAuthCredential`; never place them in persisted integration config.

| Action id        | What it does                                                             |
| ---------------- | ------------------------------------------------------------------------ |
| `figma.mcp_auth` | builds Figma remote MCP server URL, tokens, and optional MCP client info |

## Fortnox

`FortnoxConnector` exposes only GET actions, all with `read` metadata:

| Action id                                                         | What it does                                          |
| ----------------------------------------------------------------- | ----------------------------------------------------- |
| `fortnox.get_company_information`                                 | read company information                              |
| `fortnox.list_customers` / `fortnox.get_customer`                 | list or retrieve customers                            |
| `fortnox.list_invoices` / `fortnox.get_invoice`                   | list or retrieve customer invoices and available rows |
| `fortnox.list_suppliers` / `fortnox.get_supplier`                 | list or retrieve suppliers                            |
| `fortnox.list_supplier_invoices` / `fortnox.get_supplier_invoice` | list or retrieve supplier invoices by GivenNumber     |
| `fortnox.list_supplier_invoice_files`                             | list archive file IDs connected to a supplier invoice |

All resource-scoped OAuth slots share `fortnox.oauth`. Required record scope hints are `companyinformation`,
`customer`, `invoice`, `supplier`, and `supplierinvoice`. Opt-in file slots are
`FortnoxConnectFileOAuthCredentialSlot` (`connectfile`) and `FortnoxArchiveOAuthCredentialSlot`
(`archive`); they are **not** included in `FortnoxCombinedOAuthCredentialSlot`. **Fortnox scopes grant read and write**;
only the SDK action surface is read-only. Hosts provide HTTP and current Fortnox OAuth credentials,
with no integration config keys.

List actions support page/limit, one resource-specific search pair, and global selection fields.
They return runtime Chunks and normalized pagination. Resource fields retain provider spelling and
monetary types. See [Read Fortnox records](../connectors/fortnox) for setup, inputs, selected fields,
consent limitations, and failure handling.

## Dropbox

Dropbox exports `DropboxOAuthCredentialSlot`, action-scoped
`DropboxMetadataReadOAuthCredentialSlot`, `DropboxContentReadOAuthCredentialSlot`, and
`DropboxContentWriteOAuthCredentialSlot`, plus `DropboxCombinedOAuthCredentialSlot`. Every slot
uses the same `dropbox.oauth` binding id. Metadata actions request `files.metadata.read`;
file-management actions request `files.content.write`; the host-only download helper requests
`files.content.read`. The combined slot hints all three.

| Action id                      | What it does                                |
| ------------------------------ | ------------------------------------------- |
| `dropbox.list_folder`          | list a folder or begin a recursive listing  |
| `dropbox.list_folder_continue` | continue a folder listing from its cursor   |
| `dropbox.search`               | search file and folder metadata             |
| `dropbox.search_continue`      | continue a search from its cursor           |
| `dropbox.get_metadata`         | get file, folder, or deleted-entry metadata |
| `dropbox.create_folder`        | create a folder                             |
| `dropbox.move`                 | move a file or folder                       |
| `dropbox.copy`                 | copy a file or folder                       |
| `dropbox.delete`               | delete a file or folder                     |

Use `path: ''` or omit `path` with `dropbox.list_folder` to address the Dropbox API root. Continue
while `hasMore` is true. File metadata outputs use camelCase fields and a normalized
`type: 'file' | 'folder' | 'deleted'` discriminant.

The host owns OAuth code exchange, refresh, credential storage, consent, and Dropbox App Folder
versus Full Dropbox configuration. Binary upload and download **actions** are not part of this
module because the portable connector HTTP port carries string bodies; do not base64-encode file
content through these actions. Original-byte download is a separate host helper, not an action.
Host-only create/update are documented in [Transfer connector files](../connectors/files).

### Host-only Dropbox original-byte download

`downloadDropboxFile` from `@yolk-sdk/connectors/dropbox` returns original file bytes. It is not
registered on `DropboxConnector` and is never serialized by `makeConnectorToolModule`. It mirrors
[`downloadOneDriveItem`](#host-only-onedrive-original-byte-download).

```ts
import { downloadDropboxFile } from '@yolk-sdk/connectors/dropbox'

// Fragment: host-owned integration and a file id or path from discovery.
const download = downloadDropboxFile(
  integration,
  { path: selectedFile.id },
  { maxBytes: 20 * 1024 * 1024, maxErrorBodyBytes: 16 * 1024 }
)
```

The budgets are trusted host configuration, not tool parameters. Provide the existing
`CredentialResolver` and a compliant `ConnectorBinaryHttpClient` layer; default Dropbox actions
still use only `ConnectorHttpClient`. `path` is one Dropbox `/path`, bare `id:`, folder-ID-relative
path (`id:folder-id/child.txt`), `rev:`, or `ns:` value from discovery, never a share link.
Folder-ID-relative downloads return the child's own file ID. The helper sends a single `GET` to the Dropbox content endpoint,
rejects every redirect, takes served metadata from the `Dropbox-API-Result` header, and fails
non-downloadable entries such as Paper docs with `not_downloadable`. Hosts must materialize, scan,
and extract the `Uint8Array`; do not put raw bytes into generic model tool JSON. See
[Integration APIs](../api-reference/integrations#connectors) and
[Troubleshooting](../troubleshooting) for adapter and error details. Dropbox's official
[content-download protocol](https://www.dropbox.com/developers/documentation/http/documentation#content-download-endpoints)
and [path formats](https://www.dropbox.com/developers/documentation/http/documentation#path-formats)
describe GET support, argument/result headers, and folder-ID-relative addressing.

## Generic email

`@yolk-sdk/connectors/email` exposes portable protocol-neutral actions. Hosts provide an
`EmailClient` Effect layer backed by their chosen IMAP, POP3, SMTP, TLS, and MIME libraries; the
package does not bundle those libraries.

| Action id              | What it does                                   | Access        |
| ---------------------- | ---------------------------------------------- | ------------- |
| `email.list_messages`  | list normalized messages with an opaque cursor | `read`        |
| `email.get_message`    | fetch one normalized message                   | `read`        |
| `email.get_attachment` | retrieve decoded attachment content as base64  | `read`        |
| `email.create_draft`   | append a message draft to an IMAP mailbox      | `write`       |
| `email.send_message`   | submit a normalized message to the SMTP server | `destructive` |
| `email.set_read`       | mark an IMAP message read or unread            | `write`       |
| `email.trash`          | move an IMAP message to trash                  | `destructive` |
| `email.untrash`        | move an IMAP message out of trash              | `write`       |
| `email.move`           | move an IMAP message to any folder             | `write`       |
| `email.modify_labels`  | add/remove IMAP keyword labels                 | `write`       |

Incoming actions require `incomingHost` and use `EmailIncomingCredentialSlot`. They default to
`incomingProtocol: 'imap'`, `incomingSecurity: 'tls'`, and port `993`; POP3 with TLS defaults to
`995`. Optional `folder` works with IMAP and fails deterministically with POP3. SMTP send requires
`smtpHost` and `EmailSmtpCredentialSlot`; it defaults to `smtpProtocol: 'smtp'`,
`smtpSecurity: 'starttls'`, and port `587` (`tls` defaults to `465`). Override ports with an integer
or numeric string from `1` through `65535`. Security is explicit: `none`, `starttls`, or `tls`.

The two slots may bind separate host credential refs or the same ref. Resolve credentials immediately
before transport calls. Both slots require `UsernamePasswordCredential`; use the provider-specific
Google or Microsoft connectors for their OAuth flows. Message list/get outputs contain normalized
addresses, body text/HTML, and attachment metadata, never raw MIME.

When attachment metadata includes `id`, pass it with the parent `messageId` to
`email.get_attachment`. The output repeats normalized metadata and exposes decoded file bytes—not
MIME transfer-encoded text—as base64 in `contentBase64`; decoded `size` is a non-negative
integer. Existing `EmailClient` implementations may omit the optional `getAttachment` method;
invoking the action then fails with a typed validation error. Successful host output is
schema-validated at the connector boundary before it is returned. Hosts that implement it own MIME
parsing, base64 encoding, size limits, durable storage, and content scanning. IMAP adapters should fetch the selected part without marking
the message read when supported. POP3 has no standard partial-part retrieval, so adapters may fetch
the whole stable UIDL-addressed message before extracting the part. POP3 rejects `folder`; omit it
for attachment retrieval.

`email.modify_labels` takes `{ messageId, folder?, addLabels?, removeLabels? }` with at least
one label list. It requires IMAP and optional `EmailClient.modifyLabels` host support; missing
support produces a typed validation error without breaking existing adapters. The incoming
credential is used and `folder` defaults to `INBOX`. Labels must be ASCII IMAP keyword atoms,
not system flags such as `\Seen`; spaces, control characters and IMAP atom specials are rejected.
Hosts check `PERMANENTFLAGS` and apply UID `STORE` additions/removals while preserving unrelated
keywords and system flags. Removals win on overlap. Hosts return `{ messageId, labels }` with
`labels` as an Effect `Chunk`; list/get messages may expose optional `labels` arrays. There is no
standalone IMAP label catalog: assignment creates keyword usage, removal clears usage. POP3 and
SMTP cannot persist labels. Hosts own partial-write reconciliation; the SDK has no socket adapter.

`email.move` takes `{ messageId, folder?, destinationFolder }` with a required destination folder
and returns the destination plus the new message ID when the host can map it. Source `folder`
defaults to `INBOX`. It requires IMAP and optional `EmailClient.move` host support; hosts use UID
`MOVE` when advertised, otherwise `COPY` plus `\Deleted` with a UID-scoped expunge, preserving flags
and owning partial-move reconciliation. Identical source/destination folders are rejected before
dispatch. Destination UIDs differ from source UIDs: use the returned ID or re-list the destination.

`email.create_draft` requires IMAP, accepts drafts without recipients, and uses the incoming
credential. Optional `folder` selects the mailbox. When omitted, the host adapter discovers a
mailbox advertised with `\Drafts` by the IMAP SPECIAL-USE extension and may fall back to `Drafts`.
The port owns MIME generation and `APPEND` with the `\Draft` flag. Output is
`{ saved: true, folder, draftId? }`; `draftId` is optional because servers without UIDPLUS may not
return `APPENDUID`. When present, it is opaque; UIDPLUS adapters must encode both UIDVALIDITY and UID,
never a bare UID. POP3 rejects draft creation.

List message `id` values are opaque adapter identifiers that callers pass unchanged to
`email.get_message`. POP3 adapters must use UIDL or another stable mapping rather than transient
sequence numbers. An omitted IMAP `folder` means `INBOX`; POP3 uses its single mailbox. Adapters
return deterministic newest-first pages. Cursors are opaque and scoped to the integration, protocol,
folder, and ordering; mailbox changes may invalidate them. SMTP input needs at least one recipient
across `to`, `cc`, and `bcc`. `{ accepted: true }` confirms server submission acceptance only, not
delivery.

### Mark read/unread and move to/from trash

These actions require IMAP and the incoming credential. POP3 is rejected before adapter calls;
SMTP cannot manage mailbox state. Hosts opt in through optional `EmailClient.setRead`, `trash`,
`untrash`, and `move` methods. Existing adapters remain compatible; invoking a missing method returns a
typed validation error. All successful mutation outputs are schema-validated.

- `email.set_read`: `{ messageId, isRead, folder? }`. Set `isRead` to `true` for read or `false`
  for unread. The connector defaults `folder` to `INBOX`. Hosts add/remove only the `\Seen` flag
  using UID `STORE`, preserving all other flags, and return `{ messageId, isRead }` after success.
- `email.trash`: `{ messageId, folder?, trashFolder? }`. Source `folder` defaults to `INBOX`.
  Hosts use `trashFolder` or discover a `\Trash` SPECIAL-USE mailbox with a host-configured fallback.
- `email.untrash`: `{ messageId, folder?, destinationFolder? }`. Here `folder` is the source
  trash mailbox; if omitted, hosts discover it. `destinationFolder` defaults to `INBOX`, **not**
  the original folder. Supply an explicit destination to restore elsewhere.
- `email.move`: `{ messageId, folder?, destinationFolder }` with a required destination folder.
  Source `folder` defaults to `INBOX`; identical source/destination folders are rejected before
  dispatch. Returns the destination and the new message ID when the host can map it.

Hosts perform UID `MOVE` or a safe per-message copy/delete fallback. Never use blanket `EXPUNGE`,
permanent deletion, or merely set `\Deleted` as a substitute for a trash move. Return a failure
when trash discovery is missing/ambiguous, folders are identical, or a safe move is unavailable.
Trash/untrash return `{ moved: true, folder, messageId? }` (`EmailMoveMessageOutput`), where `folder`
is the destination and optional `messageId` identifies the moved message there. UIDPLUS mappings
must include destination UIDVALIDITY and UID. If no reliable ID mapping exists, omit it and re-list
the destination. Hosts own partial-move reconciliation; never blindly reuse a source UID or retry
a potentially completed copy/delete.

## Google

Google exports a generic `GoogleOAuthCredentialSlot`, action-scoped OAuth slots, and
`GoogleCombinedOAuthCredentialSlot` for broad-consent hosts. Every slot uses the same `google.oauth`
binding id, so one host credential can cover selected Gmail, Calendar, and Drive actions when its
consent includes those scopes.

Drive-specific slots use least-privilege consent hints:

| Slot                                             | Scope                                     |
| ------------------------------------------------ | ----------------------------------------- |
| `GoogleDriveMetadataReadonlyOAuthCredentialSlot` | `drive.metadata.readonly`                 |
| `GoogleDriveFileOAuthCredentialSlot`             | `drive.file`                              |
| `GoogleDriveReadonlyOAuthCredentialSlot`         | `drive.readonly`                          |
| `GoogleCombinedOAuthCredentialSlot`              | Gmail, Calendar, and default Drive scopes |
| `GoogleOAuthCredentialSlot`                      | none declared                             |

`drive.metadata.readonly` is a restricted scope that can read metadata across the authorized
Drive. `drive.file` is non-sensitive and permits create/update/delete only for files the app created
or that a user explicitly opened/shared with the app. `GoogleDriveReadonlyOAuthCredentialSlot` is
host-only content consent for Drive byte helpers (`contentAccess: 'readonly'`) and is **not** part
of `GoogleCombinedOAuthCredentialSlot`. Hosts that need mutations across arbitrary
existing files own broader restricted-scope consent, verification, and authorization policy. The
connector never manages OAuth callbacks, token refresh, storage, or consent UI.

### Fetch a normalized Gmail thread

`gmail.get_thread` requires `{ threadId, format }`, where `format` is `full`, `metadata`, or
`minimal`. Use `full` when decoded message bodies are required.

The action returns `GmailThreadOutput`. Each `GmailThreadMessage` includes selected root headers,
attachment metadata, and an optional decoded message `body` with `bodyMimeType`. Plain text is
preferred when available; otherwise HTML is used. Text and nested-message attachments do not enter
the message body. Selected headers are `Bcc`, `Cc`, `Date`, `Delivered-To`, `From`, `In-Reply-To`,
`Message-ID`, `References`, `Reply-To`, `Subject`, and `To`.

Raw MIME and attachment content are intentionally omitted. Optional attachment `size` values are
nonnegative integers; invalid sizes from Gmail MIME discovery (`-1`, `1.5`, `null`, `"12"`, missing)
are omitted rather than exposed as byte counts, and valid siblings including zero are kept. Null /
array-shaped / non-object parts are skipped. `message/rfc822` stays an attachment. Public thread
output classes and `gmail.get_attachment` (`size` plus base64url `data`) are unchanged.

Internal MIME `payload` for `gmail.get_thread` and `gmail.list_attachments` admits `Schema.Json` after
JSON parse. `Schema.Json` requires finite numbers, so raw HTTP JSON `1e999` becomes `Infinity` and
rejects the whole payload (`ConnectorError` `validation_failed`, `Invalid response shape`). That is
not a general collapse of malformed optional MIME fields. Do not demonstrate overflow with
`JSON.stringify(Infinity)` (that becomes `null` and would omit size). Hosts must still validate
actual bytes and cannot treat metadata as a download limit.
See [private attachments](../guides/private-attachments#bound-connector-downloads-before-buffering)
for separate streamed encoded-body and decoded-file limits in the host HTTP adapter.

Use `gmail.list_attachments` with one
`messageId` for metadata-only discovery without fetching a whole thread; metadata includes
inline/content-ID details when Gmail supplies them. `attachmentId` is optional because Gmail may
return inline attachment data instead. When present, pass the parent message `id`
as `messageId` plus `attachmentId` to `gmail.get_attachment`. Its typed output preserves Gmail's
`size` and base64url `data`, then adds `messageId`, `attachmentId`, and standard-base64
`contentBase64`. Omitted inline data is not retrievable through that action.

### Drive actions

| Action id             | What it does                                         | Access        |
| --------------------- | ---------------------------------------------------- | ------------- |
| `drive.list_files`    | list file/folder metadata, optionally under a parent | `read`        |
| `drive.search_files`  | search file names and indexed text                   | `read`        |
| `drive.get_file`      | fetch metadata by file id                            | `read`        |
| `drive.create_folder` | create a root or child folder                        | `write`       |
| `drive.trash_file`    | move a file or folder to trash                       | `destructive` |
| `drive.delete_file`   | permanently delete without moving to trash           | `destructive` |

List and search outputs contain `files`, optional `nextPageToken`, and optional
`incompleteSearch`. Pass the token back through `pageToken`. Trashed files are excluded by default;
set `includeTrashed: true` to include them. Search accepts a plain `query` and applies it to Drive
file names and indexed text rather than exposing raw Drive query syntax.

Set optional `driveId` to search or list one shared drive through `corpora=drive`. Drive requests
send current shared-drive support parameters, and returned file metadata may include `driveId`,
`resourceKey`, and operation `capabilities`. Pass `resourceKey` with get/trash/delete or
`parentResourceKey` with parent-scoped list/search/create; the connector forwards it through
`X-Goog-Drive-Resource-Keys` for protected link-shared files. The host should check and enforce
capabilities before destructive calls; Google still applies ownership, shared-drive role,
administrator, and per-file rules.

`drive.trash_file` is the reversible default. `drive.delete_file` bypasses trash and permanently
removes the item; deleting a folder can also remove owned descendants. Binary downloads and exports use separate host-only helpers; uploads are not added. See
[Transfer connector files](../connectors/files) for content consent and host transport. Hosts own
Google Picker or equivalent per-file authorization.

## Microsoft

Use `@yolk-sdk/connectors/microsoft` for Microsoft Outlook mail and OneDrive files. Both workloads
share Microsoft Graph v1.0 as the API and OAuth resource boundary, plus the same `microsoft.oauth`
credential binding. The connector does not use the retired Outlook REST endpoint, direct Exchange
Online APIs, or legacy OneDrive APIs.

All OAuth slots use the shared `microsoft.oauth` binding id:

| Slot                                               | Permission hint                                    |
| -------------------------------------------------- | -------------------------------------------------- |
| `MicrosoftOutlookReadOAuthCredentialSlot`          | `Mail.Read`                                        |
| `MicrosoftOutlookWriteOAuthCredentialSlot`         | `Mail.ReadWrite`                                   |
| `MicrosoftOutlookSendOAuthCredentialSlot`          | `Mail.Send`                                        |
| `MicrosoftOutlookSharedReadOAuthCredentialSlot`    | `Mail.Read.Shared`                                 |
| `MicrosoftOutlookSharedWriteOAuthCredentialSlot`   | `Mail.ReadWrite.Shared`                            |
| `MicrosoftOutlookSharedSendOAuthCredentialSlot`    | `Mail.Send.Shared`                                 |
| `MicrosoftOneDriveReadOAuthCredentialSlot`         | `Files.Read`                                       |
| `MicrosoftOneDriveWriteOAuthCredentialSlot`        | `Files.ReadWrite`                                  |
| `MicrosoftOneDriveReadAllOAuthCredentialSlot`      | `Files.Read.All`                                   |
| `MicrosoftOneDriveWriteAllOAuthCredentialSlot`     | `Files.ReadWrite.All`                              |
| `MicrosoftOutlookCategoryReadOAuthCredentialSlot`  | `MailboxSettings.Read`                             |
| `MicrosoftOutlookCategoryWriteOAuthCredentialSlot` | `MailboxSettings.ReadWrite`                        |
| `MicrosoftCombinedOAuthCredentialSlot`             | mail and file scopes, excluding category lifecycle |
| `MicrosoftOAuthCredentialSlot`                     | none declared                                      |

Inputs default to the signed-in mailbox through `/me`. Set optional `mailbox` to a user ID or user
principal name to target an Exchange Online shared/delegated mailbox through `/users/{mailbox}`.
For message actions, the connector then requests the matching Shared slot, unless the explicit `mailbox` matches the
connected user identity (`OAuthCredential.accountId`, case-insensitive), which keeps the ordinary
`Mail.*` slot on the same `/users/{mailbox}` path. The same `mailbox` must accompany an opaque
`nextLink` so the resolver receives the appropriate mailbox consent hint. Populate `accountId` with
the same Graph user ID or `userPrincipalName` callers pass as `mailbox`; the comparison ignores case
only, not whitespace, and does not resolve aliases or equate IDs with principal names. Explicit
mailboxes in delegated mode resolve the scope-free `microsoft.oauth` identity slot first, then the
selected operation slot. The identity lookup does not authorize the operation.

For delegated reads and writes, the signed-in user needs the corresponding Exchange shared-folder
or Full Access grant. Sending from another mailbox requires Exchange **Send As** or **Send on
Behalf** rights; this connector's `/users/{mailbox}` send path also requires Full Access.

For application tokens, set integration config `mailboxAccessMode` to `application` and always pass
`mailbox`. The connector then selects non-Shared `Mail.Read`, `Mail.ReadWrite`, or `Mail.Send`
application-permission hints. Scope application access to approved mailboxes with host/admin policy,
such as Exchange Online RBAC for Applications.

Hosts own Entra app registration, OAuth authority/tenant selection, consent, callbacks, token
refresh, credential storage, and Exchange mailbox authorization. Use action-scoped slots for
least-privilege consent. A single credential can cover Outlook and OneDrive when it has both the
required `Mail.*` and `Files.*` grants.

#### Categories

List takes `{ mailbox?, top?, nextLink? }` and returns `{ categories, nextLink? }`, with an Effect
`Chunk` of categories (`id`, `displayName`, optional `color`). Create takes
`{ mailbox?, displayName, color? }`, where color is `none` or `preset0` through `preset24`.
Delete takes `{ mailbox?, categoryId }` and returns `{ id, deleted: true }` without decoding
Graph's empty 204 body. The name is immutable; deleting a master category does not remove its
name from existing message assignments.

Master-category list and mutations require opt-in `MailboxSettings.Read` and
`MailboxSettings.ReadWrite`, respectively, sharing `microsoft.oauth`. These are not in the
existing combined slot. There are no `.Shared` mailbox-settings scopes; delegated access to
another mailbox's settings remains subject to Graph authorization. Application mode requires an
explicit `mailbox`. List accepts the same null/blank placeholders as message lists; replay
`nextLink` unchanged with the same mailbox. Only that Graph v1.0 category collection is accepted.

Assign names, **not category IDs**, using `outlook.set_categories` with
`{ messageId, mailbox?, categories }`; `[]` clears all names. `outlook.modify_categories` takes
`{ messageId, mailbox?, addCategories?, removeCategories? }` with at least one list. It reads
current categories, merges names (deduped by exact case-sensitive match, removals win), and PATCHes
the result. Invalid/failed
reads never trigger a PATCH. Both calls use `Mail.ReadWrite` or `Mail.ReadWrite.Shared` and
preserve the existing own-mailbox/application guards and immutable-ID headers. Neither action
creates master categories automatically. The merge is **non-atomic**: hosts must serialize
competing updates, and the SDK makes no retry or compare-and-swap guarantee.

#### Reply drafts and recovery

`outlook.create_reply_draft` creates a bodyless reply draft, then prepends the supplied text or HTML
to Graph-generated quoted history and saves it. Supply only the new reply, not the original quote.
Text replies preserve quote content, not its original HTML formatting.

This is a multi-step write. Once a draft ID is known, post-create HTTP failures return
`outlook_create_reply_draft_partial` with the HTTP `status` but no `retryAfterMs`, including for 429.
A read-back without the requested body format uses the same partial-failure code: `status` is the
last Graph response status and can be 2xx. Branch on the failure code/recovery metadata, not HTTP
status alone. Both these failures and post-create typed `ConnectorError`s carry
`underlying: { draftId, retryable: false, recovery: 'read_edit_existing_draft' }`. Inspect this
metadata before applying any retry policy: read and edit the existing draft using the original
`mailbox`, **never repeat the create action**. A failed response can follow a successful save.
If creation's response is lost or lacks a usable ID, reconcile mailbox state before attempting
another creation. The SDK neither retries creation nor deletes a partially completed draft.

#### Optional Outlook read inputs

`outlook.list_messages` and `outlook.search_messages` accept omitted, `null`, or blank optional
strings for `mailbox`, `folderId`, and `nextLink`; list also accepts these placeholders for `filter`
and `orderBy`. Decoding normalizes them to `undefined`, preserving non-blank strings unchanged.
`top` accepts omission or `null` for the provider default; explicit values must be integers from
1 to 1000. Search still requires a string `query`, and application access still requires a
non-blank `mailbox`. These rules apply to direct connector calls and generated agent tools, not
other Outlook actions.

List and search outputs expose Graph's complete `@odata.nextLink` as `nextLink`. Pass it back
unchanged; repeat `mailbox` for explicit-mailbox continuations and `folderId` for folder
continuations. The connector accepts only global Graph v1.0 links for the selected mailbox and
folder collection. Read and draft-returning requests
use Graph immutable IDs; `outlook.get_message` requests text for the full body. A draft ID can still
change when sent, which is a documented immutable-ID exception.

`outlook.list_attachments` returns normalized metadata with `kind: 'file' | 'item' | 'reference' |
'unknown'`; unlike `hasAttachments`, listing also discovers inline attachments. The list query
selects base attachment properties only and accepts explicit null `lastModifiedDateTime` values.
Do not expect `contentId` in list results; use `outlook.get_attachment` on the individual file
attachment when you need `cid:` mapping.
It accepts `top` and
returns an opaque `nextLink`; pass that link back unchanged with the same `messageId` and `mailbox`.
Use `outlook.get_attachment` with a returned file attachment ID. It requires a Graph file attachment
with valid base64 `contentBytes` and returns required `contentBase64`. Item and reference attachments
remain available only as list metadata and are rejected by this action. Hosts own base64 decoding, size limits,
durable storage, and content scanning.

#### Read state, trash, and move

`outlook.set_read` accepts `{ messageId, isRead, mailbox? }`: `true` marks read and `false` marks
unread via Graph `PATCH`. `outlook.trash` accepts `{ messageId, mailbox? }` and calls Graph `/move`
with destination `deleteditems`, never permanent deletion. `outlook.untrash` accepts
`{ messageId, mailbox?, destinationFolderId? }` and moves from Deleted Items to `inbox` by default,
or the specified folder ID/well-known name. It neither infers the original folder nor recovers
permanently deleted messages. `outlook.move_message` accepts
`{ messageId, mailbox?, destinationFolderId }` with a required destination and moves the message
there. The source folder is not an input, so the connector performs no same-folder check; Graph
decides the outcome. A `deleteditems` destination matches `outlook.trash`: hosts gating on access
should override accordingly.

All four return the updated `OutlookMessage` and request immutable IDs. Use the returned `id`
for subsequent operations. Permission hints are `Mail.ReadWrite` for the signed-in mailbox,
matching connected-user mailboxes, and application mode, or `Mail.ReadWrite.Shared` for other
explicit delegated mailboxes. Application mode
still requires `mailbox`; hosts own consent and Exchange grants. Read-state, restore, and move actions
have `write` access; trash has `destructive` access.

Send actions return `{ accepted: true }` for Graph's `202 Accepted`. Acceptance confirms submission,
not processing or delivery.

### OneDrive actions

OneDrive inputs default to `/me/drive`; set `driveId` to target `/drives/{driveId}`. Default
delegated mode uses least-privilege `Files.Read` or `Files.ReadWrite`. Set integration config
`oneDriveAccessMode` to `delegated_all` to select `Files.Read.All` or `Files.ReadWrite.All` for
broader delegated access. Application-token hosts set it to `application`, must provide `driveId`,
and use the same `Files.*.All` permission hints. The host owns admin consent and application access
policy.

| Action id                | What it does                                                 |
| ------------------------ | ------------------------------------------------------------ |
| `onedrive.list_items`    | list root or folder children with opaque Graph paging        |
| `onedrive.search_items`  | search names, metadata, and indexed content                  |
| `onedrive.get_item`      | fetch metadata by stable DriveItem id                        |
| `onedrive.create_folder` | create a root or child folder with conflict behavior         |
| `onedrive.delete_item`   | move a file or folder to the recycle bin, optionally by ETag |

Pass list/search `nextLink` values back unchanged. Repeat `driveId` for explicit-drive
continuations and `parentItemId` for folder-list continuations. The connector validates the global
Graph origin and selected OneDrive collection before replaying a link.

The current OneDrive **action set** still excludes binary download, upload, and resumable upload
sessions: its HTTP port is string/JSON-oriented. Original-byte download is a separate host helper,
not an action. Host-only create/update use a separate write port; resumable sessions remain unimplemented.

### Host-only OneDrive original-byte download

`downloadOneDriveItem` from `@yolk-sdk/connectors/microsoft` returns original file bytes. It is not
registered on `MicrosoftConnector` and is never serialized by `makeConnectorToolModule`.

```ts
import { downloadOneDriveItem } from '@yolk-sdk/connectors/microsoft'

// Fragment: host-owned integration and selected item IDs from discovery.
const download = downloadOneDriveItem(
  integration,
  { itemId: selectedItem.id, driveId: selectedItem.parentReference?.driveId },
  { maxBytes: 20 * 1024 * 1024, maxMetadataBytes: 1024 * 1024, maxErrorBodyBytes: 16 * 1024 }
)
```

The budgets are trusted host configuration, not tool parameters. Provide the existing
`CredentialResolver` and a compliant `ConnectorBinaryHttpClient` layer; default Microsoft actions
still use only `ConnectorHttpClient`. IDs come from discovery (`itemId`, optional `driveId`).
SharePoint files need a known document-library drive ID; this helper does not discover sites.
Hosts must materialize, scan, and extract the `Uint8Array`; do not put raw bytes into generic
model tool JSON. See [Integration APIs](../api-reference/integrations#connectors) and
[Troubleshooting](../troubleshooting) for adapter and error details.

The built-in endpoint targets the global Microsoft cloud; it does not currently configure
national-cloud Graph hosts.
