---
title: Tools and HITL
description: Define typed tools, expose them to the loop, and pause for human input.
---

Tools are how the model asks your app to do something. Yolk gives you schema-backed registration and protocol events; your app decides which tools are available and how risky calls are approved.

## Define a tool

Use `makeTool` with Effect Schema so validation is the source of truth.

```ts
import { Effect, Schema } from 'effect'
import { ToolResult } from '@yolk-sdk/agent/protocol'
import { makeTool } from '@yolk-sdk/agent/tools'

const EchoParams = Schema.Struct({ text: Schema.String })

export const echoTool = makeTool({
  name: 'echo',
  description: 'Echo text.',
  parameters: EchoParams,
  access: 'read',
  execute: input =>
    Effect.succeed(
      ToolResult.make({
        toolCallId: input.call.id,
        content: input.params.text
      })
    )
})
```

## Resolve tools for a request

Group tools into modules, resolve them for a request context, then pass definitions to the loop.

```ts
import { Effect } from 'effect'
import { makeToolExecutorLayer, resolveTools } from '@yolk-sdk/agent/tools'

const module = { id: 'local', tools: [echoTool] }

const toolSet = await Effect.runPromise(resolveTools([module], requestContext))
const ToolExecutorLayer = makeToolExecutorLayer(toolSet)
```

Pass `toolSet.tools` into `run`/`runRuntime`. Provide `ToolExecutorLayer` alongside your provider, loop config, and context transformer layers. Build a custom `ToolExecutor` layer only when you need advanced dispatch.

## Choose access level

Every tool declares one access level:

| Access        | Use for                                                 |
| ------------- | ------------------------------------------------------- |
| `read`        | search, fetch, inspect                                  |
| `write`       | create/update external state                            |
| `destructive` | delete, execute commands, send messages, mutate broadly |

The SDK records access metadata. Your host enforces approval policy.

## Ask a human

Human-in-the-loop is protocol-level:

- approval requests pause with `AgentAwaitingInput`
- question tools pause with structured options
- clients resume through typed HITL responses

The SDK owns generic event and response shape. Hosts own UI, auth, request matching, audit, and policy.

Use the built-in question tool when the model needs a user choice. Use approval policy when a normal tool call needs permission before execution.

## Let the model choose background execution

Any `makeTool` registration may opt into background execution with `background: true`. The flag is
inert on its own: definitions, schemas, approval ids, and inline execution stay byte-for-byte the
same until `resolveTools` receives a `backgroundHost`. Supply a host only when a real lifecycle
owner (for example a durable Workflow) will run, track, and eventually deliver the work.

```ts
import { Effect, Schema } from 'effect'
import { BackgroundToolAccepted, ToolResult } from '@yolk-sdk/agent/protocol'
import { makeTool, resolveTools, type BackgroundToolHost } from '@yolk-sdk/agent/tools'

export const reportTool = makeTool({
  name: 'build_report',
  description: 'Build a report. Choose background execution for long inputs.',
  parameters: Schema.Struct({ topic: Schema.String }),
  access: 'write',
  background: true,
  execute: input =>
    Effect.succeed(ToolResult.make({ toolCallId: input.call.id, content: 'inline report' }))
})

// Host-owned: durably admit the exact call and return a receipt, never a closure.
const backgroundHost: BackgroundToolHost<RequestContext> = {
  accept: ({ call, context }) =>
    hostReserveExecution({ callId: call.id, name: call.name, params: call.params, context }).pipe(
      Effect.map(execution =>
        BackgroundToolAccepted.make({ version: 1, executionId: execution.id })
      )
    )
}

const toolSet = await Effect.runPromise(
  resolveTools([{ id: 'local', tools: [reportTool] }], requestContext, { backgroundHost })
)
```

With a host, activated tools advertise a required envelope instead of their raw parameters:

```json
{ "execution": "foreground", "arguments": { "topic": "Q3" } }
```

The original schema nests under `arguments` unchanged (including tools whose own parameters are
named `execution`, `arguments`, or `background`), and `$defs` stay at the document root so nested
`#/$defs/...` references keep resolving through OpenAI and Anthropic lowering. Activation supports
only these document-root definition pointers (without percent-encoded fragments). Other `$ref`
forms (root `#`, anchors, `#/properties/...`, `#/definitions/...`, relative or external references)
and resource/anchor keywords (`$id`, legacy `id`, `$anchor`, `$dynamicAnchor`, `$dynamicRef`,
`$recursiveAnchor`, `$recursiveRef`) fail with `ToolRegistryError.cause: 'background_unsupported_schema'`.
This check visits schema positions, not literal defaults, examples, `const`, or `enum` data.
Without activation, schemas remain unchanged. The registry validates the envelope
and the original parameters without running business effects, strips the control fields, and then
either executes inline (`foreground`) or calls `host.accept`. Raw `ToolRegistration` objects must
provide a side-effect-free `validate` callback before they can activate; `resolveTools` fails
closed otherwise, as it does for the loop-owned `question` and `subagent` tools.

Acceptance returns one acknowledgement `ToolResult` for the original call with typed
`acceptance: { version: 1, executionId }` metadata. The loop emits `ToolExecutionAccepted` instead
of `ToolExecutionCompleted`, records no usage, and continues the model turn. Client state, chat
projection, and tool cards treat `Accepted` as settled, non-error, and not completed. Stale client
Started/input events for an accepted call cannot reopen it.

Activated `background-v1` definitions are **unsupported in voice/realtime**, even when a call chooses
`foreground`. Resolve voice toolsets without a background host. `toOpenAiRealtimeTool` and both
realtime session config builders throw `VoiceToolBridgeError` rather than advertise activated tools.
`decideVoiceToolCall` denies them and `handleVoiceToolCall` returns `Denied` before approval matching,
including replayed approvals. The low-level `executeVoiceToolCall` bridge also rejects activated
registry dispatch before validation, inline execution, or host admission. Ordinary voice tools,
including inert `background: true` definitions without a host, retain their existing behavior.

Host responsibilities:

- `accept` must be idempotent per call id so step retries recover the same receipt.
- Own authorization, cancellation, status/wait tools, terminal storage, usage accounting, and delivery.
- Never append a second result for the original call; deliver terminal output through distinct
  status/wait tool-call ids or a later host continuation.
- Fail `accept` with a `ToolError` to decline; the registry never falls back to inline execution.

Manual approval still fences the whole batch before any launch. For activated calls the approval
`requestId` binds the tool name, execution mode, and canonical arguments, so an approval cannot be
reused for a different payload or mode; a malformed envelope is rejected before anyone is asked.
Non-activated tools keep the legacy `approval:<callId>` identity.

## Spawn a subagent

The `subagent` tool contract is domain-free. Hosts provide child execution, prompts, models, tools,
and recursion policy. Current v1 subagents should not receive the `subagent` tool recursively unless
explicitly enabled in a future capability.

Use `subagentResultFromEvents` to extract final or awaiting-input text, status, HITL requests,
usage, turns, and typed `AgentError` details from child events. Pass that metadata to
`makeSubagentToolResult`. Durable hosts
can call `subagentUsageFromToolResult` on completed tool results and add the returned child usage to
their cumulative workflow usage. If a host does not implement nested HITL resume, omit approval- and
question-gated tools from child toolsets rather than returning an unresumable `awaiting_input` result.

### Background subagents

Background execution is opt-in. Set `background: true` in `makeSubagentToolModule` or
`makeNonRecursiveSubagentToolModule` registration options to advertise the optional `background`
model parameter. This does not launch work by itself: your executor must handle `params.background`
and durably start the child. Omitted registration opt-in preserves the inline contract.

After a successful background launch, return `makeSubagentAcceptedToolResult` instead of a final
child result. Host executor fragment; `hostStartChild` and `hostRunInlineChild` are host-owned
implementations:

```ts
import { Effect } from 'effect'
import { makeSubagentAcceptedToolResult } from '@yolk-sdk/agent/tools'

const execute = input =>
  Effect.gen(function* () {
    if (input.params.background !== true) return yield* hostRunInlineChild(input)
    const child = yield* hostStartChild(input)
    return makeSubagentAcceptedToolResult({
      callId: input.call.id,
      workflowRunId: child.runId
    })
  })
```

Acceptance completes the launch tool call, not the child. It emits no `SubagentCompleted` or child
usage. Keep logical `subagent:<callId>` identity separate from the physical Workflow run id.
Observe later results through distinct status/wait tool-call ids, not a second result for the
original launch call; do not charge the same child usage again.

The acknowledgement names `subagent_status` and `subagent_wait`, but these tools are **host-owned**,
not included in the SDK. Supply them before exposing background execution. Your host also owns
authenticated child lookup/routes, durable admission/reservations/results, child HITL handling,
and explicit Stop/cancellation policy. Do not infer that parent completion or failure cancels an
independent child.

For durable hosts, see [Independent child orchestration](../vercel-workflows/step-contracts#independent-child-orchestration).

### Effect-native realtime validation

Use `toOpenAiRealtimeToolEffect`, `makeOpenAiRealtimeSessionConfigEffect`, or
`openAiRealtimeSessionConfigFromVoiceEffect` from `@yolk-sdk/agent/providers/openai/realtime`
in Effect programs. They fail with typed `VoiceToolBridgeError` for activated definitions, so
`Effect.catchTag('VoiceToolBridgeError', ...)` can recover before SDP exchange or other host effects.
The synchronous counterparts remain compatible and throw that error; unexpected defects are not
converted into host-correctable failures.

`makeTool` returns the same structured `model_visible_tool_error` for invalid business arguments
with or without activation, in either execution mode, before business execution or admission.
Malformed envelopes and raw-registration/host `ToolError`s retain their typed failure semantics.

Activated approval IDs intentionally contain the full canonical payload for lossless exact binding.
Hosts must accommodate opaque, potentially long IDs or enforce input bounds before admission.
Never truncate, hash, or rebuild these IDs when storing or returning approvals.
