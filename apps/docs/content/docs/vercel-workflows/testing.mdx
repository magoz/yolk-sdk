Test three layers: package loop contracts, host behavior against a platform emulator, and real
Workflow directives.

Tests whose import graph reaches `workflow`, and tests that execute steps with `TestWorkflowWorld`
(it loads the workflow runtime's serializer), must use Vitest's Node environment, not jsdom, because
Workflow 5 captures Node `URL` intrinsics when the module loads.

## Behavioral platform emulator

`@yolk-sdk/vercel-workflows/testing` exports `TestWorkflowWorld`. Use it to exercise host code
against run lifecycle, append-only stream replay, close-once HTTP 409-style conflicts, step retry
attempts, hooks/resume, cancellation, and the SDK seam consumed by `VercelWorkflows.layerFromSdk`.

This is a test fragment; initialize one world per test and mock the ambient module before importing
the host Workflow under test:

```ts
// @vitest-environment node
import { expect, it, vi } from 'vitest'
import { TestWorkflowWorld } from '@yolk-sdk/vercel-workflows/testing'

vi.mock('workflow', async () => {
  const { testWorkflowModule } = await import('@yolk-sdk/vercel-workflows/testing')
  return testWorkflowModule
})

it('runs host orchestration against Workflow behavior', async () => {
  const world = new TestWorkflowWorld()
  const doubledStep = world.step(async (value: number) => value * 2, 'double')
  const { runId } = world.start(doubledStep, [21])

  expect(world.status(runId)).toBe('pending')
  await world.settled(runId)
  expect(world.status(runId)).toBe('completed')
  await expect(world.sdk.getRun<number>(runId).returnValue).resolves.toBe(42)
})
```

`testWorkflowModule` delegates `getWritable`, `getWorkflowMetadata`, `getStepMetadata`, and
`createHook` to the active world's `AsyncLocalStorage` context, so host code runs unchanged. The
ambient mock does not apply platform retry policy by itself: wrap host step callbacks with
`world.step(...)` or call `world.runStep(...)` when the test must exercise retries and
`getStepMetadata().attempt`. Use `world.inspect(runId)` for stream closure, write-after-close
attempts, step attempts, status, run errors, and `unstorableStepErrors` (`stepName`, `attempt`,
`error`). Use `world.sdk` with
`VercelWorkflows.layerFromSdk` when testing Effect route/service boundaries.

### Step errors

Step errors cross the platform boundary as they do in a deployment. `world.runStep` stores each
thrown value with the installed `workflow` runtime's step-error serializer and throws only the value
read back, so error tags, prototypes, and custom fields are gone and `cause` survives:

- A `FatalError` (named `FatalError`, or with `fatal: true`) is never retried; an `AbortError` is
  promoted to one, as the platform does.
- An exhausted step fails with the platform's `FatalError` whose `cause` is the last thrown value;
  its message reads `Step "<name>" failed after N retries: <message>`.
- A value the platform cannot store, such as an error with a class instance in its `cause` chain,
  never reaches the workflow body. The platform redelivers the step instead, so the world runs it
  again as the next attempt. Past the budget the step fails, without a cause, with
  `Step "<name>" exceeded max retries (N retries)`. `world.inspect(runId).unstorableStepErrors`
  lists every such value.

Carry anything the workflow body must read across the boundary as plain data, for example in an
error's `cause`, and assert `unstorableStepErrors` is empty in tests of your step failures.

## Pure contract tests

Use normal Vitest tests for `runVercelAgentWorkflow` with fake callbacks.

```ts
import { expect, it } from 'vitest'
import { runVercelAgentWorkflow } from '@yolk-sdk/vercel-workflows'

it('continues from tool results', async () => {
  const result = await runVercelAgentWorkflow({
    input: { request: 'request-1', context: 'ctx-1' },
    runModelStep: async input =>
      input.state.turn === 1
        ? {
            done: false,
            messages: ['user', 'assistant'],
            createdMessages: ['assistant'],
            toolCalls: ['tool-a'],
            usage: { turns: 1 },
            turn: 1
          }
        : {
            done: true,
            messages: ['user', 'assistant', 'tool-result', 'final'],
            createdMessages: ['assistant', 'tool-result', 'final'],
            toolCalls: [],
            usage: { turns: 2 },
            turn: 2
          },
    runToolBatchStep: async input => ({
      messages: ['tool-result'],
      createdMessages: [...input.createdMessages, 'tool-result']
    }),
    closeStream: async () => undefined,
    writeError: async () => undefined
  })

  expect(result._tag).toBe('Completed')
})
```

## Directive tests

Use `@workflow/vitest` for files that exercise `'use workflow'`, `'use step'`, hooks, streams, and cancellation.

```ts
import { getRun, resumeHook, start } from 'workflow/api'
import { waitForHook } from '@workflow/vitest'
```

Cover:

- starting host Workflow functions with `start`
- reading stream chunks and replaying with `getRun(runId).getReadable({ startIndex })`
- waiting for hooks with `waitForHook`
- resuming with `resumeHook`
- cancellation with `getRun(runId).cancel()`

## Assertions to keep

- A `done: false` model result with no tool calls continues directly to the next model step.
- One ordered tool-result message per tool call.
- HITL reruns the same tool batch with accumulated responses.
- Event sequence advances across model, tool, and HITL resume.
- Default retries are disabled.
- Retried streamed steps have de-dupe-ready event ids.
- Terminal write happens only after durable commit succeeds.
- `AgentEnd` closes exactly once through `closeStream`.
- Failure paths use `writeError`, not `closeStream`; a `writeError` rejection preserves the original
  structured failure result.
- `AgentAwaitingInput` does not close before resume; resumed execution can append and eventually
  close.
