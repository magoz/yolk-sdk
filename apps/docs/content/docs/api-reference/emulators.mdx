---
title: Emulator APIs
description: Experimental service emulators, HttpClient routing to them, and a loopback server.
---

> **Experimental.** `@yolk-sdk/emulators` may change in any canary release. It is new after
> `0.1.0-canary.95`; keep it on the same lockstep version as the other public packages.

`@yolk-sdk/emulators` runs stand-ins for outside services in tests and local development, and
routes an Effect `HttpClient` to them instead of the real service. The email emulator is a
port-level fake instead: a plain-JSON `EmailClient` backend. Emulators never import other
`@yolk-sdk/*` code: their wire shapes follow the conformance fixtures (verified recordings for the
Gateway, synthetic placeholders elsewhere), and each emulated route names the conformance cases it
follows. The package depends on `effect`; the Node-only `fortnox`, `microsoft`, `dropbox`, `notion`,
`todoist`, `telegram`, and `github` subpaths also depend on the upstream `@emulators/core` runtime
(Apache-2.0, pinned to exactly `0.12.0`).

There is no root export. Import an explicit subpath.

## Router

`@yolk-sdk/emulators/router`

| Export                              | Purpose                                                                                                           |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `EmulatorRoute`                     | `{ origin, target }`; `EmulatorRoute.url(origin, baseUrl)` and `EmulatorRoute.handler(origin, fetch)` build one   |
| `EmulatedHttpClient.layer(routes)`  | Rewrites each routed origin to a loopback base URL (path and query kept) over the `HttpClient` already in context |
| `InProcessHttpClient.layer(routes)` | Calls the route's fetch handler directly with a web `Request`; returns `HttpClientResponse.fromWeb`               |
| `EmulatorRouteInvalid`              | Build error: malformed or duplicate origin, wrong target kind, or a base URL that is not http(s) on loopback      |
| `EmulatorEnvironmentRefused`        | Build error: `NODE_ENV` is `production` or cannot be read (a missing `NODE_ENV` is allowed)                       |

Pick the transport by swapping layers; the code under test keeps calling the real origin:

| Transport | Layer                                                        |
| --------- | ------------------------------------------------------------ |
| Replay    | `ReplayHttpClient.layer` from `@yolk-sdk/conformance/replay` |
| InProcess | `InProcessHttpClient.layer`                                  |
| Emulated  | `EmulatedHttpClient.layer` over your `HttpClient`            |
| Live      | your own `HttpClient`                                        |

Both layers fail closed: a request to an origin without a route fails with an `HttpClientError`
whose message names only the origin (never the path, query, headers, or body). Emulated base URLs
must be `http(s)` on `127.0.0.0/8`, `::1`, or `localhost` (IPv4-mapped forms such as
`[::ffff:127.0.0.1]` are rejected). The in-process client sends `Empty`, `Uint8Array`, and string
`Raw` bodies; other body kinds fail with an `EncodeError`.

`EmulatedHttpClient` routes at the send step, so redirect follow-ups (`HttpClient.followRedirects`
on top) and URLs changed by your `HttpClient.mapRequest` are routed or fail closed too. Over
`FetchHttpClient`, routed requests use `redirect: 'manual'`, so a 3xx reaches the caller as a 3xx;
other `RequestInit` defaults are kept when provided around the whole client stack. Put
`HttpClient.followRedirects` on top of `EmulatedHttpClient`, never underneath it. Any other
underlying client must not follow redirects by itself.

```ts
import { Layer } from 'effect'
import { makeGatewayEmulator } from '@yolk-sdk/emulators/gateway'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const gateway = makeGatewayEmulator()

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://ai-gateway.vercel.sh', gateway.fetch)
])
```

Provide `httpLayer` below the code under test, for example a Gateway provider layer.

## Gateway emulator

`@yolk-sdk/emulators/gateway`

| Export                                  | Purpose                                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `makeGatewayEmulator(options?)`         | `{ fetch, ledger, reset, faults, script, coverage }` for `POST /v1/chat/completions`             |
| `gatewayEmulatorRoutes`                 | Route evidence manifest: `method`, `path`, `kind`, `write`, `caseIds`, `evidence`, `observedAt`  |
| `GatewayFault`, `GatewayScriptedTurn`   | Schemas and types for wire faults and scripted turns                                             |
| `GatewayLedgerEntry`, `GatewayCoverage` | Ledger entry and coverage report types                                                           |
| `gatewayEmulatorDefaultModels`          | Synthetic-safe default model ids (includes `openai/gpt-4.1-nano` and the DeepSeek ids)           |
| `gatewayEmulatorDefaultReasoningModels` | `deepseek/deepseek-v3.2` and `deepseek/deepseek-v4.1-flash`                                      |
| `gatewayEmulatorDefaultEventsPerChunk`  | `2`: SSE events per network chunk by default                                                     |
| `emulatorEvidenceHeader`                | `x-emulator-evidence`, set to `unverified` on every response from an unverified route            |
| `GatewayEmulatorInputInvalid`           | Thrown by `faults.add` / `script.enqueue` for invalid input, and for an invalid `eventsPerChunk` |

The Gateway route is `verified`: its wire shapes follow the verified live recordings of
2026-09-30 in `@yolk-sdk/agent/providers/vercel/conformance`, with synthetic ids, costs, and
routing metadata. Without a script, a known model gets synthetic output. `stream: true` streams
`chat.completion.chunk` events as recorded: a `{ role: 'assistant' }` opening delta, several text
deltas, then one finish event whose `delta` carries `provider_metadata` and which carries `usage`
(when `stream_options.include_usage` is set), `system_fingerprint`, `service_tier` (`openai/*`
models only), and `generationId`, followed only by `data: [DONE]`. Events are packed
`eventsPerChunk` per network chunk (option, default 2; counted from the end, so the finish event
and `data: [DONE]` share the last chunk). `stream: false` returns one JSON completion (not covered
by a recording). Reasoning models asked for reasoning (`reasoning_effort`, or `thinking` enabled)
stream `delta.reasoning` with `delta.reasoning_details` first. A request with `tools` gets one tool
call whose arguments are synthesized from the tool's JSON Schema and streamed in several
fragments, finishing with `tool_calls`; a `tool_choice` naming an offered function picks that tool
(otherwise the first), and `tool_choice: 'none'` answers with text. Unknown models get the
recorded 404 envelope `{ error: { message, type: 'model_not_found', param: { modelId } } }` (no
`code`), a missing bearer credential gets 401, and unknown routes get a 404 JSON error. The
credential is never checked or stored.

`script.enqueue(turn)` queues a completion (`text`, `reasoning`, `reasoningField`, `order`,
`toolCalls`, `usage`, `finishReason`; `usage: null` drops usage, `reasoningField` defaults to
`reasoning`) or an error (`{ error: { status, body, headers? } }`) for the next request.
`faults.add` injects `status` (for example 429 with `retry-after`), `error-after-chunks`, or
`truncate-after-chunks`, each with an optional `match: { path?, model? }` and `count`; chunk faults
count network chunks, each packing up to `eventsPerChunk` events. Emulators never redirect and always send a body: fault and scripted-error statuses
exclude 1xx, 204, 205, and every 3xx (including 304), header names and values must be valid, and a
`location` header is rejected.

The ledger records every emulated API request (control-plane requests are not recorded): method,
path, parsed body, model, `stream`, the `max_tokens` limit (`maxCompletionTokens`, never
validated), `reasoning_effort`, `thinking`, tool names, the applied fault,
the evidence tag, the status actually sent, and body chunks sent; never credential headers. When a
planned response cannot be built, the emulator answers an evidence-tagged 500, records it with
`responseError`, and does not use up the fault. The same fetch handler serves the control plane:

| Route                | Methods                 |
| -------------------- | ----------------------- |
| `/_emulate/ledger`   | `GET`, `DELETE`         |
| `/_emulate/faults`   | `GET`, `POST`, `DELETE` |
| `/_emulate/script`   | `POST`                  |
| `/_emulate/reset`    | `POST`                  |
| `/_emulate/state`    | `GET`                   |
| `/_emulate/coverage` | `GET`                   |

## Anthropic emulator

`@yolk-sdk/emulators/anthropic`

| Export                                      | Purpose                                                                            |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `makeAnthropicEmulator(options?)`           | `{ fetch, ledger, reset, faults, script, coverage }` for `POST /v1/messages`       |
| `anthropicEmulatorRoutes`                   | Route evidence manifest linked to the Anthropic Messages conformance cases         |
| `AnthropicFault`, `AnthropicScriptedTurn`   | Schemas and types for wire faults (including a mid-stream `error` event) and turns |
| `AnthropicLedgerEntry`, `AnthropicCoverage` | Ledger entry and coverage report types                                             |
| `anthropicEmulatorDefaultModels`            | Synthetic-safe default model ids (`claude-haiku-4-5`, `claude-sonnet-4-5`)         |
| `AnthropicEmulatorInputInvalid`             | Thrown by `faults.add` / `script.enqueue` for invalid input                        |

It stands in for Anthropic Messages at `https://api.anthropic.com`. `stream: true` streams the
events in the order the API sends them: `message_start` (input usage), then per content block
`content_block_start`, its deltas, and `content_block_stop` (a `ping` follows the first block
start), then `message_delta` (`stop_reason`, and usage with input and cache counts next to
`output_tokens`, as the unverified fixtures record it) and `message_stop`; `stream: false`
returns one `message` JSON body. A request with `thinking` enabled (`enabled` or `adaptive`) gets a
`thinking` block (`thinking_delta` events, then a `signature_delta`) before the text. A request
with `tools` gets one `tool_use` block whose input is synthesized from the tool's `input_schema`
and streamed as `input_json_delta` fragments, stopping with `tool_use`; `tool_choice: { type:
'tool', name }` picks that tool and `tool_choice: { type: 'none' }` answers with text. An answer
that would not fit `max_tokens` is cut and stops with `max_tokens`.

Errors use the Anthropic envelope `{ type: 'error', error: { type, message } }`: an unknown model
gets 404 `not_found_error`; a missing or unsupported `anthropic-version` (only `2023-06-01`, the
value the SDK providers send), a missing or non-positive `max_tokens`, or `thinking` with a forced
`tool_choice` (`tool` or `any`) gets 400 `invalid_request_error`; and a request with neither a non-empty `x-api-key` (native API keys) nor
an `Authorization: Bearer` credential (Claude OAuth) gets 401 `authentication_error`. Neither
credential is checked or stored; the ledger records which header carried it
(`credentialHeader`), `anthropic-version`, `anthropic-beta`, `max_tokens` (`maxTokens`),
`thinking`, `tool_choice`, and tool names. The OAuth `anthropic-beta` header and `budget_tokens`
limits are not enforced.

Scripted turns are messages (`thinking`, `text`, `toolUses` with `inputFragments`, `order`,
`usage`, `stopReason`; `usage: null` drops usage, `order: 'text-first'` sends thinking after the
text) or errors. Faults are `status` (the default body is the envelope for the status, for
example `rate_limit_error` for 429 and `overloaded_error` for 529), `error-after-chunks`,
`truncate-after-chunks` (for example before `message_stop`), and `error-event-after-chunks`
(N events, then an `event: error` with `overloaded_error` by default; streamed responses only,
and only before `message_stop`). Faults, the ledger, and the control plane are shared with the
Chat Completions emulators.

## Responses emulators

`@yolk-sdk/emulators/codex` and `@yolk-sdk/emulators/xai`

| Export                                                       | Purpose                                                                                      |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `makeCodexEmulator(options?)`                                | `{ fetch, ledger, reset, faults, script, coverage }` for `POST /backend-api/codex/responses` |
| `makeXAiGrokEmulator(options?)`                              | The same for `POST /v1/responses` on the Grok CLI proxy                                      |
| `codexEmulatorRoutes`, `xAiGrokEmulatorRoutes`               | Route evidence manifests linked to the Codex and Grok Responses conformance cases            |
| `CodexFault`, `CodexScriptedTurn`, `XAiGrok*`                | Schemas and types for wire faults (including mid-stream error events) and turns              |
| `CodexLedgerEntry`, `XAiGrokLedgerEntry`                     | Ledger entry types                                                                           |
| `codexEmulatorDefaultModels`, `xAiGrokEmulatorDefaultModels` | Synthetic-safe default model ids                                                             |
| `CodexEmulatorInputInvalid`, `XAiGrokEmulatorInputInvalid`   | Thrown by `faults.add` / `script.enqueue` for invalid input                                  |

They stand in for the ChatGPT Codex endpoint at `https://chatgpt.com` and the xAI Grok CLI proxy
at `https://cli-chat-proxy.grok.com`, on one shared OpenAI Responses core. `stream: true` streams
server-sent events with typed `event:` names and a `sequence_number`, in the API's order:
`response.created`, `response.in_progress`, then per output item `response.output_item.added`, its
parts and deltas, and `response.output_item.done`, then `response.completed` with the full
`response` and `usage`; `stream: false` returns one completed `response` JSON body. A request whose
`reasoning` asks for a `summary` gets a `reasoning` item (summary part and
`response.reasoning_summary_text.delta` events) first; answers are a `message` item
(`response.output_text.delta`); a request with function `tools` gets one `function_call` item whose
arguments are synthesized from the tool's JSON Schema and streamed as
`response.function_call_arguments.delta` fragments.

Errors use `{ error: { message, type, param, code } }`: an unknown model gets 400
`model_not_found`, and a request without a non-empty `Authorization: Bearer` credential gets 401
`invalid_api_key` (never checked or stored). `/codex` answers `max_output_tokens` with 400
`unsupported_parameter` (the endpoint takes no output limit) and records `originator`. `/xai`
requires, in order, `X-XAI-Token-Auth` (401), `x-grok-client-version` (426), and
`x-grok-model-override` (400); it records the client version and model override (never the
token-auth value) and records `max_output_tokens` as `maxOutputTokens`.

Scripted turns are responses (`reasoning`, `text`, `functionCalls` with `argumentFragments`,
`order`, `usage`, and `format: 'json'` for a JSON body even on `stream: true`) or errors. Faults are
`status` (for example 429 with `retry-after`), `error-after-chunks`, `truncate-after-chunks` (for
example before `response.completed`), and `error-event-after-chunks` (N events, then an `error`
event, or a `response.failed` event with `event: 'response.failed'`; streamed responses only, and
only before `response.completed`).

## Fixture-only routes

The OpenCode Go routes and the Claude, Codex, and Grok subscription-usage routes are fixture-only;
the earlier model routes above keep their behaviour. A request matching a recorded request's shape
gets that fixture's recorded response (same status, headers, and bytes). Everything else answers
one 400 not-emulated, written to the ledger and using up no fault or turn:
`{ error: { type: 'not_emulated', message } }`. That covers unknown routes and methods, missing or
invalid credentials, missing or other headers and query parameters, unknown models, non-streamed
modes, tools, reasoning, and extra fields. No provider status or error envelope is guessed.

Accepted request-shape latitude: any credential value; extra headers; key order; any string value
except `model`, `role`, `type`, and `phase`; any positive integer where the recording has a number
(the output-token limit); an `anthropic-beta` list that includes `oauth-2025-04-20`; any
non-empty Grok `x-userid` and `x-grok-client-version`; and `content-type` parameters. The query
string must match byte for byte (a bare `?` counts as no query), and Grok's `X-XAI-Token-Auth` (`xai-grok-cli`) and
`x-grok-client-mode` (`headless`) must be the SDK's fixed values. Test controls are the shared faults, scripted error turns, and, on usage
routes, a scripted `{ usage }` body or `subscriptionUsage` option with the recorded JSON shape;
fault and scripted-error statuses are 400-599 only. All
of these routes are `unverified` (synthetic fixtures).

## Subscription-usage routes

The Anthropic, Codex, and Grok emulators also answer their provider's subscription-usage endpoint
on the same origin, with their own manifest, ledger, faults, turns, and coverage (`emulator.usage`,
control plane `/_emulate/usage/*`). The model route's manifest and coverage are unchanged; the
emulator types gain `usage` and a `subscriptionUsage` option.

| Emulator     | Route                            | Headers the fetcher sends (all required)                                              | Manifest                                   |
| ------------ | -------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------ |
| `/anthropic` | `GET /api/oauth/usage`           | Bearer, `anthropic-beta` listing `oauth-2025-04-20`                                   | `anthropicSubscriptionUsageEmulatorRoutes` |
| `/codex`     | `GET /backend-api/wham/usage`    | Bearer, `ChatGPT-Account-Id`                                                          | `codexSubscriptionUsageEmulatorRoutes`     |
| `/xai`       | `GET /v1/billing?format=credits` | Bearer, `X-XAI-Token-Auth`, `x-userid`, `x-grok-client-version`, `x-grok-client-mode` | `xAiGrokSubscriptionUsageEmulatorRoutes`   |

Each answers its recorded synthetic snapshot body (`*SubscriptionUsageDefault`) for a request with
those headers, `accept: application/json`, and exactly the recorded query; anything else is 400
not-emulated. Credential and account values are never recorded, and are not checked except Grok's
fixed `X-XAI-Token-Auth: xai-grok-cli`.

## Email emulator

`@yolk-sdk/emulators/email`

| Export                                                                                          | Purpose                                                                                                   |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `makeEmailEmulator({ seed? })`                                                                  | `{ call, state, seed, ledger, reset, faults, coverage }`: a fixture-driven fake `EmailClient` backend     |
| `emailEmulatorRoutes`                                                                           | Route evidence manifest: one `PORT EmailClient.<method>` route per emulated method, linked to email cases |
| `emailEmulatorPort`, `emailEmulatorRouteMethod`                                                 | Helpers: `EmailClient` and `PORT`, the port name and pseudo method of the manifest routes                 |
| `EmailEmulatorSpecialUse`, `EmailEmulatorFolder`, `EmailEmulatorMessage`                        | Seed schemas: SPECIAL-USE attributes, folders, and messages                                               |
| `emailEmulatorDefaultSeed`, `EmailEmulatorSeed`                                                 | The synthetic practice mailbox the fixtures describe (folders, SPECIAL-USE attributes, messages)          |
| `EmailEmulatorFault`, `EmailEmulatorLedgerEntry`, `EmailEmulatorReply`, `EmailEmulatorCoverage` | Fault schema, ledger entry, reply, and coverage types                                                     |
| `emailEmulatorFixtures`                                                                         | The email conformance `PortFixture`s, copied as data                                                      |
| `EmailEmulatorInputInvalid`                                                                     | Thrown for an invalid seed or fault                                                                       |

Yolk never speaks IMAP, POP3, or SMTP, and neither does this emulator: no socket, TLS, MIME, or
mail library, no Node builtin, and no SDK import. `call(method, request)` takes one `EmailClient`
call as plain JSON (without credential fields) and answers `{ response }`, `{ failure }`, or
`{ notEmulated: { reason } }`. `emailClientLayerFromBackend(emulator)` from
`@yolk-sdk/connectors/email/conformance` turns it into the `EmailClient` layer.

Responses come only from the email conformance fixtures. The in-memory mailbox only selects the
first matching fixture consistent with it (preferring fixtures unused since the last reset) and
records what that fixture says happened (flags set, a draft appended, a message moved to the
destination id the fixture names, a message deleted, a Sent copy saved); it never invents an id,
flag, or response.

- Request-shape latitude: credential fields are never compared or recorded, and `connection.host`
  is not compared. Every other connection field (`protocol`, `port`, `security`) and everything
  else must equal a fixture request.

Anything else fails closed with a ledgered `notEmulated` answer, the port analogue of HTTP 400:
`unknown-method`, `invalid-request`, `no-matching-fixture`, or `state-conflict`. Faults
(`{ kind: 'failure', method, match?, count?, failure }`, `match` a deep subset of the request)
change no state. `reset()` restores the seed and clears the ledger, faults, and fixture use.

## Fortnox emulator

`@yolk-sdk/emulators/fortnox`

> **Experimental, Node only.** A stateful stand-in for the Fortnox `/3` API, built on the
> `@emulators/core` custom runtime (loaded lazily when you create an emulator).

| Export                                          | Purpose                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `makeFortnoxEmulator(options?)`                 | `Promise` of `{ fetch, baseUrl, ledger, faults, reset, seed, snapshot, coverage, close }`        |
| `fortnoxEmulatorRoutes`                         | Route evidence manifest (every route is `unverified`; four are connector write routes)           |
| `fortnoxEmulatorQuirks`                         | The observed quirks it implements, each with its conformance case id and drill knob              |
| `FortnoxEmulatorSeed`, `FortnoxEmulatorProfile` | Typed seed schema (`profile`, `company`, `customers`, `invoices`) and account-variance profiles  |
| `FortnoxFault`                                  | `{ kind: 'status', status, headers?, body?, match?: { method?, path? }, count? }`                |
| `fortnoxEmulatorErrorCodes`                     | `ErrorInformation` codes (customer-not-found codes from the fixtures; `2999xxx` codes synthetic) |
| `FortnoxEmulatorInputInvalid`                   | Invalid seed, fault, or option passed to the JS API                                              |

It serves `GET /3/companyinformation`, `GET /3/customers`, `GET`/`PUT /3/customers/{CustomerNumber}`,
`GET`/`POST /3/invoices`, `GET`/`PUT /3/invoices/{DocumentNumber}`,
`GET /3/invoices/{DocumentNumber}/preview` (a small synthetic PDF), and
`GET /3/invoices/{DocumentNumber}/email` (marks the invoice sent and records an outbox entry in
state; nothing is ever delivered). Requests need `Authorization: Bearer <non-empty>`; the token is
never stored or ledgered. Anything else fails closed with a 404 `ErrorInformation`, and unsupported
query parameters or fields get a 400 instead of being ignored.

The default seed holds the synthetic fixture entities with the same numbers as
`fortnoxConformanceFixtureSeeds`, so the Fortnox conformance cases run unmodified against it.
Profiles: `default`, `empty-company`, `no-booked-invoices`. `reset()` restores the seed; `seed()`
replaces it.

It implements the quirks the Fortnox cases claim: an omitted row `Discount` stays on positional row
updates (`Discount: 0` clears; RowIds regenerate; totals are recomputed); an empty customer string
keeps the stored value; `unpaid`/`unpaidoverdue`/`fullypaid` skip unbooked invoices
(`unpaidoverdue` uses the injectable `now` clock); rejected writes answer 400 `ErrorInformation`;
customer `Country` is read-only.

The `quirks` option (`stickyRowDiscount: false`, `emptyStringClears: true`,
`paymentFiltersIncludeUnbooked: true`) is a test-only drill knob: it flips one quirk to prove that
the matching conformance case fails.

Fortnox faults are `status` faults only
(`{ kind: 'status', status, headers?, body?, match?: { method?, path? }, count? }`), answered
before the route runs, so nothing is written. They follow
the Gateway emulator's rules: statuses without a body (1xx, 204, 205) and redirects (3xx) are
rejected, as are invalid header names or values, a `location` header, and framing headers, both in
`faults.add` and in `POST /_emulate/faults`. A fault is used up only after its response is built;
a response that cannot be built answers an evidence-tagged 500 `ErrorInformation` recorded in the
ledger with `responseError`. The control plane serves `/_emulate/ledger`, `faults`, `reset`,
`state`, `seed`, and `coverage`; unlike the Gateway, it has no scripted turns and no chunk
faults, and `reset`/`seed` also restore or replace the Fortnox state.

```ts
import { makeFortnoxEmulator } from '@yolk-sdk/emulators/fortnox'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const fortnox = await makeFortnoxEmulator({ seed: { profile: 'default' } })

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://api.fortnox.se', fortnox.fetch)
])
```

## Microsoft Graph emulator

`@yolk-sdk/emulators/microsoft`

> **Experimental, Node only.** A stateful stand-in for the Microsoft Graph v1.0 routes the Microsoft
> conformance cases use (calendar, Outlook mail, OneDrive) plus the OneDrive copy monitor URL,
> built on the same `@emulators/core` runtime (loaded lazily when you create an emulator).

| Export                                                                       | Purpose                                                                                                                       |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `makeMicrosoftEmulator(options?)`                                            | `Promise` of `{ fetch, baseUrl, sharePointOrigin, ledger, faults, monitors, reset, seed, snapshot, coverage, close }`         |
| `microsoftEmulatorRoutes`                                                    | Route evidence manifest (19 routes, all `unverified`; eleven are connector write routes)                                      |
| `MicrosoftEmulatorSeed`, `MicrosoftEmulatorProfile`                          | Typed seed schema (`profile`, `user`, `mailFolders`, `messages`, `attachments`, `calendars`, `events`, `drive`, `driveItems`) |
| `MicrosoftFault`                                                             | `{ kind: 'status', status, headers?, body?, match?: { method?, path? }, count? }`                                             |
| `microsoftEmulatorErrorCodes`                                                | Graph error codes, in three groups (below)                                                                                    |
| `MicrosoftEmulatorInputInvalid`                                              | Invalid seed, fault, or option passed to the JS API                                                                           |
| `microsoftEmulatorDefaultOrigin`, `microsoftEmulatorDefaultSharePointOrigin` | `https://graph.microsoft.com` and `https://synthetic-my.sharepoint.com` (the copy monitor host)                               |

Route both origins to the same fetch handler (the paths never overlap, so one loopback server serves
both):

```ts
import { makeMicrosoftEmulator } from '@yolk-sdk/emulators/microsoft'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const microsoft = await makeMicrosoftEmulator()

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://graph.microsoft.com', microsoft.fetch),
  EmulatorRoute.handler(microsoft.sharePointOrigin, microsoft.fetch)
])
```

It serves, under `/v1.0`: `calendarView` (events overlapping `[startDateTime, endDateTime)`), event
create, get, update, delete, and `cancel` (202; the event is removed, so later reads and deletes are
404); folder message listing (by folder id) with `$top`/`$skip` and an opaque `@odata.nextLink`;
draft create, update, and move to Deleted Items; attachment listing (inline included, never
`contentId`) and retrieval (with `contentId`); `$batch` with draft `permanentDelete` subrequests
only; and OneDrive item read, children listing, folder create, delete, and file copy (202 with one
monitor `Location`). Folder message listings, calendar views, and children listings need `$top`, at
most the largest value a fixture sends (2, 50, and 200); calendar views and children listings
answer one page. The monitor URL needs no credential; its first poll answers `completed` with a
`resourceId`, as the copy fixture records (`copyInProgressPolls`, default 0, adds `inProgress`
answers first). Graph routes need `Authorization: Bearer <non-empty>`; the token is never stored or
ledgered, and credential-named keys in ledgered bodies and queries are redacted. Responses carry
the fixtures' `@odata.context` envelopes.

Behaviour comes only from the conformance fixtures. Everything they do not show fails closed with
the Graph error envelope `{ error: { code, message, innerError } }`: `/me` paths and other unknown
routes get 404; query keys, `$select` fields, body properties (including unknown nested keys), and
values the emulator does not emulate get a 400 before anything is written. That includes Outlook
requests without `Prefer: IdType="ImmutableId"` and calendar requests without
`Prefer: outlook.timezone="UTC"` (every fixture of theirs sends it), writes to messages that are
not drafts, moves to any destination but `deleteditems`, folder listings by well-known name,
`If-Match`, conflict behaviors other than `fail`, name conflicts, folder or renamed copies, and
failed copies. A route handler that throws answers a 500 envelope recorded in the ledger. The few
behaviours the cases need without a fixture (the concurrency window, advancing id counters, removal
on delete, synthesized seed values), the request-shape latitude it accepts (for example optional `$select`,
smaller `$top`, user aliases, subsets of the fixture body keys), and the opt-in in-progress copy
polls are listed in the package README under "Emulator extrapolations (no fixture)".

`microsoftEmulatorErrorCodes` groups:

- **From the fixtures:** `ErrorItemNotFound`, `itemNotFound`, `ErrorIrresolvableConflict`.
- **Documented Graph codes (no fixture):** `InvalidAuthenticationToken` (missing bearer),
  `ErrorInvalidUser` (a user other than the seeded mailbox), `TooManyRequests` (the default 429
  fault body).
- **Synthetic emulator codes:** `SyntheticRouteNotEmulated`, `SyntheticQueryNotEmulated`,
  `SyntheticValueNotEmulated`, `SyntheticInvalidRequest`, `SyntheticInvalidBody`,
  `SyntheticUpstreamError`.

Messages keep their immutable id across moves. Event times are UTC with seven fractional digits.
For concurrent writes, the first write to reach the handler holds the message for
`conflictWindowMs` (default 25); an overlapping write gets 409 `ErrorIrresolvableConflict`;
non-overlapping writes both apply (an emulator extrapolation). The default seed is the synthetic
fixture entities with the same ids as `microsoftConformanceFixtureSeeds`; profiles `default` and
`empty`. Faults, the ledger (which also records the `Prefer` header), and the `/_emulate/*` control
plane behave as in the Fortnox emulator; `reset` and `seed` also clear copy monitors. The `drills`
option (`calendarRangeEmpty`, `createOmitsId`, `timestampPrecisionDigits`, `omitNextLink`) is a
test-only drill knob that makes the matching conformance case fail.

## Dropbox emulator

`@yolk-sdk/emulators/dropbox`

> **Experimental, Node only.** A stateful stand-in for the Dropbox `/2` RPC and upload routes the
> Dropbox conformance cases use, built on the same `@emulators/core` runtime (loaded lazily when you
> create an emulator). It is fixture-only, without exceptions: it answers only what the
> conformance fixtures show.

| Export                                                     | Purpose                                                                                                     |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `makeDropboxEmulator(options?)`                            | `Promise` of `{ fetch, fetchOn, ledger, faults, cursors, reset, seed, snapshot, coverage, close }`          |
| `dropboxEmulatorRoutes`                                    | Route evidence manifest (10 routes, all `unverified`; five are connector write routes)                      |
| `DropboxEmulatorSeed`, `DropboxEmulatorProfile`            | Typed seed schema (`profile`, `entries` by display path, `deleted`)                                         |
| `DropboxFault`                                             | `{ kind: 'status', status (400-599), headers?, body?, match?: { method?, path? }, count? }`                 |
| `dropboxEmulatorErrorBodies`                               | The fixtures' 409 `error_summary` envelopes, byte for byte (`notFound`, `folderConflict`, `uploadConflict`) |
| `DropboxEmulatorInputInvalid`                              | Invalid seed, fault, or option passed to the JS API                                                         |
| `dropboxEmulatorApiOrigin`, `dropboxEmulatorContentOrigin` | `https://api.dropboxapi.com` (RPC) and `https://content.dropboxapi.com` (upload)                            |

Each route answers only on the origin its fixtures record. `fetch` reads the origin from the
request URL (in-process routing keeps it); behind a loopback rewrite, serve `fetchOn(origin)` for
each origin on its own server:

```ts
import { makeDropboxEmulator } from '@yolk-sdk/emulators/dropbox'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const dropbox = await makeDropboxEmulator()

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://api.dropboxapi.com', dropbox.fetch),
  EmulatorRoute.handler('https://content.dropboxapi.com', dropbox.fetch)
])
```

It serves, as `POST` under `/2/files`: `list_folder` and `list_folder/continue` (cursor paging; every
page carries a cursor), `get_metadata` (case-insensitive lookups; `path_display` keeps the stored
casing of the last component only; `include_deleted: true` answers `deleted` metadata after an empty
folder's delete), `search_v2` and `search/continue_v2` (file name matches in the nested `metadata`
envelope; a cursor only with `has_more`), `create_folder_v2` (metadata without `.tag`; an existing
folder in any casing is a 409 `path/conflict/folder`), `delete_v2` (by path or `id:`; folders and
their content), `copy_v2` (a new file with the source's size and content hash) and `move_v2` (the
same id), and `upload` on the content host (`add` never overwrites; `update` by `id:` needs the
current rev; both conflicts are 409 `path/conflict/file`). Route errors are the fixtures' HTTP 409
`error_summary` envelopes. Every route needs `Authorization: Bearer <non-empty>`; the token is never
stored or ledgered.

Every answer value comes from a fixture, or is a value the emulator mints (created ids and revs from
counters that start above the seeded ones, content hashes derived from revs, upload timestamps from
the injectable `now` clock, and cursors). Folders a fixture never shows (the parents of the seeded
paths) are implied: never rendered. A cursor is accepted only when this emulator issued it since the
last reset and its listing or search renders exactly as when it was issued. Anything else answers
one ledgered 400 not-emulated (`{ error: { type: 'not_emulated', message } }`), writes nothing, and
uses up no fault: each route's pure, state-reading eligibility check runs before a fault is
decided. That includes a listing of an empty folder and a search without matches (no fixture
records either), so `findDropboxConformanceLeftovers` fails against the default seed's empty work
folder with `DropboxConformanceActionFailed` (HTTP 400), which the live runner reports as its
lookup-failed `WARN`.

- Request-shape latitude (`/dropbox`, the only accepted deviations): any bearer value (never
  checked or stored); extra request headers; JSON key order; `content-type` media-type parameters;
  any path and search query (looked up in the state); any `list_folder` `limit` from 1 to 2000 and
  any `search_v2` `options.max_results` from 1 to 1000; and any upload body bytes. Everything else
  (other keys, booleans, modes, query parameters, another origin, ids or revs where the fixtures
  send paths, the root folder, and cursors not issued since the last reset or whose listing
  changed) is not emulated.

The default seed is the synthetic fixture entries at the paths of `dropboxConformanceFixtureSeeds`;
profiles `default` and `empty`. Faults (statuses 400-599, default body
`{ error: { type: 'emulator_fault', message } }`), the ledger (which records the `Dropbox-API-Arg`
header and any JSON-looking query value with credential-named keys redacted, and an upload's length,
never its bytes), and the `/_emulate/*` control plane behave as in the Microsoft Graph emulator;
`reset` and `seed` also clear cursors. The `drills` option (eight booleans, one per Dropbox case) is
a test-only drill knob that makes exactly the matching conformance case fail. The package README
lists the routes, wire behaviour, minted values, and refusals in full.

## Notion emulator

`@yolk-sdk/emulators/notion`

> **Experimental, Node only.** A stateful stand-in for the Notion `/v1` routes the Notion conformance
> cases use at API version `2025-09-03`, built on the same `@emulators/core` runtime (loaded lazily
> when you create an emulator). It is fixture-only, without exceptions: it answers only what the
> conformance fixtures show.

| Export                                          | Purpose                                                                                                                  |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `makeNotionEmulator(options?)`                  | `Promise` of `{ fetch, fetchOn, ledger, faults, reset, seed, snapshot, coverage, close }`                                |
| `notionEmulatorRoutes`                          | Route evidence manifest (10 routes, all `unverified`; two are connector write routes)                                    |
| `NotionEmulatorSeed`, `NotionEmulatorProfile`   | Typed seed schema (`profile`, `botUser`, `pages`, `impliedPages`, `blocks`, `propertyItems`, `databases`, `dataSources`) |
| `NotionFault`                                   | `{ kind: 'status', status (400-599), headers?, body?, match?: { method?, path? }, count? }`                              |
| `NotionEmulatorInputInvalid`                    | Invalid seed, fault, or option passed to the JS API                                                                      |
| `notionEmulatorOrigin`, `notionEmulatorVersion` | `https://api.notion.com` and `2025-09-03`                                                                                |

```ts
import { makeNotionEmulator } from '@yolk-sdk/emulators/notion'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const notion = await makeNotionEmulator()

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://api.notion.com', notion.fetch)
])
```

It serves, under `/v1`: `POST /search` (pages by title, `filter` `object: page` only), `GET
/users/me` (the bot user), `GET /pages/{id}` (trashed pages too; 404 `object_not_found` and 400
`validation_error` envelopes as the fixtures record them), `POST /pages` (the recorded create: a
child of a page titled `yolk-conformance page: safe to delete`), `PATCH /pages/{id}` with
`{ archived: true }` (the page with `archived` and `in_trash` true; it still reads back), `GET
/blocks/{id}/children`, `GET /pages/{id}/properties/{propertyId}` (the property id decoded once, so
the connector's second percent-encoding names it), and the database / data source split: `GET
/databases/{id}` lists its `data_sources`, `GET /data_sources/{id}` holds the schema and names its
database, and `POST /data_sources/{id}/query` with `page_size: 1` answers the recorded first row,
whose parent is the data source, and the next row's id as its cursor. Lists page with `has_more`
and `next_cursor`, and the last page carries `next_cursor: null`. Every route needs
`Authorization: Bearer <non-empty>` (never stored or ledgered) and `Notion-Version: 2025-09-03`,
and answers only on the recorded origin `https://api.notion.com` (`notionEmulatorOrigin`): `fetch`
reads the origin from the request URL; behind a loopback rewrite, serve
`fetchOn(notionEmulatorOrigin)`.

Every answer value comes from a fixture, or is a value the emulator mints (created page ids from a
counter that starts above the seeded ones, their timestamps from the injectable `now` clock,
request ids, and cursors). Pages a fixture only names by id (the blocks page, the parent
pages, the next query row) are implied: their ids resolve where a fixture names them, but they are
never rendered, and search considers only the pages whose content the state holds, so an implied
page never matches. A cursor is accepted only when this emulator issued it for the same list since
the last reset or seed and the list renders exactly as when it was issued. No cursor value crosses
a reset or seed: property cursors come from a counter that never resets, and search and block
cursors are the next result's id (the fixture's value) only in the generation that first issued
that id for that list, `<id>.g<generation>` afterwards, so a pre-reset cursor stays refused even
after the same first-page request. Anything else answers one ledgered
400 not-emulated, writes nothing, and uses up no fault: unknown routes and methods, another
origin, other `Notion-Version` values, query parameters a route does not take, a missing `page_size`, other
search filters, a search without matches or whose matches include a trashed page or a page shown
only as a query row, children of a page without recorded child blocks, `sorts` and query filters, a
query page that would show an unrecorded row, creates with `children`, under a database, or with another
title, page updates other than `{ archived: true }`, and archiving a missing or already trashed
page. So `findNotionConformanceLeftovers` fails against a clean workspace or after the write case
(no match, or a trashed match) with `NotionConformanceActionFailed` (HTTP 400), which the live
runner reports as its lookup-failed `WARN`.

- Request-shape latitude (`/notion`, the only accepted deviations): any bearer value (never checked
  or stored); extra request headers; JSON key order; `content-type` media-type parameters; the
  order of query parameters; Notion ids with or without dashes, in any case; any search `query`
  (looked up in the state); and any `page_size` from 1 to 100 whose page shows only recorded results
  (the data source query: 1). `Notion-Version` must be `2025-09-03`. Everything else (other keys,
  filters, booleans, sorts, query parameters, another origin, titles, repeated or missing `page_size`, and cursors
  not issued for the same list since the last reset or whose list changed) is not emulated.

The default seed is the synthetic fixture entities with the same ids as
`notionConformanceFixtureSeeds`; profiles `default` and `empty`; an archived page stays in the
state, in the trash. Faults, the ledger (which records the `Notion-Version` header), and the control
plane behave as in the Dropbox emulator. The `drills` option (eight booleans, one per Notion case)
is a test-only drill knob that makes exactly the matching conformance case fail.

## Todoist emulator

`@yolk-sdk/emulators/todoist`

> **Experimental, Node only.** A stateful, fixture-only stand-in for the Todoist API v1 routes the
> Todoist conformance cases use, built on the same `@emulators/core` runtime (loaded lazily when you
> create an emulator).

| Export                                          | Purpose                                                                                                |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `makeTodoistEmulator(options?)`                 | `Promise` of `{ fetch, ledger, faults, cursors, reset, seed, snapshot, coverage, close }`              |
| `todoistEmulatorRoutes`                         | Route evidence manifest (nine routes, all `unverified`; five are connector write routes)               |
| `TodoistEmulatorSeed`, `TodoistEmulatorProfile` | Typed seed schema (`profile`, `userId`, `projects`, `tasks`, `labels`); profiles `default` and `empty` |
| `TodoistFault`                                  | `{ kind: 'status', status (400-599), headers?, body?, match?: { method?, path?, route? }, count? }`    |
| `TodoistEmulatorInputInvalid`                   | Invalid seed or fault passed to the JS API                                                             |
| `todoistEmulatorDefaultOrigin`                  | `https://api.todoist.com`                                                                              |

```ts
import { makeTodoistEmulator } from '@yolk-sdk/emulators/todoist'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const todoist = await makeTodoistEmulator()

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://api.todoist.com', todoist.fetch)
])
```

It serves, under `/api/v1` with `Authorization: Bearer <token>` (at least 8 characters; never stored
or ledgered, and refused when the path, query, or body repeats it): `GET /tasks` (active tasks of a
project, REST v1 cursor paging with `next_cursor`), task create, read, update, and close, `GET
/labels`, and project create, read, and delete (which removes the project's task). Case projects are
named `yolk-conformance-<runId>-<case>` with any `run-` run id, so a live runner's `run-<hex>` ids
work. Bodies, 404 envelopes (`{ error, error_code, error_extra, error_tag, http_code }`), cursors,
and due objects follow the synthetic fixtures; created ids (reserved prefix `6XEmu`, which seeds may
not use) and `event_id`s come from counters that only advance, timestamps from the injectable `now`
clock, and cursors are valid only as issued since the last reset or seed.

It is **fixture-only**, with no synthesised answers: anything the fixtures do not record answers one
ledgered 400 `{ error: { type: 'not_emulated', message } }` before anything is written and before
any fault is chosen, for example other routes, body fields such as `labels` or `due_string`, other
due values, task listings other than the paging project with `limit=2` or a case project created
here without `limit`, unpaged label listings larger than `limit`, a closed task, reading a seeded
project (no fixture records its object), writes to seeded items (only items created through the
recorded create flow are updated, closed, or deleted), and a second task in a case project or a
second sub-project (the fixtures record `child_order: 1` only). That includes the project listing
(`GET /projects`) of the read-only leftover lookup `findTodoistConformanceLeftovers`, which no
fixture records: the lookup fails (`todoist_list_projects_failed`, HTTP 400), and the repository
runners print their lookup-failed WARN instead of leftover warnings.

Unrecognised requests (no emulated route under that HTTP method, or raw id segments that are not
Todoist ids) are ledgered and answered with constant text only: the path `/<unrecognised>`, a
standard method or `<other>`, no query or body, and a constant reason. So is a request whose
`Authorization` header is present but is not one recognisable bearer, whatever its route: its
credential cannot be extracted and scrubbed.

Run write cases sequentially on one emulator, or `reset()` between cases: a seeded parent takes one
case project at a time (the fixtures record `child_order: 1` only), so concurrent write cases, or a
case that failed before its cleanup, make later project creates answer not-emulated (a definitive
rejection: nothing is created).

Accepted request-shape latitude: any credential value of at least 8 characters that occurs nowhere
else in the request (its path, query, or body; never checked against anything, stored, or ledgered);
extra request headers; `content-type` parameters; query parameters in any order; any Todoist id
(1-64 of `[A-Za-z0-9_-]`) of an existing item where a fixture has an id (reads: seeded or created
tasks and created projects; task listings: the paging project with `limit=2` and case projects
created here without `limit`; writes: only items created through the recorded create flow; a new
project's `parent_id`: a seeded project); any `run-` run id (at most 40 characters) in a case
project name; any non-empty task `content`; a task update sending `content`, `due_datetime`, or
both; a label listing `limit` of 1 to 200 that covers every label. The `drills` option
(`cursorRestarts`, `notFoundWithoutError`, `taskLabelsAsIds`, `listIncludesClosed`, `ignoreDue`,
`createOmitsParent`, `deleteKeepsTasks`) is a test-only knob that makes exactly one Todoist case
fail.

## Telegram emulator

`@yolk-sdk/emulators/telegram`

> **Experimental, Node only.** A stateful, fixture-only stand-in for the Telegram Bot API routes the
> Telegram conformance cases use, built on the same `@emulators/core` runtime (loaded lazily when
> you create an emulator).

| Export                                            | Purpose                                                                                              |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `makeTelegramEmulator(options?)`                  | `Promise` of `{ fetch, ledger, faults, reset, seed, snapshot, coverage, close }`                     |
| `telegramEmulatorRoutes`                          | Route evidence manifest (four routes, all `unverified`; `sendMessage` is a connector write route)    |
| `TelegramEmulatorSeed`, `TelegramEmulatorProfile` | Typed seed schema (`profile`, `bot`, `chats`, `files`, `nextMessageId`); profiles `default`, `empty` |
| `TelegramFault`                                   | `{ kind: 'status', status (400-599), headers?, body?, match?: { method?, path?, route? }, count? }`  |
| `TelegramEmulatorInputInvalid`                    | Invalid seed or fault passed to the JS API                                                           |
| `telegramEmulatorDefaultOrigin`                   | `https://api.telegram.org`                                                                           |

It serves `POST /bot<token>/getChat` (a member chat, or the recorded 400 `chat not found`), `GET
/bot<token>/getFile?file_id=...`, the hosted file download `GET /file/bot<token>/<file_path>`, and
`POST /bot<token>/sendMessage`. **The bot token is required but never stored, forwarded, ledgered,
or echoed.** The emulator fails closed: only a request whose raw path is exactly one of these route
shapes (the strict token on the raw segment, an emulated method, no other path text) is recognised,
and its token is taken from that exact segment. Every other request is ledgered and answered with
constant text only (the path `/<unrecognised>`, a standard method or `<other>`, no query or body, a
constant reason), so an encoded separator, a malformed token, or extra segments carry nothing into
the ledger. For a recognised request, the token and its secret part are scrubbed from the ledgered
method, path (`/bot<redacted>/...`), query keys and values, and every not-emulated message, and a
query, remaining path, or body that repeats them (raw, percent-decoded, or in any parsed JSON key,
string value, or number) is refused with constant text. A token whose bot id is `0` names no bot
(`getChat` answers the recorded 401). A send is irreversible on the real service; the emulator
records it in its state (`sentMessages`) and never delivers anything.

It is **fixture-only**, like the Todoist emulator: anything else answers the ledgered 400
not-emulated. Accepted request-shape latitude: any credential value of at least 8 characters that
occurs nowhere else in the request (its path, query, or body; never checked against anything,
stored, or ledgered); extra request headers; `content-type` parameters; a well-formed
`<digits>:<secret>` bot token with a secret of at least 8 characters (the bot id `0` names no bot);
any well-formed `chat_id` string (an integer or a public `@username`; one the bot is not in answers
the recorded 400 on `getChat`); any non-empty message `text`. The `drills` option (`getChatOkFalse`,
`errorsAs200`, `fileSizeOffByOne`, `sendOkFalse`) makes exactly one Telegram case fail.

Both emulators share faults (status only, 400-599, chosen only after the request passed every check,
including the route's eligibility check against the state, and answered before the commit, so a
refused request never uses one and nothing is written; a 429 reaches the connector as
`todoist_rate_limited` / `telegram_rate_limited`), the ledger (credential-named query and body keys
redacted, guarded credential values scrubbed), clock-free recovery (a handler that throws answers an
evidence-tagged 500 `emulator_error` recorded with `responseError`; a closed emulator answers 503),
and the `/_emulate/*` control plane (`ledger`, `faults`, `reset`, `state`, `seed`, `coverage`).

stored, or ledgered), `Accept: application/vnd.github+json` (`githubEmulatorAccept`), and
`X-GitHub-Api-Version: 2026-03-10` (`githubEmulatorApiVersion`), and answers only on the recorded
origin `https://api.github.com` (`githubEmulatorOrigin`): `fetch` reads the origin from the request
URL; behind a loopback rewrite, serve `fetchOn(githubEmulatorOrigin)`.

Every answer value comes from a fixture, or is a value the emulator mints: created issue numbers and
comment ids from counters that only advance (the default seed starts at the fixtures' issue `42` and
comment `9000000001`, a seed's counters lie above its seeded numbers, no seeded node id may use a
minted form at or above its counter, and a create past the last addressable number or id is
refused), the issue and comment ids derived from them in the fixtures' form, and timestamps from the
injectable `now` clock. Issue numbers below the counter that the state does not hold are implied,
never rendered. Label pages are page numbers, not cursors, and the label list never changes within a
seed (no route writes labels). A deleted comment's id and a closed issue stay in the state (GitHub
keeps both), so a write case ends at the seed except those and the counters.

It fails closed: only a request whose raw path is exactly an emulated route shape under that route's
method, with no `Authorization` header or exactly `Bearer <token>`, is recognised. Every other
request is ledgered and answered with constant text only (the path `/<unrecognised>`, a standard
method or `<other>`, no query or body, a constant reason). A recognised bearer must match the RFC
6750 `b64token` syntax exactly (`^[A-Za-z0-9\-._~+/]+=*$`, at least 8 characters) and hold at least
one character outside the JSON-number alphabet `[0-9.eE+-]` (every GitHub and Google token form
does: `ghp_…`, `github_pat_…`, `gho_…`, `ya29.…`). So no number's text can contain it, and it holds
none of the characters the transforms consume (`\`, `%`, `"`), so no neighbouring escape can shift
across its own characters; an `Authorization` header with any other value is unrecognisable. A
recognised request that repeats the bearer value in its raw path, any path segment, the raw query or
any query key or value, any recorded header, or its body is refused and ledgered with constant text
only: a standard method, the path `/<unrecognised>`, its route template, an empty query, no headers
or body, and a constant reason (`the query repeats the credential`, for example). Each part is
checked through a bounded closure of two total, lexical transforms that cannot fail: a tolerant
percent-decode (every `%XX` below `%80` becomes its ASCII character; any other `%` sequence is left
as it is) and a tolerant JSON-unescape (in any text, whether or not it parses as JSON, `\uXXXX`
below `\u0080` and `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t` become their characters). Starting
from each part's raw text, up to 4 rounds apply either transform to every text of the previous
round, deduplicated, and every intermediate text is checked for the bearer as a substring. So each
part's raw text gets 4 layers of percent-encoding or JSON escaping, in any order: the raw path and
each raw path segment, the raw query and each query key and value (already decoded once by
`URLSearchParams`, so one layer more), each recorded header, and the raw body (whose own JSON
escaping costs a round only where it escapes the bearer's text). Any other recognised request has
the bearer value scrubbed from its ledgered fields and every not-emulated reason (plan-time reasons
included); its recorded query is keyed by recorded key; a key recorded more than once lists its
values in order (as a JSON array); and recorded headers and query keys and values that start like
JSON (`{`, `[`, `"`) are recorded parsed with credential-named keys redacted at any depth, or as
`<redacted>` when they do not parse, whatever the header's declared format. Also, refusals never
echo a request's own query or body keys; empty query components are refused. It is **fixture-only**:
anything else answers the ledgered 400 not-emulated before anything is written and before any fault
is chosen, for example other routes, issue creates with labels or assignees, updates other than the
two recorded ones (so the lifecycle case's failure-path restore, which closes as `not_planned`, is
not emulated), adding a label the repository lacks (it would create it), a comment listing of more
than one comment, rendering an issue that holds comments (every fixture answers `comments: 0`), and
writes to closed or implied issues. That includes the open-issue listing of the read-only leftover
lookup `findGithubConformanceLeftovers`, which no fixture records: the lookup fails
(`github_validation`, HTTP 400), and the repository runner prints its lookup-failed WARN instead of
leftover warnings.

- Request-shape latitude (`/github`, the only accepted deviations): any bearer value in the RFC 6750
  `b64token` syntax (`[A-Za-z0-9\-._~+/]+=*`) of at least 8 characters, at least one outside
  `[0-9.eE+-]`, that occurs nowhere else in the request (never compared against anything, stored, or
  ledgered); extra request headers; JSON key order; `content-type` media-type parameters; the order
  of query parameters; any non-empty issue title and comment body, and any issue body text; any
  comment listing `since` of the form `YYYY-MM-DDTHH:MM:SSZ`; any label listing `per_page` from 1 to
  100, with no `page` or a `page` from 2 to one past the last page; any issue search `q` that starts
  with the seeded `repo:<owner>/<repo>` qualifier and whose query after it is longer than 256
  characters (answered the recorded 422); any issue number the repository has not reached (answered
  the recorded 404); and any issue, comment, repository label, or file the state holds where a
  fixture has one, under the per-route state rules. `Authorization` must be exactly `Bearer <token>`
  (that spelling, one space), `Accept` `application/vnd.github+json`, and `X-GitHub-Api-Version`
  `2026-03-10`. Everything else (other keys and values, query parameters, empty query components
  such as a bare `?` or a stray `&`, another origin or repository, a repeated query key, an explicit
  `page=1`, and a comment listing `per_page` other than 100) is not emulated.

Faults, the ledger (which records the `Accept` and `X-GitHub-Api-Version` headers), clock-free
recovery, and the control plane behave as in the Dropbox emulator; a 429 fault reaches the
connector as `github_rate_limited`. The `drills` option (seven booleans, one per GitHub case) is a
test-only knob that makes exactly the matching conformance case fail.

## Node server

`@yolk-sdk/emulators/node`

| Export                                    | Purpose                                                                           |
| ----------------------------------------- | --------------------------------------------------------------------------------- |
| `serveFetchHandler(handler, { port? })`   | Scoped Effect resource `{ url, close }` serving on `127.0.0.1` (port `0` default) |
| `startFetchHandlerServer(handler, opts?)` | The same server as a Promise `{ url, close }`, for non-Effect test runners        |
| `EmulatorServeError`                      | Refused host, invalid port, or listen failure                                     |

Only `127.0.0.1` is accepted as a host. Streamed bodies are written chunk by chunk, so progressive
delivery survives the socket; a body stream error drops the connection.

## Evidence

Emulated routes carry evidence: `verified` routes follow a live observation dated by `observedAt`;
`unverified` routes follow synthetic placeholders. Fetch-handler emulators tag every response from
an unverified route with `x-emulator-evidence: unverified`; the email emulator's plain-JSON replies
carry no header, so it records the evidence on each ledger entry instead. The Gateway route is
verified (`observedAt: '2026-09-30'`): the emulator follows the verified live Gateway recordings,
and the Yolk repository checks its response shapes against each recording. The OpenAI, Anthropic,
Codex, Grok, OpenCode Go, subscription-usage, email, Fortnox, Microsoft, Dropbox, Notion, Todoist,
Telegram, and GitHub routes are unverified, like the synthetic fixtures they follow. The email write
routes are connector writes: until an owner-approved live run against a practice mailbox, through a
host `EmailClient` implementation, verifies them, the repository lists them in a time-bounded
allowlist
(`scripts/emulator-evidence-pending.json`), and the evidence check reports them as PENDING warnings
until each entry's expiry date and fails again after it. The four Fortnox write routes, the eleven
Microsoft write routes, the five Dropbox write routes, the two Notion write routes, the five Todoist
write routes, the Telegram `sendMessage` route, and the six GitHub write routes are held in the same
pending list until a live run against a Fortnox test company, a Microsoft practice tenant, a Dropbox
practice account, a Notion practice workspace, a Todoist practice account, a practice bot, or a
GitHub practice repository verifies them.
