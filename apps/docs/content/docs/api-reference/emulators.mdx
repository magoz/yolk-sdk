---
title: Emulator APIs
description: Experimental service emulators, HttpClient routing to them, and a loopback server.
---

> **Experimental.** `@yolk-sdk/emulators` may change in any canary release. It is new after
> `0.1.0-canary.95`; keep it on the same lockstep version as the other public packages.

`@yolk-sdk/emulators` runs stand-ins for outside services in tests and local development, and routes
an Effect `HttpClient` to them instead of the real service. The email and R2 emulators are
port-level fakes instead: plain-JSON backends for `EmailClient` and for `R2Presigner` and
`R2ObjectClient`. Emulators never import other `@yolk-sdk/*` code: their wire shapes follow the
conformance fixtures (verified recordings for the Gateway, synthetic placeholders elsewhere), and
each emulated route names the conformance cases it follows. The package depends on `effect`; the
Node-only `fortnox`, `microsoft`, `dropbox`, `notion`, `todoist`, `telegram`, `github`, `google`,
`linkedin-search`, and `mcp` subpaths also depend on the upstream `@emulators/core` runtime
(Apache-2.0, pinned to exactly `0.12.0`).

There is no root export. Import an explicit subpath.

## Router

`@yolk-sdk/emulators/router`

| Export                              | Purpose                                                                                                           |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `EmulatorRoute`                     | `{ origin, target }`; `EmulatorRoute.url(origin, baseUrl)` and `EmulatorRoute.handler(origin, fetch)` build one   |
| `EmulatedHttpClient.layer(routes)`  | Rewrites each routed origin to a loopback base URL (path and query kept) over the `HttpClient` already in context |
| `InProcessHttpClient.layer(routes)` | Calls the route's fetch handler directly with a web `Request`; returns `HttpClientResponse.fromWeb`               |
| `EmulatorRouteInvalid`              | Build error: malformed or duplicate origin, wrong target kind, or a base URL that is not http(s) on loopback      |
| `EmulatorEnvironmentRefused`        | Build error: `NODE_ENV` is `production` or cannot be read (a missing `NODE_ENV` is allowed)                       |

Pick the transport by swapping layers; the code under test keeps calling the real origin:

| Transport | Layer                                                        |
| --------- | ------------------------------------------------------------ |
| Replay    | `ReplayHttpClient.layer` from `@yolk-sdk/conformance/replay` |
| InProcess | `InProcessHttpClient.layer`                                  |
| Emulated  | `EmulatedHttpClient.layer` over your `HttpClient`            |
| Live      | your own `HttpClient`                                        |

Both layers fail closed: a request to an origin without a route fails with an `HttpClientError`
whose message names only the origin (never the path, query, headers, or body). Emulated base URLs
must be `http(s)` on `127.0.0.0/8`, `::1`, or `localhost` (IPv4-mapped forms such as
`[::ffff:127.0.0.1]` are rejected). The in-process client sends `Empty`, `Uint8Array`, and string
`Raw` bodies; other body kinds fail with an `EncodeError`.

`EmulatedHttpClient` routes at the send step, so redirect follow-ups (`HttpClient.followRedirects`
on top) and URLs changed by your `HttpClient.mapRequest` are routed or fail closed too. Over
`FetchHttpClient`, routed requests use `redirect: 'manual'`, so a 3xx reaches the caller as a 3xx;
other `RequestInit` defaults are kept when provided around the whole client stack. Put
`HttpClient.followRedirects` on top of `EmulatedHttpClient`, never underneath it. Any other
underlying client must not follow redirects by itself.

```ts
import { Layer } from 'effect'
import { makeGatewayEmulator } from '@yolk-sdk/emulators/gateway'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const gateway = makeGatewayEmulator()

const httpLayer = InProcessHttpClient.layer([
  EmulatorRoute.handler('https://ai-gateway.vercel.sh', gateway.fetch)
])
```

Provide `httpLayer` below the code under test, for example a Gateway provider layer.

## Gateway emulator

`@yolk-sdk/emulators/gateway`

| Export                                            | Purpose                                                                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `makeGatewayEmulator(options?)`                   | `{ fetch, ledger, reset, faults, script, coverage }` for `POST /v1/chat/completions`             |
| `gatewayEmulatorRoutes`                           | Route evidence manifest: `method`, `path`, `kind`, `write`, `caseIds`, `evidence`, `observedAt`  |
| `gatewayEvaluateEmulatorRoutes`                   | Manifest of the fixture-only classifier route `POST /v1/evaluate` (`unverified`)                 |
| `GatewayEvaluateFault`, `GatewayEvaluateEmulator` | Classifier-route fault schema and its emulator API (`emulator.evaluate`)                         |
| `GatewayFault`, `GatewayScriptedTurn`             | Schemas and types for wire faults and scripted turns                                             |
| `GatewayLedgerEntry`, `GatewayCoverage`           | Ledger entry and coverage report types                                                           |
| `gatewayEmulatorDefaultModels`                    | Synthetic-safe default model ids (includes `openai/gpt-4.1-nano` and the DeepSeek ids)           |
| `gatewayEmulatorDefaultReasoningModels`           | `deepseek/deepseek-v3.2` and `deepseek/deepseek-v4.1-flash`                                      |
| `gatewayEmulatorDefaultEventsPerChunk`            | `2`: SSE events per network chunk by default                                                     |
| `emulatorEvidenceHeader`                          | `x-emulator-evidence`, set to `unverified` on every response from an unverified route            |
| `GatewayEmulatorInputInvalid`                     | Thrown by `faults.add` / `script.enqueue` for invalid input, and for an invalid `eventsPerChunk` |

The Gateway route is `verified`: its wire shapes follow the verified live recordings of
2026-09-30 in `@yolk-sdk/agent/providers/vercel/conformance`, with synthetic ids, costs, and
routing metadata. Without a script, a known model gets synthetic output. `stream: true` streams
`chat.completion.chunk` events as recorded: a `{ role: 'assistant' }` opening delta, several text
deltas, then one finish event whose `delta` carries `provider_metadata` and which carries `usage`
(when `stream_options.include_usage` is set), `system_fingerprint`, `service_tier` (`openai/*`
models only), and `generationId`, followed only by `data: [DONE]`. Events are packed
`eventsPerChunk` per network chunk (option, default 2; counted from the end, so the finish event
and `data: [DONE]` share the last chunk). `stream: false` returns one JSON completion (not covered
by a recording). Reasoning models asked for reasoning (`reasoning_effort`, or `thinking` enabled)
stream `delta.reasoning` with `delta.reasoning_details` first. A request with `tools` gets one tool
call whose arguments are synthesized from the tool's JSON Schema and streamed in several
fragments, finishing with `tool_calls`; a `tool_choice` naming an offered function picks that tool
(otherwise the first), and `tool_choice: 'none'` answers with text. Unknown models get the
recorded 404 envelope `{ error: { message, type: 'model_not_found', param: { modelId } } }` (no
`code`), a missing bearer credential gets 401, and unknown routes get a 404 JSON error. The
credential is never checked or stored.

`script.enqueue(turn)` queues a completion (`text`, `reasoning`, `reasoningField`, `order`,
`toolCalls`, `usage`, `finishReason`; `usage: null` drops usage, `reasoningField` defaults to
`reasoning`) or an error (`{ error: { status, body, headers? } }`) for the next request.
`faults.add` injects `status` (for example 429 with `retry-after`), `error-after-chunks`, or
`truncate-after-chunks`, each with an optional `match: { path?, model? }` and `count`; chunk faults
count network chunks, each packing up to `eventsPerChunk` events. Emulators never redirect and always send a body: fault and scripted-error statuses
exclude 1xx, 204, 205, and every 3xx (including 304), header names and values must be valid, and a
`location` header is rejected.

The same fetch handler answers the classifier route `POST /v1/evaluate` (AI Gateway calls
classification "evaluation"), fixture-only: a request matching one of the four synthetic
classifier recordings in `@yolk-sdk/agent/providers/vercel/conformance` (the `model` and question
`type` exact, any other string, the recorded question ids, option keys, and level count) gets the
recorded answer; anything else answers 400 not-emulated. It has its own unverified manifest
(`gatewayEvaluateEmulatorRoutes`), ledger, faults (statuses 400-599), scripted errors, and coverage
(`emulator.evaluate`, control plane `/_emulate/evaluate/*`); `reset()` resets both routes.

The ledger records every emulated API request (control-plane requests are not recorded): method,
path, parsed body, model, `stream`, the `max_tokens` limit (`maxCompletionTokens`, never
validated), `reasoning_effort`, `thinking`, tool names, the applied fault,
the evidence tag, the status actually sent, and body chunks sent; never credential headers. When a
planned response cannot be built, the emulator answers an evidence-tagged 500, records it with
`responseError`, and does not use up the fault. The same fetch handler serves the control plane:

| Route                | Methods                 |
| -------------------- | ----------------------- |
| `/_emulate/ledger`   | `GET`, `DELETE`         |
| `/_emulate/faults`   | `GET`, `POST`, `DELETE` |
| `/_emulate/script`   | `POST`                  |
| `/_emulate/reset`    | `POST`                  |
| `/_emulate/state`    | `GET`                   |
| `/_emulate/coverage` | `GET`                   |

## Anthropic emulator

`@yolk-sdk/emulators/anthropic`

| Export                                      | Purpose                                                                            |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `makeAnthropicEmulator(options?)`           | `{ fetch, ledger, reset, faults, script, coverage }` for `POST /v1/messages`       |
| `anthropicEmulatorRoutes`                   | Route evidence manifest linked to the Anthropic Messages conformance cases         |
| `AnthropicFault`, `AnthropicScriptedTurn`   | Schemas and types for wire faults (including a mid-stream `error` event) and turns |
| `AnthropicLedgerEntry`, `AnthropicCoverage` | Ledger entry and coverage report types                                             |
| `anthropicEmulatorDefaultModels`            | Synthetic-safe default model ids (`claude-haiku-4-5`, `claude-sonnet-4-5`)         |
| `AnthropicEmulatorInputInvalid`             | Thrown by `faults.add` / `script.enqueue` for invalid input                        |

It stands in for Anthropic Messages at `https://api.anthropic.com`. `stream: true` streams the
events in the order the API sends them: `message_start` (input usage), then per content block
`content_block_start`, its deltas, and `content_block_stop` (a `ping` follows the first block
start), then `message_delta` (`stop_reason`, and usage with input and cache counts next to
`output_tokens`, as the unverified fixtures record it) and `message_stop`; `stream: false`
returns one `message` JSON body. A request with `thinking` enabled (`enabled` or `adaptive`) gets a
`thinking` block (`thinking_delta` events, then a `signature_delta`) before the text. A request
with `tools` gets one `tool_use` block whose input is synthesized from the tool's `input_schema`
and streamed as `input_json_delta` fragments, stopping with `tool_use`; `tool_choice: { type:
'tool', name }` picks that tool and `tool_choice: { type: 'none' }` answers with text. An answer
that would not fit `max_tokens` is cut and stops with `max_tokens`.

Errors use the Anthropic envelope `{ type: 'error', error: { type, message } }`: an unknown model
gets 404 `not_found_error`; a missing or unsupported `anthropic-version` (only `2023-06-01`, the
value the SDK providers send), a missing or non-positive `max_tokens`, or `thinking` with a forced
`tool_choice` (`tool` or `any`) gets 400 `invalid_request_error`; and a request with neither a non-empty `x-api-key` (native API keys) nor
an `Authorization: Bearer` credential (Claude OAuth) gets 401 `authentication_error`. Neither
credential is checked or stored; the ledger records which header carried it
(`credentialHeader`), `anthropic-version`, `anthropic-beta`, `max_tokens` (`maxTokens`),
`thinking`, `tool_choice`, and tool names. The OAuth `anthropic-beta` header and `budget_tokens`
limits are not enforced.

Scripted turns are messages (`thinking`, `text`, `toolUses` with `inputFragments`, `order`,
`usage`, `stopReason`; `usage: null` drops usage, `order: 'text-first'` sends thinking after the
text) or errors. Faults are `status` (the default body is the envelope for the status, for
example `rate_limit_error` for 429 and `overloaded_error` for 529), `error-after-chunks`,
`truncate-after-chunks` (for example before `message_stop`), and `error-event-after-chunks`
(N events, then an `event: error` with `overloaded_error` by default; streamed responses only,
and only before `message_stop`). Faults, the ledger, and the control plane are shared with the
Chat Completions emulators.

## Responses emulators

`@yolk-sdk/emulators/codex` and `@yolk-sdk/emulators/xai`

| Export                                                       | Purpose                                                                                      |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `makeCodexEmulator(options?)`                                | `{ fetch, ledger, reset, faults, script, coverage }` for `POST /backend-api/codex/responses` |
| `makeXAiGrokEmulator(options?)`                              | The same for `POST /v1/responses` on the Grok CLI proxy                                      |
| `codexEmulatorRoutes`, `xAiGrokEmulatorRoutes`               | Route evidence manifests linked to the Codex and Grok Responses conformance cases            |
| `CodexFault`, `CodexScriptedTurn`, `XAiGrok*`                | Schemas and types for wire faults (including mid-stream error events) and turns              |
| `CodexLedgerEntry`, `XAiGrokLedgerEntry`                     | Ledger entry types                                                                           |
| `codexEmulatorDefaultModels`, `xAiGrokEmulatorDefaultModels` | Synthetic-safe default model ids                                                             |
| `CodexEmulatorInputInvalid`, `XAiGrokEmulatorInputInvalid`   | Thrown by `faults.add` / `script.enqueue` for invalid input                                  |

They stand in for the ChatGPT Codex endpoint at `https://chatgpt.com` and the xAI Grok CLI proxy
at `https://cli-chat-proxy.grok.com`, on one shared OpenAI Responses core. `stream: true` streams
server-sent events with typed `event:` names and a `sequence_number`, in the API's order:
`response.created`, `response.in_progress`, then per output item `response.output_item.added`, its
parts and deltas, and `response.output_item.done`, then `response.completed` with the full
`response` and `usage`; `stream: false` returns one completed `response` JSON body. A request whose
`reasoning` asks for a `summary` gets a `reasoning` item (summary part and
`response.reasoning_summary_text.delta` events) first; answers are a `message` item
(`response.output_text.delta`); a request with function `tools` gets one `function_call` item whose
arguments are synthesized from the tool's JSON Schema and streamed as
`response.function_call_arguments.delta` fragments.

Errors use `{ error: { message, type, param, code } }`: an unknown model gets 400
`model_not_found`, and a request without a non-empty `Authorization: Bearer` credential gets 401
`invalid_api_key` (never checked or stored). `/codex` answers `max_output_tokens` with 400
`unsupported_parameter` (the endpoint takes no output limit) and records `originator`. `/xai`
requires, in order, `X-XAI-Token-Auth` (401), `x-grok-client-version` (426), and
`x-grok-model-override` (400); it records the client version and model override (never the
token-auth value) and records `max_output_tokens` as `maxOutputTokens`.

Scripted turns are responses (`reasoning`, `text`, `functionCalls` with `argumentFragments`,
`order`, `usage`, and `format: 'json'` for a JSON body even on `stream: true`) or errors. Faults are
`status` (for example 429 with `retry-after`), `error-after-chunks`, `truncate-after-chunks` (for
example before `response.completed`), and `error-event-after-chunks` (N events, then an `error`
event, or a `response.failed` event with `event: 'response.failed'`; streamed responses only, and
only before `response.completed`).

## Fixture-only routes

The OpenCode Go routes and the Claude, Codex, and Grok subscription-usage routes are fixture-only;
the earlier model routes above keep their behaviour. A request matching a recorded request's shape
gets that fixture's recorded response (same status, headers, and bytes). Everything else answers
one 400 not-emulated, written to the ledger and using up no fault or turn:
`{ error: { type: 'not_emulated', message } }`. That covers unknown routes and methods, missing or
invalid credentials, missing or other headers and query parameters, unknown models, non-streamed
modes, tools, reasoning, and extra fields. No provider status or error envelope is guessed.

Accepted request-shape latitude: any credential value; extra headers; key order; any string value
except `model`, `role`, `type`, and `phase`; any positive integer where the recording has a number
(the output-token limit); an `anthropic-beta` list that includes `oauth-2025-04-20`; any
non-empty Grok `x-userid` and `x-grok-client-version`; and `content-type` parameters. The query
string must match byte for byte (a bare `?` counts as no query), and Grok's `X-XAI-Token-Auth` (`xai-grok-cli`) and
`x-grok-client-mode` (`headless`) must be the SDK's fixed values. Test controls are the shared faults, scripted error turns, and, on usage
routes, a scripted `{ usage }` body or `subscriptionUsage` option with the recorded JSON shape;
fault and scripted-error statuses are 400-599 only. All
of these routes are `unverified` (synthetic fixtures).

The Anthropic, Codex, and Grok emulators also answer their provider's subscription-usage endpoint
on the same origin, with their own manifest, ledger, faults, turns, and coverage (`emulator.usage`,
control plane `/_emulate/usage/*`). The model route's manifest and coverage are unchanged; the
emulator types gain `usage` and a `subscriptionUsage` option.

| Emulator     | Route                            | Headers the fetcher sends (all required)                                              | Manifest                                   |
| ------------ | -------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------ |
| `/anthropic` | `GET /api/oauth/usage`           | Bearer, `anthropic-beta` listing `oauth-2025-04-20`                                   | `anthropicSubscriptionUsageEmulatorRoutes` |
| `/codex`     | `GET /backend-api/wham/usage`    | Bearer, `ChatGPT-Account-Id`                                                          | `codexSubscriptionUsageEmulatorRoutes`     |
| `/xai`       | `GET /v1/billing?format=credits` | Bearer, `X-XAI-Token-Auth`, `x-userid`, `x-grok-client-version`, `x-grok-client-mode` | `xAiGrokSubscriptionUsageEmulatorRoutes`   |

Each answers its recorded synthetic snapshot body (`*SubscriptionUsageDefault`) for a request with
those headers, `accept: application/json`, and exactly the recorded query; anything else is 400

fixed `X-XAI-Token-Auth: xai-grok-cli`.

## Email emulator

`@yolk-sdk/emulators/email`

| Export                                                                                          | Purpose                                                                                                   |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `makeEmailEmulator({ seed? })`                                                                  | `{ call, state, seed, ledger, reset, faults, coverage }`: a fixture-driven fake `EmailClient` backend     |
| `emailEmulatorRoutes`                                                                           | Route evidence manifest: one `PORT EmailClient.<method>` route per emulated method, linked to email cases |
| `emailEmulatorPort`, `emailEmulatorRouteMethod`                                                 | Helpers: `EmailClient` and `PORT`, the port name and pseudo method of the manifest routes                 |
| `EmailEmulatorSpecialUse`, `EmailEmulatorFolder`, `EmailEmulatorMessage`                        | Seed schemas: SPECIAL-USE attributes, folders, and messages                                               |
| `emailEmulatorDefaultSeed`, `EmailEmulatorSeed`                                                 | The synthetic practice mailbox the fixtures describe (folders, SPECIAL-USE attributes, messages)          |
| `EmailEmulatorFault`, `EmailEmulatorLedgerEntry`, `EmailEmulatorReply`, `EmailEmulatorCoverage` | Fault schema, ledger entry, reply, and coverage types                                                     |
| `emailEmulatorFixtures`                                                                         | The email conformance `PortFixture`s, copied as data                                                      |
| `EmailEmulatorInputInvalid`                                                                     | Thrown for an invalid seed or fault                                                                       |

Yolk never speaks IMAP, POP3, or SMTP, and neither does this emulator: no socket, TLS, MIME, or
mail library, no Node builtin, and no SDK import. `call(method, request)` takes one `EmailClient`
call as plain JSON (without credential fields) and answers `{ response }`, `{ failure }`, or
`{ notEmulated: { reason } }`. `emailClientLayerFromBackend(emulator)` from
`@yolk-sdk/connectors/email/conformance` turns it into the `EmailClient` layer.

Responses come only from the email conformance fixtures. The in-memory mailbox only selects the
first matching fixture consistent with it (preferring fixtures unused since the last reset) and
records what that fixture says happened (flags set, a draft appended, a message moved to the
destination id the fixture names, a message deleted, a Sent copy saved); it never invents an id,
flag, or response.

- Request-shape latitude: credential fields are never compared or recorded, and `connection.host`
  is not compared. Every other connection field (`protocol`, `port`, `security`) and everything
  else must equal a fixture request.

Anything else fails closed with a ledgered `notEmulated` answer, the port analogue of HTTP 400:
`unknown-method`, `invalid-request`, `no-matching-fixture`, or `state-conflict`. Faults
(`{ kind: 'failure', method, match?, count?, failure }`, `match` a deep subset of the request)
change no state. `reset()` restores the seed and clears the ledger, faults, and fixture use.

## R2 emulator

`@yolk-sdk/emulators/r2`

| Export                                                                              | Purpose                                                                                                    |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `makeR2Emulator({ seed? })`                                                         | `{ call, state, seed, ledger, reset, faults, coverage }`: a fixture-driven fake R2 port backend            |
| `r2EmulatorRoutes`                                                                  | Route evidence manifest: one `PORT <Port>.<method>` route per emulated method, linked to R2 cases          |
| `r2EmulatorPresignerPort`, `r2EmulatorObjectClientPort`, `r2EmulatorRouteMethod`    | Helpers: `R2Presigner`, `R2ObjectClient`, and `PORT`, the port names and pseudo method of the routes       |
| `R2EmulatorObject`, `R2EmulatorBucket`, `r2EmulatorDefaultSeed`, `R2EmulatorSeed`   | Seed schemas and the synthetic practice bucket the fixtures describe (the object the get fixtures read)    |
| `R2EmulatorFault`, `R2EmulatorLedgerEntry`, `R2EmulatorReply`, `R2EmulatorCoverage` | Fault schema, ledger entry, reply, and coverage types                                                      |
| `r2EmulatorFixtures`                                                                | The R2 conformance `PortFixture`s, copied as data                                                          |
| `r2EmulatorRedacted`, `r2EmulatorUnrecognised`                                      | The constant request (`<redacted>`) and port and method (`<unrecognised>`) of refusals that record nothing |
| `R2EmulatorInputInvalid`                                                            | Thrown for an invalid seed or fault                                                                        |

The R2 connector never talks to R2 itself, and neither does this emulator: no SigV4 signer, S3
client, socket, Node builtin, or SDK import. `call(port, method, request)` takes one `R2Presigner`
or `R2ObjectClient` call as plain JSON (without credential fields; bytes as base64) and answers
`{ response }`, `{ failure }`, or `{ notEmulated: { reason } }`. `r2PortsLayerFromBackend(emulator)`
from `@yolk-sdk/connectors/r2-storage/conformance` turns it into both port layers.

Responses come only from the R2 conformance fixtures. The in-memory bucket only selects the first
matching fixture consistent with it (preferring fixtures unused since the last reset) and records
what that fixture says happened (an object created absent-only or replaced under its current etag,
with the etag the fixture names); it never invents an etag, a byte, or a failure, and presigning
writes nothing. The connector cannot delete R2 objects, so objects the write cases create stay, and
running the write cases again on the same emulator fails them without writing.

Credentials never reach the ledger or any other output. Every credential field (`credential(s)`,
`accessKeyId`, `secretAccessKey`, `sessionToken`, `token`, and the other names the shared port scan
classifies as credentials) is dropped at any depth before anything is compared or recorded. Every
refusal is ledgered with constant text only (request `<redacted>`), uses no fault, and changes no
state; only a request equal to a fixture request is recorded, with every `bodyBase64` as
`<redacted>` plus its decoded length (`bodyBytes`). Every `bodyBase64` (put bytes) must be canonical
standard base64 of UTF-8 text (else `uncheckable-body`), and its decoded text is checked like the
rest of the request. A request is refused as `credential-in-request` when any key, string value,
number (as printed or as its digit string), or decoded body repeats a value found under a credential
field (any non-empty key, string, or number, with no minimum length), or holds, outside the exact
canonical synthetic placeholders, `X-Amz-Credential`, `X-Amz-Signature`, `X-Amz-Security-Token`, a
credential query parameter, or a token the shared scan flags (a bearer token, a common API-key
prefix, a JSON Web Token, a PEM private key). Each text is checked raw, within three rounds of
percent-decoding and three of escape-decoding (`\uXXXX`, `\xXX`, and numeric HTML references, as the
R2 conformance guard decodes), and through any depth of percent-encoding and JSON escaping, failing
closed past a work cap. A request with an own `__proto__` key at any depth is refused as
`invalid-request`, and one the checks cannot walk (cyclic, or nested too deeply) as
`uncheckable-request`: `call` never throws. The copied key, parameter, and token lists have one test
sample each, counted against the list and checked against the shared scan.

- Request-shape latitude: credential fields are never compared or recorded, and JSON key order is
  not compared. Everything else (the endpoint, bucket, key, content type, `maxBytes`,
  `expectedEtag`, the put `condition`, `bodyBase64`, and `maxUploadBytes`) must equal a fixture
  request exactly, so only the fixtures' `run-synthetic` run id is emulated. A `bodyBase64` must be
  canonical standard base64 of UTF-8 text (else `uncheckable-body`); it is compared as sent but
  recorded only as its decoded length. No object may have an own `__proto__` key (else
  `invalid-request`), and no key or value, the decoded body included, may carry a credential or
  repeat a dropped credential value of any length (else `credential-in-request`). Every refusal is
  ledgered with constant text only (request `<redacted>`).

Anything else fails closed with a ledgered `notEmulated` answer, the port analogue of HTTP 400, with
constant text only (request `<redacted>`): `unknown-method` and `uncheckable-request` (ledgered as
`<unrecognised>`), `invalid-request`, `uncheckable-body`, `credential-in-request`,
`no-matching-fixture`, or `state-conflict`; none uses a fault or changes the bucket. Faults
(`{ kind: 'failure', port, method, match?, count?, failure }`, `match` a deep subset of the request)
apply only to a call a fixture would answer and change no state. `reset()` restores the seed and
clears the ledger, faults, and fixture use.

It serves, on the seeded repository: `GET /repos/{owner}/{repo}/labels` (`per_page`, `page`, with
the paging fixture's `Link` header minted in its exact form; a listing that fits one page carries
none), `GET .../issues/{number}` (the recorded 404 for a number the repository has not reached),
`GET /search/issues` (the recorded 422 for a repository-scoped query longer than 256 characters),
`GET .../contents/{path}` (base64 folded every 60 characters), comment create, listing `since`
(`per_page=100`), and delete (204, then the recorded 404), issue label add and remove (the recorded
404 for a repository label not on the issue; removing an issue's last label is not emulated), and
issue create, rename, and close as completed. Every route needs exactly
`Authorization: Bearer <token>` (a recognisable bearer, as below; never compared against anything,

`X-GitHub-Api-Version: 2026-03-10` (`githubEmulatorApiVersion`), and answers only on the recorded
origin `https://api.github.com` (`githubEmulatorOrigin`): `fetch` reads the origin from the request
URL; behind a loopback rewrite, serve `fetchOn(githubEmulatorOrigin)`.

Every answer value comes from a fixture, or is a value the emulator mints: created issue numbers and
comment ids from counters that only advance (the default seed starts at the fixtures' issue `42` and
comment `9000000001`, a seed's counters lie above its seeded numbers, no seeded node id may use a
minted form at or above its counter, and a create past the last addressable number or id is
refused), the issue and comment ids derived from them in the fixtures' form, and timestamps from the
injectable `now` clock. Issue numbers below the counter that the state does not hold are implied,
never rendered. Label pages are page numbers, not cursors, and the label list never changes within a
seed (no route writes labels). A deleted comment's id and a closed issue stay in the state (GitHub
keeps both), so a write case ends at the seed except those and the counters.

It fails closed: only a request whose raw path is exactly an emulated route shape under that route's
method, with no `Authorization` header or exactly `Bearer <token>`, is recognised. Every other
request is ledgered and answered with constant text only (the path `/<unrecognised>`, a standard
method or `<other>`, no query or body, a constant reason). A recognised bearer must match the RFC
6750 `b64token` syntax exactly (`^[A-Za-z0-9\-._~+/]+=*$`, at least 8 characters), start with a
character in `[G-Zg-z\-._~+/]` other than `n`, `r`, `t`, `u`, and hold at least one character
outside the JSON-number alphabet `[0-9.eE+-]` (every GitHub and Google token form does: `ghp_…`,
`github_pat_…`, `gho_…`, `ya29.…`). So no number's text can contain it; it holds no escape
introducer (`%`, `\`, `"`), so no escape starts inside it; and its first character is no hex digit
and no JSON escape letter, so no stray `%`, `\`, or partial escape to its left can complete with it,
and its characters always decode in place. An `Authorization` header with any other value is
unrecognisable. A recognised request that repeats the bearer value in its raw path, any path
segment, the raw query or any query key or value, any recorded header, or its body is refused and
ledgered with constant text only: a standard method, the path `/<unrecognised>`, its route template,
an empty query, no headers or body, and a constant reason (`the query repeats the credential`, for
example). Each part is checked through the closure of two total, lexical transforms that cannot
fail: a tolerant percent-decode (every `%XX` below `%80` becomes its ASCII character; any other `%`
sequence is left as it is) and a tolerant JSON-unescape (in any text, whether or not it parses as
JSON, `\uXXXX` below `\u0080` and `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t` become their
characters). Starting from each part's raw text, either transform is applied to every text of the
previous step, deduplicated, until no new text appears (a fixpoint), and every text is checked for
the bearer as a substring; both transforms never lengthen a text and shorten it whenever they change
it. So any depth of percent-encoding or JSON escaping, in any order, is seen through in every part:
the raw path and each raw path segment, the raw query and each query key and value (already decoded
once by `URLSearchParams`), each recorded header, and the raw body. The work is capped at 64 rounds,
1024 distinct texts, or 8 Mi characters read by the transforms, whichever comes first; a part whose
closure hits a cap before its fixpoint counts as repeating the credential and is refused with the
same constant entry (uncertainty refuses, it never admits; so any part over 4 Mi characters is
always refused). Any other recognised request has the bearer value scrubbed from its ledgered fields
and every not-emulated reason (plan-time reasons included); its recorded query is keyed by recorded
key; a key recorded more than once lists its values in order (as a JSON array); and recorded headers
and query keys and values that start like JSON (`{`, `[`, `"`) are recorded parsed with
credential-named keys redacted at any depth, or as `<redacted>` when they do not parse, whatever the
header's declared format. Also, refusals never echo a request's own query or body keys; empty query
components are refused. It is **fixture-only**: anything else answers the ledgered 400 not-emulated
before anything is written and before any fault is chosen, for example other routes, issue creates
with labels or assignees, updates other than the two recorded ones (so the lifecycle case's
failure-path restore, which closes as `not_planned`, is not emulated), adding a label the repository
lacks (it would create it), a comment listing of more than one comment, rendering an issue that
holds comments (every fixture answers `comments: 0`), and writes to closed or implied issues. That
includes the open-issue listing of the read-only leftover lookup `findGithubConformanceLeftovers`,
which no fixture records: the lookup fails (`github_validation`, HTTP 400), and the repository
runner prints its lookup-failed WARN instead of leftover warnings.

- Request-shape latitude (`/github`, the only accepted deviations): any bearer value in the RFC 6750
  `b64token` syntax (`[A-Za-z0-9\-._~+/]+=*`) of at least 8 characters, starting with a character in
  `[G-Zg-z\-._~+/]` other than `n`, `r`, `t`, `u` (so a legacy all-hex token is refused), with at
  least one outside `[0-9.eE+-]`, that occurs nowhere else in the request (never compared against

  `X-GitHub-Api-Version` `2026-03-10`. Everything else (other keys and values, query parameters,

  query key, an explicit `page=1`, and a comment listing `per_page` other than 100) is not emulated.

Faults, the ledger (which records the `Accept` and `X-GitHub-Api-Version` headers), clock-free
recovery, and the control plane behave as in the Dropbox emulator; a 429 fault reaches the
connector as `github_rate_limited`. The `drills` option (seven booleans, one per GitHub case) is a

percent-encoding or JSON escaping, is ledgered as the constant credential-repeat entry, and any
other has it scrubbed from everything the ledger keeps. The bearer is never stored or ledgered:
through the shared wrapper's opt-in per-origin bearer digest, routes see only SHA-256 of the origin,
a space, and the key, which they compare with the digests of the seed's rejected keys for that
origin. The state holds only those digests, so a key a request carries as its bearer, a rejected one
included, never reaches the state, a snapshot, or `/_emulate/*` (a key sent as data elsewhere in a
request is ledgered like any other text), and no seed error quotes one: seed errors are constant
text, a category and a field path. This guarding covers the emulated provider API calls only:
`/_emulate/*` is the host's trusted control plane, and the seed and fault data a host gives it is
stored and returned as given.

- Request-shape latitude (`/linkedin-search`, the only accepted deviations): any bearer value in the
  RFC 6750 `b64token` syntax (`[A-Za-z0-9\-._~+/]+=*`) of at least 8 characters, starting with a
  character in `[G-Zg-z\-._~+/]` other than `n`, `r`, `t`, `u`, with at least one outside
  `[0-9.eE+-]`, that occurs nowhere else in the request (never stored or ledgered; only its
  per-origin digest is compared, with the digests of the keys the seed marks as rejected on that
  origin); extra request headers; JSON key order; `content-type` media-type parameters on the
  search; any percent-encoding of the `linkedin_profile_url` value that decodes once to the same
  profile URL; and, with a key the seed marks as rejected on the request's origin, any search
  `query` (one trimmed line of at most 500 characters) with any integer `numResults` from 1 to 100,
  and any profile URL of the form `https://<host>/in/<slug>`, each answered the origin's
  recorded 401. `Authorization` must be exactly `Bearer <token>` (that spelling, one space).
  Everything else (other body keys or values, a `category` other than `people`, a `type` other than
  `auto`, `contents` other than `{ "text": true }`, a search the state holds no answer for (another
  query, or a `numResults` no seeded search of that query records), a profile URL the state holds
  neither as a profile nor as absent, an email lookup of an absent profile, any query parameter on
  the search, other, missing, or repeated query parameters on a lookup, a query parameter name in
  any but its plain form (such as `%6cinkedin_profile_url`), empty query components such as a bare
  `?` or a stray `&`, a body on a lookup, another origin, and a bearer repeated anywhere in the
  request) is not emulated.

Seed with `seed: { searches?, profiles?, absentProfileUrls?, exaRejectedKeys?,
enrichLayerRejectedKeys? }` (each list replaces the default's). Faults, the ledger, recovery, and
the control plane behave as in the Dropbox emulator; the connector maps every non-2xx answer to its
action's failure code, so a 429 fault reaches it as `linkedin_search_failed` with status 429. The
`drills` option (seven booleans, one per LinkedIn search case) is a test-only knob that makes
exactly the matching conformance case fail.

## MCP emulator

`@yolk-sdk/emulators/mcp`

> **Experimental, Node only.** A stateful, fixture-only stand-in for the two synthetic MCP servers
> of the `@yolk-sdk/mcp/conformance` fixtures and for the Afloat MCP endpoint of the
> `@yolk-sdk/connectors/afloat/conformance` fixtures, built on the same `@emulators/core` runtime
> (loaded lazily when you create an emulator).

| Export                                       | Purpose                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `makeMcpEmulator(options?)`                  | `Promise` of `{ fetch, fetchOn, ledger, faults, reset, seed, snapshot, coverage, close }`   |
| `mcpEmulatorRoutes`                          | Route evidence manifest (12 rows: one `RPC <origin><path>#<method>` per method, plus `GET`) |
| `McpEmulatorSeed`                            | Typed seed schema (`modernListing`: `one-page` or `two-pages`; sessions are never seeded)   |
| `McpFault`                                   | A status fault (400-599) or `{ kind: 'truncate-after-chunks', chunks, match?, count? }`     |
| `McpEmulatorInputInvalid`                    | Invalid seed, fault, or option passed to the JS API                                         |
| `mcpEmulatorOrigin`                          | `https://mcp.example.test` (paths `/modern/mcp` and `/legacy/mcp`)                          |
| `mcpEmulatorReservedInvalidCredential`       | `yolk-conformance-invalid-credential-0000`, answered the recorded 401 on the era probe      |
| `mcpEmulatorFixtures`                        | The sixteen synthetic MCP fixtures, copied as data                                          |
| `mcpEmulatorAfloatOrigin`                    | `https://useafloat.com`: the origin of the `afloat` profile                                 |
| `mcpEmulatorAfloatPath`                      | `/mcp`: the path of the `afloat` profile (`https://useafloat.com/mcp`)                      |
| `mcpEmulatorAfloatKeyPrefix`                 | `afloat_`: the public key prefix; the remainder after it is the guarded secret              |
| `mcpEmulatorAfloatReservedInvalidCredential` | `afloat_yolkconformanceinvalid0000`, answered the recorded 401 on the Afloat era probe      |
| `mcpEmulatorAfloatFixtures`                  | The eight derived Afloat MCP fixtures, copied as data                                       |

Setup fragment (not a runnable example): it builds the emulator and the `HttpClient` layer to
provide to the code under test, which then targets `https://mcp.example.test/{modern,legacy}/mcp`
with a synthetic `Authorization: Bearer` header; `await mcp.close()` when done.

```ts
import { makeMcpEmulator, mcpEmulatorOrigin } from '@yolk-sdk/emulators/mcp'
import { EmulatorRoute, InProcessHttpClient } from '@yolk-sdk/emulators/router'

const mcp = await makeMcpEmulator()

const httpLayer = InProcessHttpClient.layer([EmulatorRoute.handler(mcpEmulatorOrigin, mcp.fetch)])
```

It serves profile `synthetic-modern` on `https://mcp.example.test/modern/mcp` (stateless
`2026-07-28`: `server/discover`, `tools/list`, and `tools/call`, JSON answers) and profile
`synthetic-legacy` on `https://mcp.example.test/legacy/mcp` (the era probe's recorded 400 fallback,
`initialize`, `notifications/initialized`, the standing `GET` answered 405, `tools/list`, and
`tools/call`, SSE answers), so `@yolk-sdk/mcp/client` and the MCP conformance cases run unchanged
against it. Every request needs `Authorization: Bearer <token>` (a recognisable bearer); behind a
loopback rewrite, serve `fetchOn(mcpEmulatorOrigin)`.

It also serves profile `afloat` on the provider endpoint `https://useafloat.com/mcp` (stateless
`2026-07-28`, JSON answers, no session, one listing page): the published nine-tool subset, the
`list-invoices` read call, its `VALIDATION_ERROR` tool error, the absent tool's JSON-RPC error (HTTP
200), and the 401, all from the derived Afloat fixtures (from the provider's source, not recorded
live; unverified). Answering the two derived `tools/call` fixtures, rather than only recorded calls,
is in scope by the owner's decision; they stay unverified until a live call is recorded. Its
credential rule: an Afloat key is `afloat_` and a remainder, and `a` is a hex digit, so on
`https://useafloat.com` a bearer is recognised only as `afloat_<remainder>` whose remainder is a
recognisable bearer, and the remainder is the guarded secret (repeat checks, output guard, digest),
never stored, ledgered, or echoed. Use a synthetic key such as `afloat_synthetic-key-0001`; a
real-format key whose remainder starts with a hex digit, a bearer without `afloat_` there, and an
`afloat_` key on the synthetic origin are not emulated. Behind a loopback rewrite, serve
`fetchOn(mcpEmulatorAfloatOrigin)`.

Every answer is a fixture's, byte for byte, with only the request id substituted at the recorded
place (the top-level `id` of a JSON answer, or of the SSE response event's payload; notification
events and SSE `id:` lines stay byte for byte), the minted session id in the recorded
`mcp-session-id` header, and the cursor of the current generation. `initialize` mints
`yolk-emu-session-<n>` from a counter that never resets (a form no seed holds); at most 256 sessions
are held, and another `initialize` is refused before any fault; `reset` and `seed` clear the
sessions. With `seed: { modernListing: 'two-pages' }`, `tools/list` answers the recorded paged
listing, whose first page issues `synthetic-cursor-0001` in the generation that first issues it and
`<cursor>.g<generation>` after a reset or seed; the second page answers only the cursor issued in
the current generation. The bearer is never stored, ledgered, or echoed: routes see only its digest,
compared only with the digest of the public reserved invalid credential (on the Afloat profile, of
the remainder of `afloat_yolkconformanceinvalid0000`) to answer its recorded 401.
Scope: the bearer is never copied from the request into a response, the state, or `/_emulate/*`; the
output guard also refuses a prepared fixture answer, minted session id, or cursor that happens to
contain it, but the emulator's other constants (state values such as `initializing`, wrapper headers
such as `x-emulator-evidence`) and host-configured control-plane data (a fault body) may
coincidentally equal a bearer and are not checked. A request that repeats the bearer in any header
name or value (not only the recorded headers), its path, query, or body, and a request whose
prepared answer or minted session id or cursor would repeat it (a bearer such as
`yolk-emu-session-1`, or `synthetic-mcp`, inside the recorded `yolk-synthetic-mcp`), is refused
before any fault is decided or anything is written. Every refusal, by shape or by state, is one 400
not-emulated ledgered with constant text only (`/<unrecognised>`, no query, headers, or body), and
it writes nothing and uses up no fault.

- Request-shape latitude (`/mcp`, the only accepted deviations): any bearer value in the RFC 6750
  `b64token` syntax (`[A-Za-z0-9\-._~+/]+=*`) of at least 8 characters, starting with a character in
  `[G-Zg-z\-._~+/]` other than `n`, `r`, `t`, `u`, with at least one outside `[0-9.eE+-]` (on the
  Afloat profile, `afloat_` followed by such a value: an Afloat key starts with the hex digit `a`,
  so its remainder after `afloat_` is the value checked, guarded, and digested), that occurs nowhere
  else in the request (any header name or value included) and in no answer or value the request
  would store (never stored or ledgered; only its digest is compared, with the digest of the public
  reserved invalid credential `yolk-conformance-invalid-credential-0000`, or on the Afloat profile
  of the remainder of `afloat_yolkconformanceinvalid0000`, each answering the recorded 401 on its
  profile's era probe); extra request headers, except `mcp-*` headers other than `mcp-method`,
  `mcp-name`, `mcp-protocol-version`, and `mcp-session-id`; a recorded header value sent as several
  headers that the HTTP layer joins into the recorded value; JSON key order; any JSON-RPC request id
  that is an integer from 0 to 2^53 - 1 or 1 to 64 printable ASCII characters where the recording
  has an id; any non-empty `name` and `version` (and no other key) in the `_meta` client info
  (`io.modelcontextprotocol/clientInfo`) of a modern request; a session id this emulator minted
  since the last reset or seed where the recording sends `mcp-session-id` (initializing for
  `notifications/initialized`, ready otherwise); and, with the seed's `two-pages` listing, the
  cursor this emulator issued in the current generation on the second page. `Authorization` must be
  exactly `Bearer <token>` (that spelling, one space). Everything else (another origin or path, any
  query, other HTTP methods such as `DELETE` or a `GET` on the modern or Afloat profile, a bearer
  without `afloat_` on the Afloat profile or with it on the synthetic profiles, an Afloat key whose
  remainder fails the rule above (such as one starting with a hex digit), JSON-RPC methods no
  fixture of the profile records such as `ping`, `resources/*`, or `prompts/*`, batches and
  client-sent responses, other members, a JSON body repeating a key (compared after unescaping), a
  `null`, negative, or fractional id, other params (other tools, arguments, protocol versions, or
  capabilities, extra client-info keys, a cursor on the Afloat listing, and a legacy `initialize`
  client info other than the recorded one), the MCP headers `accept`, `content-type`, `mcp-method`,
  `mcp-protocol-version`, `mcp-name`, and `last-event-id` other than the recorded values or present
  where none is recorded, any other `mcp-*` header (such as `mcp-param-*`), `mcp-session-id` missing
  where recorded or present where not, an unknown session or one in the wrong phase, a cursor not
  issued in the current generation, a reserved invalid credential on anything but its profile's era
  probe, a bearer repeated anywhere in the request, and a bearer an answer or a minted session id or
  cursor would repeat) is not emulated.

Not emulated: `DELETE`, `ping`, `resources/*`, `prompts/*`, `logging/*`, `completion/*`, `tasks/*`,
JSON-RPC batches and client-sent responses, a JSON body repeating a key, `mcp-*` headers no
recording carries (such as `mcp-param-*`), cursors the emulator did not issue, any other tool or
arguments, and a missing `Authorization`. Status and `truncate-after-chunks` faults apply only after
a request is admitted and planned, and a faulted request writes nothing: a truncation sends the
prepared answer cut short and never runs its commit (a truncated `initialize` mints no session; a
truncated first page issues no cursor). Truncating a legacy SSE answer after its first chunk ends
the stream before the response, so the client fails as an `McpError` at its timeout instead of
hanging. In `match`, `method` is the HTTP method and `route` one manifest row; a `route` naming no
row is rejected when the fault is added. `makeMcpEmulator` throws when a copied recording is not
canonical JSON. The ledger, recovery, and the control plane behave as in the Dropbox emulator. The
`drills` option (nine booleans, one per MCP case) is a test-only knob that makes exactly the
matching conformance case fail, on every profile whose answers it changes (the Afloat profile
included, except the legacy-only session knob).

## Node server

`@yolk-sdk/emulators/node`

| Export                                    | Purpose                                                                           |
| ----------------------------------------- | --------------------------------------------------------------------------------- |
| `serveFetchHandler(handler, { port? })`   | Scoped Effect resource `{ url, close }` serving on `127.0.0.1` (port `0` default) |

## Evidence

Emulated routes carry evidence: `verified` routes follow a live observation dated by `observedAt`;
`unverified` routes follow synthetic placeholders. Fetch-handler emulators tag every response from
an unverified route with `x-emulator-evidence: unverified`; the email and R2 emulators' plain-JSON
replies carry no header, so they record the evidence on each ledger entry instead. The Gateway route
is verified (`observedAt: '2026-09-30'`): the emulator follows the verified live Gateway recordings,
and the Yolk repository checks its response shapes against each recording. The OpenAI, Anthropic,
Codex, Grok, OpenCode Go, subscription-usage, email, R2, Fortnox, Microsoft, Dropbox, Notion,
Todoist, Telegram, GitHub, Google, LinkedIn search, and MCP routes are unverified, like the
synthetic fixtures they follow (the LinkedIn search routes and the MCP rows are reads, so none is
held in the pending list).
The email write routes are connector writes: until an owner-approved live run against a practice
mailbox, through a host `EmailClient` implementation, verifies them, the repository lists them in a
time-bounded allowlist (`scripts/emulator-evidence-pending.json`), and the evidence check reports
them as PENDING warnings until each entry's expiry date and fails again after it. The R2
`R2ObjectClient.put` route is held in the same list until a live run against a practice bucket,
through a host `R2ObjectClient` implementation, verifies it. The four Fortnox write routes, the
eleven Microsoft write routes, the five Dropbox write routes, the two Notion write routes, the five
Todoist write routes, the Telegram `sendMessage` route, the six GitHub write routes, and the fifteen
Google write routes are held in the same pending list until a live run against a Fortnox test
company, a Microsoft practice tenant, a Dropbox practice account, a Notion practice workspace, a
Todoist practice account, a practice bot, a GitHub practice repository, or a practice Google account
verifies them.
