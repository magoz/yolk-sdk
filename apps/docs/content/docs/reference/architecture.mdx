title: Architecture
description: Package boundaries and dependency direction.
---

Yolk packages are reusable mechanics. Apps provide product policy.

```txt
host app / runtime / UI
  -> @yolk-sdk/agent
  -> @yolk-sdk/mcp
  -> @yolk-sdk/knowledge
  -> @yolk-sdk/connectors
  -> @yolk-sdk/sandbox
  -> @yolk-sdk/vercel-workflows
  -> @yolk-sdk/harness

host tests / fixture scripts
  -> @yolk-sdk/conformance (experimental)
  -> @yolk-sdk/emulators (experimental)
```

Rules of thumb:

- packages expose contracts and helpers
- apps own auth, storage, prompts, providers, enabled tools, approvals, and UI
- use explicit subpaths
- keep provider/platform-specific code behind provider/platform subpaths

## Dependency direction

- `agent/protocol` is the shared wire vocabulary.
- `agent/loop` is stateless and provider/tool-service driven.
- `agent/runtime` adds generic session orchestration, not app persistence.
- `mcp` adapts MCP tools/results to agent protocol, but the loop stays MCP-agnostic.
- `knowledge`, `connectors`, and `sandbox` expose optional agent adapters behind explicit subpaths.
- `vercel-workflows` stays generic over serializable `unknown` payloads and does not import agent protocol.
- `harness` owns run lifecycle (claims, inbox, drains). It is not the agent loop and does not add a Workflow driver.
- `conformance` (experimental) depends only on `effect`: it records, replays, and fault-injects HTTP wire fixtures for tests, defines port fixtures for non-HTTP host ports (such as `EmailClient`), defines conformance cases, and runs them behind a safety policy; it never performs network I/O itself. Provider fixture and case modules such as `agent/providers/vercel/conformance` import it; runtime code does not.
- `emulators` (experimental) depends on `effect` and never imports other Yolk packages: emulators follow the recorded fixture wire shapes and name the conformance cases behind each route. `router` swaps `HttpClient` layers to reach them; `email` and `r2` are plain-JSON fake `EmailClient` and `R2Presigner` / `R2ObjectClient` backends that connectors bridge structurally (connectors never import emulators); only the `node`, `fortnox`, `microsoft`, `dropbox`, `notion`, `todoist`, `telegram`, `github`, `google`, and `linkedin-search` subpaths use Node builtins, and only `fortnox`, `microsoft`, `dropbox`, `notion`, `todoist`, `telegram`, `github`, `google`, and `linkedin-search` use the upstream `@emulators/core` runtime (pinned exactly).

Strict boundaries let the packages fit many hosts: Next.js, Workers, Durable Objects, Workflows, CLIs, and tests.
