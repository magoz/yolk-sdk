Yolk packages are canary-stage. APIs can change between canary releases.

## Version rule

Keep every public package on the same canary version:

```bash
pnpm add @yolk-sdk/agent@canary @yolk-sdk/mcp@canary @yolk-sdk/knowledge@canary @yolk-sdk/connectors@canary @yolk-sdk/sandbox@canary @yolk-sdk/vercel-workflows@canary @yolk-sdk/harness@canary @yolk-sdk/codemode@canary @yolk-sdk/extractors@canary
pnpm add -D @yolk-sdk/conformance@canary @yolk-sdk/emulators@canary
```

Add only the packages you use. `@yolk-sdk/harness` is available from `0.1.0-canary.77`.
`@yolk-sdk/codemode`, `@yolk-sdk/conformance`, and `@yolk-sdk/emulators` are available from
`0.1.0-canary.96`. `@yolk-sdk/extractors` is available from `0.1.0-canary.98`. Keep each of them
on the same lockstep version as the other public packages.

Check installed versions:

```bash
pnpm list '@yolk-sdk/*'
```

Do not mix versions unless a release note explicitly says it is safe.

## Recent canary migrations

### Canary.105: Gmail draft attachments

New, opt-in: `gmail.draft_compose`, `gmail.draft_update`, and `gmail.draft_reply` take an optional
`attachments` array of `{ filename, mimeType, contentBase64 }`. It is available from
`0.1.0-canary.105`. New exports from `@yolk-sdk/connectors/google`: `GmailDraftAttachment`,
`GmailDraftAttachments`, `GmailDraftAttachmentFilename`, `GmailDraftAttachmentMimeType`,
`GmailDraftAttachmentBase64`, and the limits `gmailDraftAttachmentsMaxItems` (10 files),
`gmailDraftAttachmentsMaxBytes` (25 MiB decoded in total), and `gmailDraftMessageMaxBytes` (35 MiB
of decoded MIME). See [Gmail draft attachments](./integrations/connectors#gmail-draft-attachments).

- A draft with attachments is written with one never-retried `multipart/related` upload to
  `https://gmail.googleapis.com/upload/gmail/v1/users/me/drafts?uploadType=multipart` (an update:
  `PUT .../drafts/{id}?uploadType=multipart`). Host HTTP adapters must forward that body exactly as
  UTF-8 and accept outgoing bodies up to about 35 MiB.
- A draft whose decoded MIME exceeds 35 MiB fails with `validation_failed` and
  `underlying: { outcome: 'rejected', retryable: false, reason: 'too_large' }` before anything is
  written.
- `gmail.draft_update` replaces the whole message: attachments not sent again are removed.
- Drafts without attachments (absent or empty) are written exactly as before, through the JSON
  endpoint.
- The Google emulator does not emulate the draft media upload: a draft with attachments answers its
  unrecognised 400. See [Google emulator](./api-reference/emulators#google-emulator).

### Canary.104: tool change previews

New, opt-in: approval-gated tools can describe what a call would change with
`makeTool({ approval, changePreview })`. It is available from `0.1.0-canary.104`. Pass
`toolSet.approvalPreviews` as `approvalPreviews` to your loop or runtime config and pending
`ToolApprovalRequest`s carry `preview` (a `ToolChangePreview`) or `previewError`; staged plan
reviews use the same hook. See [Preview the change](./agent/tools-hitl#preview-the-change).

Breaking changes for staged plan hosts:

- `staging.preview` is removed. Move it to the tool's `changePreview` and return a
  `ToolChangePreview` (`{ target, changes, ... }`) instead of arbitrary JSON.
- `ToolPlanPreview` `ok` entries carry `params` and either `preview: ToolChangePreview`,
  `previewError` (`{ cause, message }`), or neither (no hook), never both; narrow with
  `entry.status === 'ok' && entry.preview !== undefined`. A failing preview no longer turns the
  entry into `status: 'error'`, and oversized previews are truncated with markers instead of
  becoming error entries.
- `maxToolPlanPreviewBytes` is removed. Use `defaultToolChangePreviewMaxBytes` (16 KiB) and set
  the bound with `resolveTools(..., { changePreview: { maxBytes } })`.

Type changes that may need code updates even if you don't use staged plans:

- `ToolRegistryError` has a new cause, `change_preview_unsupported_policy` (a `changePreview` on a
  tool without `approval`). Update exhaustive matches.
- `ResolvedToolSet` has a new required field, `approvalPreviews`: update hand-built tool sets.

### Canary.103: staged tool plans

New, opt-in: code mode scripts can stage approval-gated tool calls with `stage(name, args)`, and a
person reviews the plan once through `makePlanReviewTool` before Yolk applies the selected calls.
It is available from `0.1.0-canary.103` and needs `makeTool({ approval, staging })` on the tools,
`resolveTools(..., { interactionHost, plans: { store } })`, and one plan review tool. Without them,
tool execution and code mode are unchanged. See
[Stage approval-gated writes](./integrations/code-mode#stage-approval-gated-writes) and
[Review a staged plan](./agent/tools-hitl#review-a-staged-plan).

Type changes that may need code updates even if you don't use staged plans:

- `prepareToolBatch` now returns `Effect<PreparedToolBatch, ToolError>`. It fails with `ToolError`
  `unavailable` only when host storage read by an interaction call validator is unavailable;
  nothing runs, so fail the step and retry it.
- Interaction call validators (`InteractionCallValidator`) and `validateAction` may fail with
  `InteractionHostError` for a storage outage, and `validateInteractionSubmission` then answers the
  new `InteractionAdmissionError` cause `unavailable`: treat it as retryable, not as invalid input.
- `ToolRegistryError` has three new causes: `staging_unsupported_policy`,
  `staging_validation_required`, and `plan_review_duplicate`. Update exhaustive matches.
- Raw interaction registrations' action `validate` (`InteractionActionHandler.validate`) now also
  receives the interaction `call` (`makeInteractionTool` action `validate` is unchanged), and interaction
  registrations accept an optional `unknownOutcome` hook. Existing handlers keep working.

If you adopt staged plans with a tool ledger, resolve the review step with the same ledger scope on
every redelivery, keep ledger entries as long as review receipts, and wire your per-call write
authorizer as `makePlanReviewTool({ beforeCall })`: applied calls bypass `beforeNestedCall` and
`ToolExecutor` decorators.

### Canary.102: Gmail draft bodies and thread body decoding

`gmail.draft_compose`, `gmail.draft_update`, and `gmail.draft_reply` keep their inputs and outputs,
plus a new optional `contentType: 'text' | 'html'` (`GmailDraftContentType`, `text` when omitted).
The draft MIME they write changes:

- A `text` body is now 7-bit `multipart/alternative` (a quoted-printable text/plain part and a
  derived text/html part) instead of one unencoded text/plain part, so Gmail web no longer
  hard-wraps it when a person sends the draft. An `html` body is one quoted-printable text/html
  part. Write each paragraph as one line. See
  [Gmail draft bodies](./integrations/connectors#gmail-draft-bodies).
- Tests, fakes, or recorded fixtures that compare a draft's exact `message.raw` need updating.
- `gmail.get_thread` no longer applies a part's `Content-Transfer-Encoding` to Gmail's already
  decoded `body.data`: quoted-printable text holding `=XX` (such as `?date=2026`) and base64-encoded
  parts now read back correctly. Remove any host workaround for those bodies.

`gmail.send_message` is unchanged.

### Canary.99: durable tool-call ledger

New, opt-in: `resolveTools(modules, context, { ledger: { store } })` runs ledgered tool calls at
most once per ledger key when a step re-executes. It is available from `0.1.0-canary.99`; without
`ledger`, tool execution is unchanged.

- Vercel Workflow tool-batch steps are at-least-once: the queue redelivers them after crashes and
  sometimes while a first execution is still running, even with `noWorkflowStepRetry`. Hosts that
  resolve tools inside a step should pass a durable store. See
  [Tool steps run at least once](./integrations/vercel-workflow#tool-steps-run-at-least-once) and
  [Ledger writes for re-executed steps](./agent/tools-hitl#ledger-writes-for-re-executed-steps).
- Custom executor or registration wrappers must forward `idempotencyKey` (like `nested`).
- A custom `isLedgered` should compose `defaultToolLedgerPolicy`, which also ledgers the built-in
  `subagent` tool.
- Code mode: `ToolResult.nestedCalls` is now sized from `limits.maxNestedCalls` (up to 4096)
  instead of a fixed 256, and `NestedToolCalls` gains optional per-status `counts`. Hosts with a
  higher limit store larger records in step output and audit storage.

### Canary.98: extractors package

New package: `@yolk-sdk/extractors`, bounded text extraction for PDF, DOCX, XLSX, PPTX, CSV, JSON,
Markdown, and plain-text files. Existing packages have no API changes, and `@yolk-sdk/knowledge`
does not depend on it.

- The root export is runtime-portable (`FileExtractor`, formats, limits, errors).
  `@yolk-sdk/extractors/node` is server-only and parses PDF and Office files in a worker thread
  per file; text formats are decoded in the calling thread.
  `@yolk-sdk/extractors/knowledge` exports `FileKnowledgeExtractorLayer`, which provides
  `KnowledgeExtractor` for [knowledge ingestion](./knowledge/ingestion-pipeline).
- SheetJS is an optional peer needed only for XLSX. Install it from
  `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, not the npm `xlsx`.
- In Next.js, keep the package unbundled:
  `serverExternalPackages: ['@yolk-sdk/extractors', 'xlsx']`.

### Canary.97: Effect 4.0.0

Canary.97 targets the stable `effect@4.0.0` release; canary.96 and earlier use
`effect@4.0.0-rc.115`. Upgrade matching Yolk packages and Effect together, and keep `effect` and the coordinated Effect runtime packages
(`@effect/platform-*`, `@effect/sql-*`, `@effect/opentelemetry`, `@effect/vitest`) on the same
version. Tooling such as `@effect/language-service` is versioned independently.

- Effect 4.0.0 removes the `effect/unstable/*` entrypoints. Drop the `unstable` segment:
  `effect/unstable/http` becomes `effect/http`, likewise `effect/socket`, `effect/sql`,
  `effect/process` and the other areas; `effect/unstable/httpapi` becomes `effect/http-api`. Import
  `Arbitrary` from `effect`.
- Check Effect-integrated dependencies for removed paths, not just your own code. For example,
  `drizzle-orm` `1.0.0-rc.5` declarations still import `effect/unstable/sql/SqlError`; with
  `skipLibCheck` that type silently becomes `any` and `catchTag('SqlError')` stops being checked.
  The Next example pins a declaration-only `pnpm patch` until drizzle ships a fix.
- `effect/Encoding` is split into `effect/encoding/Base64`, `Base64Url`, `Hex` and
  `EncodingError`. For example, `Encoding.encodeBase64` / `decodeBase64` become `Base64.encode` /
  `Base64.decode`.
- Host Effect code must also adopt upstream renames, such as `Schema.isBetweenLength` /
  `Schema.isBetweenProperties` and `Scope.close` accepting only a `Scope.Closeable`. Follow
  Effect's release notes for semantic changes in your own code; for example, `Array`, `Chunk`,
  `Effect` and `Record` `partition` now return successes before failures.
- Tool JSON Schemas: Effect 4.0.0 exports `Schema.isPattern` only when the regex flags are `u`,
  optionally with `d`, `g` or `y`, and silently omits other patterns (including `v`-mode regexes and
  `u` combined with `i`, `m` or `s`). Yolk's connector schemas now use `u`, so connector tool
  parameters keep their `pattern` hints with unchanged runtime validation; the Fortnox identifier
  pattern is advertised as the equivalent BMP-only class
  `^(?!\.{1,2}$)[\u0020-\u007e\u0080-\ud7ff\ue000-\uffff]+$`. Add `u` to `Schema.isPattern` in
  your own tool parameter schemas to keep their hints, and check that `u` does not change what
  your regex accepts (surrogate ranges and bounded quantifiers over astral characters can).
- String `Schema.isMinLength(n)` and the minimum of `Schema.isBetweenLength` (`n >= 2`) are
  advertised as `minLength: ceil(n / 2)` code points. Tool execution still validates against the
  original Effect Schema (through its JSON codec).

### Canary.97: tool arguments accept `null` for optional fields and reject unknown keys

`makeTool`, `makeInputTool`/`makeInteractionTool` call params, and the `question` tool now decode
model arguments with `Schema.toCodecJson(parameters)`, the codec that `ToolDef.parameters` already
advertised. `null` on `Schema.optional(X)` now decodes as omitted instead of failing validation;
`Schema.optional(Schema.NullOr(X))` still keeps `null`, and required fields still reject it.
`resolveTools` also drops `null` on properties advertised as optional without `null`
(`Schema.optionalKey(X)`, the subagent `model`/`reasoning_effort`, raw MCP schemas) before any
registration sees the call. Advertised schemas are unchanged. Non-finite numbers stay rejected.
Unknown keys are now rejected (`onExcessProperty: 'error'`) instead of silently stripped, matching
the `additionalProperties: false` that tool schemas already advertised; one error reports every
issue, naming each unknown key with the allowed ones (root `Schema.Struct({})` tools included),
including a `null` on another union member's field. Callers or fixtures that sent extra keys to a tool now get a model-visible validation
error, and app wrappers that only existed to reject unknown keys can be removed.
If you worked around this with `Schema.optional(Schema.NullOr(X))` plus `null`-to-`undefined`
mapping, `Schema.optional(X)` is now enough; app wrappers that re-decoded with the JSON codec can
use `makeTool` directly. Custom `invalidParamsMessage` callbacks can keep the unknown-key hint with
the new `withToolArgumentsErrorHint`. `omitNullOptionalToolArguments` is new on `@yolk-sdk/agent/tools` for
hosts that dispatch registrations without `resolveTools`.

Package-generated agent tools follow the same policy: connector tools from
`makeConnectorToolModule`, `knowledge_lookup`/`knowledge_manage`, and the `sandbox` tool reject
unknown keys instead of stripping them. For example, `outlook.list_messages` rejects the search-only
`query`, and Fortnox invoice update tools reject provider-managed fields such as `Booked` or `Sent`.
Connector `execute`/`invoke` and `executeTyped` are unchanged.

### Canary.97: code mode JSON arguments and structured tool outputs

- Code mode (`@yolk-sdk/codemode`, breaking): nested calls that end in an error result, a
  `beforeNestedCall` failure, or the `maxNestedCalls` limit now reject in the script with
  `<label>: <message>` instead of the bare message. The label is `tools.<identifier>`, or
  `tools["<name>"]` when an earlier tool already uses the identifier; cancelled and
  failed-unexpectedly rejections use the same label. `ToolResult.nestedCalls` keeps the raw
  message. Update scripts or checks that compare rejection messages.
- The pi executor now rejects, inside the script and before the call, arguments that JSON would
  silently change: `NaN`/`Infinity`, invalid `Date`s, `undefined`/function/symbol array items and
  holes, functions, symbols, bigints, cycles, `Map`/`Set`/`RegExp`/`Error`/class instances without
  `toJSON`, and arguments with more than 100000 values or 64 levels of nesting. A valid `Date` is
  sent as its ISO string. See [What scripts see](./integrations/code-mode#what-scripts-see).
- `CodeModeCatalogTool` gains a required `callLabel`; hosts that build catalog entries by hand must
  set it. Custom executors receive an optional `CodeModeExecutorTool.callLabel` (set by
  `makeCodeModeTool`) and should apply the same argument rules.
- Connector agent tools (`makeConnectorToolModule`) return the JSON encoding of the action
  `outputSchema` in both `structuredContent` and the text: `Chunk`s become arrays (instead of
  `{"_id":"Chunk","values":[...]}`), `DateTime`s ISO strings, class instances plain objects, and
  fields the output schema does not declare are dropped. A value that does not encode fails the call
  with an `execution` `ToolError`. Provider failures keep their text; their `structuredContent` is
  the JSON-encoded `ProviderFailure`, without a non-JSON `underlying`. Update UI or persistence that
  read the old shapes. Modules now carry the connector `description` (override it with the
  `description` option).
- `knowledge_lookup`/`knowledge_manage` declare `KnowledgeLookupOutput`/`KnowledgeManageOutput` and
  the `sandbox` tool declares `SandboxToolOutput` (with bounded `stdout`/`stderr`), returned as
  `structuredContent`; code mode scripts now receive these objects instead of the text. Text
  content is unchanged for the model.
- New: the experimental `@yolk-sdk/connectors/afloat/conformance` subpath and the `afloat` profile
  of `@yolk-sdk/emulators/mcp`; see [Afloat MCP conformance](./connectors/afloat).

### Canary.96: code mode, classifier models, conformance, and emulators

New packages: `@yolk-sdk/codemode` ([Add code mode](./integrations/code-mode)) and the
experimental, test-only `@yolk-sdk/conformance` and `@yolk-sdk/emulators`
([Test with emulators](./guides/testing-with-emulators)). `@yolk-sdk/agent`, `@yolk-sdk/connectors`,
and `@yolk-sdk/mcp` now depend on `@yolk-sdk/conformance` for their conformance subpaths; add it
yourself only if you import its runner or replay client.

The agent tool contract gains optional fields. Existing tools keep working unchanged:

- `ToolDef.outputSchema` (`makeTool({ output })`), `callableBy` (default `all`), and `discovery`.
- `nestedToolAccess` and `describe` on registrations, and `ToolResult.nestedCalls` and
  `ToolResult.usage`. Neither reaches the model; `toolResultMessageFromResult` drops both and the
  loop does not add `ToolResult.usage` to run usage.
- `ToolRegistryError` gains the `codemode_unsupported_tool` and `invalid_tool_exposure` causes. If
  you match its `cause` exhaustively, add both.
- If you send `ToolDef`s to providers yourself (outside `run`/`runModelTurn`), filter them with
  protocol `providerToolDefs` so codemode-only tools never reach providers.

`@yolk-sdk/agent/classification` and `@yolk-sdk/agent/providers/vercel/ai-gateway-classifier` add
classifier models over AI Gateway `POST /v1/evaluate`; see
[Classifier models](./agent/classifier-models). Connector and MCP tool adapters accept an
`exposure` option for code mode.

`gmail.draft_delete` now succeeds on Gmail's empty `204` response instead of failing to decode it.

### Canary.95: Gmail multipart send and Outlook draft attachments

`gmail.send_message` keeps its `{ raw, threadId? }` input and output and still sends exactly one
request. 7-bit MIME now goes to `upload/gmail/v1/users/me/messages/send?uploadType=multipart`
carrying the decoded MIME, so messages up to Gmail's 35 MiB cap are accepted; MIME with any byte
`>= 0x80` keeps the previous JSON `raw` request. Decoded MIME larger than 35 MiB now fails before
credentials or network with `validation_failed` and
`underlying: { outcome: 'rejected', retryable: false, reason: 'too_large' }`; nothing is sent.
Host HTTP adapters must preserve the `multipart/related` content type and the string body exactly.
Rejected/unknown HTTP classification is unchanged.

`addOutlookAttachment` is a new host-only helper (not an action) on `@yolk-sdk/connectors/microsoft`.
It requires `CredentialResolver` and `ConnectorHttpClient`: its Graph JSON POSTs
(`fileAttachment` under 3 MiB and `createUploadSession`) use your existing string HTTP adapter,
which must allow those POSTs and a success body of `maxMetadataBytes` plus the echoed base64 content,
and must not log, trace or persist those bodies (file content and the token-bearing `uploadUrl`).
Only files of 3 MiB or more need a `ConnectorBinaryWriteHttpClient` with the new optional
`uploadSession` method; hosts without that method, or without the port at all, fail those uploads
with `upload_session_required` before credentials or network. See
[Attach a file to an Outlook draft](./connectors/files#attach-a-file-to-an-outlook-draft).

### Canary.94: Fortnox customer write inputs

This is a breaking change to the Fortnox customer write actions that shipped in canary.90. When
upgrading `@yolk-sdk/connectors` from canary.93:

- `FortnoxCreateCustomerInput` and `FortnoxUpdateCustomerInput` no longer accept `Country` or
  `Phone`. Set `CountryCode` instead of `Country`, and `Phone1`/`Phone2` instead of `Phone`.
  `FortnoxCustomer` and `FortnoxSupplier` responses still include both fields.
- `fortnox.create_customer` and `fortnox.update_customer` reject unknown keys instead of dropping
  them, before any request is sent. Connector `execute`/`invoke` and `executeTyped` fail with
  `ConnectorError` cause `validation_failed`; generated agent tools reject the call arguments with a
  tool `validation` error. Remove `Country`, `Phone`, and any other unsupported keys from host-built
  inputs, and expect model tool calls that include them to fail validation.
- The `inputSchema` of both actions is now a closed wrapper, not the input class. Build typed
  inputs with `FortnoxCreateCustomerInput.make` / `FortnoxUpdateCustomerInput.make`. Decoding those
  classes directly still strips unknown keys.

Invoice write inputs were unchanged in canary.94: `execute` and generated agent tools still dropped
unknown keys (from canary.97, generated agent tools reject them), and
`executeTyped` trusts an existing invoice input class instance without rechecking its keys. See
[Fortnox write semantics](./connectors/fortnox#fortnox-write-semantics).

### Canary.91: OneDrive move/copy and email Sent copy

Upgrading `@yolk-sdk/connectors` adds three Microsoft tools when hosts pass the complete
`MicrosoftConnector` to `makeConnectorToolModule`: `onedrive.move_item` and `onedrive.copy_item`
(`write`), and `onedrive.get_copy_status` (`read`). Copy acceptance is not completion. Hosts that
allowlist actions or override access should review the new ids. Copy polling sends no credential to
the monitor URL and requires the host HTTP adapter to honor `redirect: 'manual'` and
`credentials: 'omit'`.

`email.send_message` now returns `sentCopy` even for legacy hosts: `unsupported` when saving was
requested but unavailable, or `skipped` when disabled. Saving is requested by default; set
`saveToSentItems: false` to skip it. A `failed` or unverified Sent copy after SMTP acceptance does
not mean the message was not sent; do not resend.

OpenAI-compatible Chat Completions lower tool-result images, readable text documents, and opted-in
PDFs to supplementary user content after the complete tool-result block. Other document formats and
audio still fail. Canonical history is unchanged.

### Canary.90: Fortnox customer and invoice writes

Upgrading `@yolk-sdk/connectors` adds four generated write tools when hosts pass the complete
`FortnoxConnector` to `makeConnectorToolModule`: `fortnox.create_customer`,
`fortnox.update_customer`, `fortnox.create_invoice`, and `fortnox.update_invoice`. Existing Fortnox
resource scopes already grant read and write access, so this does not require new OAuth consent.

Read-only hosts should restrict enabled actions explicitly and review any host access override:
blanket `access: 'read'` overrides declared action metadata, including these new `write` declarations.
Keep authorization and approval policy host-owned. Sending, booking, cancellation, and payment remain
outside the connector. See [Fortnox](./connectors/fortnox).

### Unreleased: reviewed email connector primitives

- `gmail.send_message` is a new **destructive** action for complete host-generated base64url MIME.
  It supports new messages and replies whose headers and `threadId` meet Google's threading
  requirements. Keep it out of model allowlists unless the host explicitly intends that exposure;
  a host-owned reviewed interaction is a separate opt-in. Success means submission, not delivery.
- Its `GoogleGmailSendOAuthCredentialSlot` uses the existing `google.oauth` binding and hints
  `gmail.send`. Existing `gmail.compose`, `gmail.modify`, or full-mail grants already permit sending;
  the action inspects OAuth scope metadata, then re-resolves through the selected operation slot
  so strict host resolvers enforce an existing sufficient grant without additional consent. Bearer
  credentials or missing scope metadata fall back to the send slot. Combined consent and existing
  draft APIs are unchanged.
- `outlook.update_draft` is a new **write** action for edited recipients, subject, and complete body.
  Omitted fields remain unchanged; empty arrays clear recipients. Unlike `create_reply_draft`, its
  body replaces the full content and does not prepend quoted history. Update followed by send is
  not atomic and does not provide compare-and-swap.
- `outlook.reply` is a new **destructive** action that sends the complete reviewed reply in one
  Graph `POST .../reply` with explicit `to`/`cc`/`bcc`, subject, and full body. Required recipient
  arrays (including empty ones) prevent provider recipient defaults; no `comment`, `from`, quoted
  history, or draft round-trip is involved. It reuses the existing send-slot mailbox permissions.
  Only HTTP 202 counts as accepted, meaning submission rather than delivery, with no message ID
  or exactly-once claim. Prefer it over update-then-send for reviewed replies.
- None of these three actions retries automatically. Gmail/Outlook unconfirmed-send metadata and
  Outlook's existing-draft recovery identity must be handled before another mutation. See
  [connector sending and editing](./integrations/connectors#submit-a-reviewed-gmail-message).

### Action-backed interaction opt-in

`makeInteractionTool` introduces distinct interaction request, response, event and client-input
variants. Update exhaustive HITL consumers before advertising these tools; never downgrade
`InteractionResponse` to data-only input or synthesize a result from `InteractionSubmitted`.
`makeInputTool`, questions and ordinary approvals retain their existing behavior.

Opt-in hosts must authenticate and atomically accept immutable submissions, provide the scoped
`InteractionHost`, load receipt snapshots before durable preflight, and forward the optional
`ToolExecutionOptions.interaction` reference through executor decorators. Raw HITL responses or
client transcript replay are not execution authority. No live example app opts in implicitly.
See [Authorize one action](./agent/tools-hitl#authorize-one-action).

### Canary.82: typed inputs and Gateway streaming

When upgrading from canary.81:

- Prefer `resolveTools` over hand-built toolsets. `ResolvedToolSet` now requires `inputs`; custom
  toolsets without typed input tools must supply an empty record (`inputs: {}`). Pass the resolved handlers as
  `inputs: toolSet.inputs` to loop/runtime configuration and `prepareToolBatch`; serializable
  definitions alone return unavailable instead of prompting.
- Update exhaustive protocol/client/React consumers for input requests, submitted/cancelled
  responses, lifecycle events, `InputResponseInput`, and `InputRequested`/`InputSubmitted`/`InputCancelled` tool states. Extend any
  host-owned closed persistence/wire schemas before storing or transporting these variants.
- Keep typed input pending until server acceptance. Invalid response data re-pends the same request
  for correction; transport failure is not an accepted result. Existing question behavior remains
  compatible. Input collection is not approval, and voice still supports approvals only.
- Full `run` streams now emit synthetic `ToolExecutionCompleted` events for rejected calls and
  resolved HITL, including while siblings remain pending. These do not execute tools; custom event
  consumers should preserve server results without completing the same call twice.
- Gateway keeps JSON completions by default. Factory `streaming: true` enables SSE deltas;
  `reasoningContent: true` independently preserves compatible reasoning output and assistant replay
  (spending input tokens). Neither option is enabled automatically.

See [typed input wiring](./agent/tools-hitl#collect-typed-input) and
[Gateway setup](./integrations/provider-setup#vercel-ai-gateway).

### Next canary: generic-email labels, flags, moves, and required headers

New `@yolk-sdk/connectors` actions `email.modify_labels`, `email.set_flag`, and `email.move`
work through optional `EmailClient` host methods; missing methods fail with a typed validation
error, so existing adapters keep working. `email.get_message` now requires `headers` and

### Next canary: chat-stream failure diagnostics

OpenAI-compatible chat streaming now rejects a 2xx response with an explicit non-SSE content type
before reading its body: `invalid_response` carries `providerCode: 'unexpected_content_type'`

`attachmentId` exists, fetch content through `gmail.get_attachment` with the parent message `id` as

from normalized thread output and cannot be fetched through that action.

## Upgrade checklist

1. Update all `@yolk-sdk/*` dependencies together.
2. Run typecheck and tests in your host app.
3. Search for changed subpath imports.
4. Re-run one agent loop with the fake provider.
5. Re-run one real provider smoke test.
6. Re-run one tool call, one HITL pause/resume, and one stream reconnect path if your app uses them.
7. Re-check connector credentials and OAuth scopes if connector packages changed.
8. Re-check sandbox lifecycle and Workflow terminal-event ordering if platform packages changed.

## What can break during canary

| Area         | Watch for                                                            |
| ------------ | -------------------------------------------------------------------- |
| Protocol     | event names, message fields, terminal state, tool/HITL payloads      |
| Loop/runtime | required Effect services, runtime request shapes, stream semantics   |
| Client/React | projection state, transport headers, resume helpers                  |
| Providers    | auth config, model capabilities, output limits, usage/error metadata |
| Tools        | registration metadata, access levels, approval semantics             |
| MCP          | remote/local config, result adaptation, HTTPS policy                 |
| Knowledge    | store contracts, search request shape, agent tool options            |
| Connectors   | action ids, input/output schemas, credential slots, config keys      |
| Sandbox      | lifecycle defaults, command result shape, provider adapter options   |
| Workflows    | callback contracts, terminal status, retry/default behavior          |
| Harness      | drain/token contracts, claim vs Inbox persistence, recovery budgets  |

## Safe migration pattern

Create one compatibility boundary in your app for each package area:

| Boundary              | Owns                                                      |
| --------------------- | --------------------------------------------------------- |
| Agent runtime adapter | provider layer, loop config, enabled tools, stream format |
| Tool catalog          | app-owned tools, connector tools, MCP tools, approvals    |
| Persistence adapter   | transcript/session event store and replay repair          |
| Credential adapter    | OAuth/API token resolution and refresh                    |
| UI adapter            | event projection, retry display, HITL controls            |

Then most package changes affect one adapter instead of the entire app.

## Stable import habit

Use public subpaths only:

```ts
import { runRuntime } from '@yolk-sdk/agent/runtime'
import { listRemoteMcpServerTools } from '@yolk-sdk/mcp/client'
import { GoogleConnector } from '@yolk-sdk/connectors/google'
```

Avoid root imports for feature APIs and never import from package `src/*` internals.

## Before filing an issue

Include:

- exact package versions
- Node version
- runtime environment
- relevant public subpath imports
- minimal reproduction using `FauxProvider` when possible
- terminal `AgentError` or typed provider/tool error metadata
