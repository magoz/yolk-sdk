---
title: Read and write Fortnox records
description: Read and write Fortnox records, prices, payments, offers, inbox, and settings with host-owned OAuth.
---

Use `@yolk-sdk/connectors/fortnox` to read Fortnox records directly or expose them as agent tools.
The connector exposes 91 actions: 42 `read`, 31 `write`, and 18 `destructive`. It sends GET, POST,
PUT, and DELETE requests to `https://api.fortnox.se/3`.

`destructive` actions cannot be undone through the Fortnox API: deletes, payment bookkeeping, offer
conversion, cancellation, emailing, and marking an offer sent. Gate them with host approval. Customer
invoices still have no send, book, cancel, or credit action; those remain host capabilities.

Host-only invoice and offer preview PDFs, archive and inbox downloads, inbox upload, and
supplier-file discovery are described in [Transfer connector files](./files#fortnox-and-notion).
Previews do not mark a document Sent.

## Connect a host credential

Install matching canary versions:

```bash
pnpm add @yolk-sdk/connectors@canary @yolk-sdk/agent@canary effect@4.0.0
```

Wiring fragment (host layers and Effect execution omitted):

```ts
import { makeCredentialBinding, makeIntegration } from '@yolk-sdk/connectors'
import { FortnoxConnector, FortnoxOAuthCredentialSlot } from '@yolk-sdk/connectors/fortnox'

const integration = makeIntegration({
  connectorId: 'fortnox',
  credentialBindings: [
    makeCredentialBinding({
      slotId: FortnoxOAuthCredentialSlot.id,
      credentialRef: 'host-fortnox-credential'
    })
  ]
})

const program = FortnoxConnector.invoke({
  integration,
  action: 'fortnox.list_invoices',
  input: { filter: 'unpaid', limit: 25 }
})
```

Provide `CredentialResolver` and `ConnectorHttpClient` Effect layers. The resolver must return an
`OAuthCredential` with `provider: 'fortnox'` and a current `accessToken`. Resolve or refresh the
credential before returning it; the connector does not refresh tokens or enforce their expiry.
Integration config needs no keys and must not contain tokens or client secrets.

The HTTP adapter must preserve `Authorization: Bearer …` and `Accept: application/json`.
When a request carries a JSON body it must also preserve `Content-Type: application/json` and the
body. Lifecycle PUTs (`bookkeep`, `createorder`, `createinvoice`, `cancel`, `externalprint`) and all
DELETEs are body-less. `fortnox.email_offer` is a side-effecting GET: never retry it or follow its
redirects.
Hosts own network policy, response-size limits, redirect safety, and avoiding credential/body logs.

## Choose consent scopes

**Fortnox has no read-only OAuth scopes.** Each resource scope grants read and write access at the
provider. Explain this distinction during consent and retain host authorization checks. Fortnox also
requires a company license for each resource. Action access metadata (`read`, `write`,
`destructive`) is what hosts gate on; it does not narrow the token.

All slots bind through `fortnox.oauth`:

| Slot                                           | Required scope       | Developer Portal name | Fortnox license               |
| ---------------------------------------------- | -------------------- | --------------------- | ----------------------------- |
| `FortnoxCompanyInformationOAuthCredentialSlot` | `companyinformation` | Företagsinformation   | Any                           |
| `FortnoxCustomerOAuthCredentialSlot`           | `customer`           | Kund                  | Kundfaktura or Order          |
| `FortnoxInvoiceOAuthCredentialSlot`            | `invoice`            | Faktura               | Order or Kundfaktura          |
| `FortnoxSupplierOAuthCredentialSlot`           | `supplier`           | Leverantör            | Bokföring                     |
| `FortnoxSupplierInvoiceOAuthCredentialSlot`    | `supplierinvoice`    | Leverantörsfaktura    | Bokföring                     |
| `FortnoxConnectFileOAuthCredentialSlot`        | `connectfile`        | Koppla filer          | Bokföring, Anläggning, Arkiv  |
| `FortnoxArchiveOAuthCredentialSlot`            | `archive`            | Arkivplats            | Any                           |
| `FortnoxArticleOAuthCredentialSlot`            | `article`            | Artikel               | Order or Kundfaktura          |
| `FortnoxPriceOAuthCredentialSlot`              | `price`              | Pris                  | Order or Kundfaktura          |
| `FortnoxCostCenterOAuthCredentialSlot`         | `costcenter`         | Kostnadsställe        | Bokföring, Order, Kundfaktura |
| `FortnoxPaymentOAuthCredentialSlot`            | `payment`            | Betalningar           | Bokföring, Order, Kundfaktura |
| `FortnoxOfferOAuthCredentialSlot`              | `offer`              | Offert                | Order                         |
| `FortnoxPrintOAuthCredentialSlot`              | `print`              | Utskrift              | Order or Kundfaktura          |
| `FortnoxInboxOAuthCredentialSlot`              | `inbox`              | Inbox                 | Any                           |
| `FortnoxSettingsOAuthCredentialSlot`           | `settings`           | Inställningar         | Any                           |
| `FortnoxProfileOAuthCredentialSlot`            | `profile`            | Profil                | Any                           |

`print` covers only print templates; printing, previewing, or emailing a document uses the
document's own scope (`invoice`, `offer`). Fortnox also lists Company Logo (Företagslogga) and a
sales API (Försäljnings-API) as Developer Portal scopes, but documents no endpoints for them, so the
connector has no actions for either.

`FortnoxOAuthCredentialSlot` is the generic binding without scope hints.
`FortnoxCombinedOAuthCredentialSlot` declares the original five record scopes only (not the file,
article, price, cost-center, payment, offer, print, inbox, settings, or profile scopes); use it only
when the host needs exactly those resources. Action-scoped slots supply consent hints to the
resolver, not a token store or permission checker.

Host OAuth implementation:

- Use `fortnoxOAuthAuthorizeUrl` (`https://apps.fortnox.se/oauth-v1/auth`) with `response_type=code`,
  a CSRF-protected `state`, the registered redirect URI, and space-delimited scopes. Request
  `access_type=offline` when refresh is needed. Service-account selection is host policy.
- Exchange the code at `fortnoxOAuthTokenUrl` (`https://apps.fortnox.se/oauth-v1/token`) with HTTP
  Basic client authentication and a form-urlencoded body.
- Store and refresh tokens server-side. Fortnox rotates refresh tokens; serialize refreshes and
  persist the replacement safely. Hosts own revocation, reauthorization, and credential identity.

`fortnox.list_supplier_invoice_files` takes `{ givenNumber, page?, limit? }`, returns
`{ files, pagination }`, and uses `connectfile` consent. Its filter is internal GivenNumber, not
supplier InvoiceNumber. The new file scopes grant both reads and writes like other Fortnox scopes.

### Master data, payments, offers, inbox, settings, and profile

Get and delete inputs use camelCase identifiers (`{ articleNumber }`, `{ code }`,
`{ paymentNumber }`, `{ documentNumber }`, `{ itemId }`, `{ labelId }`). Create and update inputs
use Fortnox field spelling, carry the identifier, and bind it into the URL instead of the body.
Deletes return `{ <identifier>, deleted: true }` without decoding Fortnox's empty answer.

All action IDs carry the `fortnox.` prefix. Notes per resource:

- **Articles.** `ArticleNumber` is assigned by Fortnox when omitted and cannot change later.
  `SalesPrice` is read-only (it is the price in the default price list); set prices through the
  price actions. Update changes only the sent fields. Delete is permanent.
- **Prices.** A price is identified by price list, article number, and `FromQuantity` (0 for the
  base price); all three form its URL path. The default price list is usually `A`. Fortnox
  documents no price-list delete. `list_prices` lists one article's prices in one price list.
- **Cost centers.** `Code` is writable only on create. Prefer `Active: false` over deleting.
- **Payments.** Created payments are normally unbooked; check `Booked` in the response.
  `AmountCurrency` is required when the invoice currency is not SEK. A supplier invoice payment's
  `InvoiceNumber` is the supplier invoice **GivenNumber** (`FortnoxGivenNumber`), not the supplier's
  own invoice number. Bookkeeping posts a voucher and has no API undo.
- **Offers.** Row updates follow the invoice rules below (rows replace the list; `RowId` matches
  rows and is regenerated). `create_order_from_offer` needs the Order license;
  `create_invoice_from_offer` creates a customer invoice. Both return the offer number and the new
  order or invoice number (null if Fortnox does not report it); do not retry an ambiguous
  conversion, read the offer instead. `email_offer` sends to the offer's stored
  `EmailInformation` recipient through a GET (the only method Fortnox offers); host HTTP adapters
  must not retry it or follow redirects. `mark_offer_sent` sets `Sent` without producing a document. There
  is no print action: `/print` returns bytes and marks the offer Sent; use the host preview plus
  `mark_offer_sent`.
- **Inbox.** Fortnox has nine static root folders (`inbox_s` supplier invoices, `inbox_v`
  vouchers, `inbox_kf` customer invoices, and others). `get_inbox_folder` returns folder metadata;
  a file id returns bytes, so use the host download helper. Deleting a subfolder deletes everything
  in it; `delete_inbox_item` refuses `root` and the static folders.
- **Settings.** Company settings and the locked period are read-only through the API.
  `update_predefined_account` changes the account Fortnox books with by default. Deleting a label
  removes it from every document that uses it. Labels and predefined accounts are not paginated.
- **Not covered.** Article URL connections, price-list deletion, `?path=` inbox addressing,
  Email Senders, Predefined Voucher Series, Company Logo, and the sales API (scope or endpoint not
  confirmed).

These additions follow Fortnox's current API reference and archived resource pages; none has been
observed against a live company yet. The
[Fortnox emulator](../api-reference/emulators#fortnox-emulator) serves their read endpoints
(including the offer preview and inbox file bytes) with unverified, synthetic shapes named after the
fields these actions read; their writes, and side-effecting reads such as `email_offer`, are not
emulated and fail closed with a 404.

Create customer inputs require `Name`; Fortnox assigns `CustomerNumber`. Create invoice inputs
require `CustomerNumber`; Fortnox assigns `DocumentNumber`. Update inputs carry the provider
identifier (`CustomerNumber` or `DocumentNumber`) and omit it from the request body because it is
bound into the URL. Invoice write inputs use `InvoiceRows` as JSON arrays; returned invoice rows are
runtime `Chunk` values. Writes do not send or book invoices and are subject to host authorization.
The connector forwards accepted write fields unchanged; it does not inject defaults or rewrite
values. Invoice write inputs are not closed: when `execute` decodes input, unknown or
provider-managed keys (such as `Booked` or `VoucherNumber`) are dropped before the request. Agent
tools from `makeConnectorToolModule` reject those keys instead, with a model-visible validation
error, so a model never believes it booked or sent an invoice.
`executeTyped` trusts an existing invoice input class instance and does not re-check its keys.

### Fortnox write semantics

These notes describe Fortnox behavior and connector validation. The action descriptions that agents
see repeat the Fortnox behavior:

- **Customer contact fields.** Customer write inputs omit `Country` and `Phone`. Fortnox derives the
  read-only `Country` from `CountryCode`, and the Customer resource has no `Phone` field; use
  `Phone1`/`Phone2`. `Phone` appears only in list rows. The `fortnox.create_customer` and
  `fortnox.update_customer` action inputs are closed: `Country`, `Phone`, or any other unknown key
  fails input validation before a request is sent, rather than being stripped. Decoding the
  exported input classes directly uses default Effect parsing, which strips unknown keys. `FortnoxCustomer` and `FortnoxSupplier` responses still include
  `Country` and `Phone`.
- **Customer updates.** Only provided fields change; omitted fields keep their stored value. An
  empty string does not clear a stored value.
- **Invoice rows on update.** Sending `InvoiceRows` replaces the row list: existing rows that are
  not sent are deleted. If no sent row has `RowId`, rows are matched to existing rows by position,
  and fields omitted on a matched row keep their previous value (for example
  `Discount`/`DiscountType`). Send every row that should remain with all pricing fields, including
  `Discount: 0` when no discount is intended. If any sent row has `RowId`, rows with a matching
  `RowId` are updated and rows without one are added. Fortnox
  regenerates RowIds on every update, so read the invoice again before reusing them.
- **Referenced records.** `CostCenter`, `Project`, `ArticleNumber`, `AccountNumber`, and a non-SEK
  `Currency` must already exist in the Fortnox company.

Pass identifier strings returned by the provider, preserving leading zeros. `givenNumber` is the
numeric-string **GivenNumber**, not the supplier's `InvoiceNumber`. Identifiers are validated and
encoded as path segments; returned provider URLs are never followed. Typed file-discovery inputs
and outputs use `FortnoxGivenNumber`; `downloadFortnoxInvoicePreview` takes
`FortnoxDocumentNumber`. Decode raw provider/request values with those exported schemas, or use
`.make` for trusted constants. Dynamic `FortnoxConnector.invoke` still accepts plain JSON and
decodes it at runtime.

Resource fields retain Fortnox spelling, including `CustomerNumber`, `DocumentNumber`,
`GivenNumber`, `CompanyName`, and `OrganisationNumber` (company information uses
`OrganizationNumber`). These are bounded read models: unknown provider fields are omitted, not a
lossless accounting export. The exported schemas define the selected contact, status, reference,
amount, and invoice-row fields. Supplier bank details and unmodeled provider fields are not exposed.
List responses can contain fewer fields than detail responses; optional omission does not mean zero
or false. Use a get action to retrieve available rows.

Collections are runtime Effect `Chunk` values, including `InvoiceRows` and `SupplierInvoiceRows`.
Customer-invoice `Total` and `Balance` remain numbers; supplier-invoice `Total` and `Balance` remain
strings, preserving their supplied decimal representation. Row amounts retain their provider types
and nullable `Total`/`CostCenter` values. The connector performs no monetary arithmetic or rounding.

### Pagination and search

Every list action fetches exactly one page. Record-list inputs support `page` (integer, at least 1), `limit`
(integer, 1–500), and `lastModified` (provider timestamp string). Omitted values use Fortnox defaults
(page 1, limit 100). Output `pagination` contains `currentPage`, `totalPages`, `totalResources`, and
optional `nextPage`. Continue with `page: nextPage`, repeating the same limit and selection fields;
stop when `nextPage` is absent. Missing or malformed pagination metadata is an error, not an assumed
final page. The connector does not auto-paginate or promise snapshot consistency while records change.

Fortnox's OpenAPI invoice-list wrapper omits the generic `MetaInformation` field that this connector
expects. Invoice pagination needs confirmation with a sanitized response from your account before
production use; the connector does not infer completion when metadata is missing.

For resource-specific searches, supply one `search: { field, value }` pair:

| Resource                  | Supported `search.field` values                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Customers                 | `customernumber`, `name`, `organisationnumber`, `email`, `city`, `phone`                                                  |
| Suppliers                 | `suppliernumber`, `name`, `organisationnumber`, `email`, `city`, `phone`                                                  |
| Invoices                  | `customernumber`, `customername`, `documentnumber`, `ocr`                                                                 |
| Supplier invoices         | `suppliernumber`, `suppliername`, `invoicenumber`, `serialnumber`, `ocr`                                                  |
| Articles                  | `articlenumber`, `description`, `ean`, `suppliernumber`, `manufacturer`, `manufacturerarticlenumber`                      |
| Price lists               | `code`, `comments`                                                                                                        |
| Invoice payments          | `invoicenumber` (customer invoice DocumentNumber)                                                                         |
| Supplier invoice payments | `invoicenumber` (supplier invoice GivenNumber)                                                                            |
| Offers                    | `customername`, `customernumber`, `documentnumber`, `offerdate`, `ourreference`, `yourreference`, `costcenter`, `project` |

Fortnox supports only one resource-specific search field at a time; matching follows provider
semantics, not guaranteed exact equality. Combine it with global `lastModified`, and for invoice
lists, `fromDate`/`toDate` date strings. Dates are forwarded unchanged without timezone conversion.

Customers and articles additionally accept `filter: 'active' | 'inactive'`. Offers accept
`cancelled`, `expired`, `completed`, `notcompleted`, `ordercreated`, or `ordernotcreated`, plus
`fromDate`/`toDate`. Settings registers (modes of payment, terms, ways of delivery, units) take
`page` and `limit` only. Print templates, labels, and predefined accounts are not paginated. Both invoice lists accept `cancelled`,
`fullypaid`, `unpaid`, `unpaidoverdue`, or `unbooked`; supplier invoices also accept `pendingpayment`
and `authorizepending`. Supplier lists do not expose a status filter. Unsupported sort/offset or
arbitrary query parameters are not part of this connector.

Fortnox's API docs do not state how payment-status filters treat unbooked invoices. On a demo
tenant, `unpaid`, `unpaidoverdue`, and `fullypaid` did not return unbooked customer invoices; use
`filter: 'unbooked'` for those. An empty payment-status result does not prove nothing is outstanding.

## Handle failures and rate limits

Non-2xx responses return `ActionResult.failure`, including `fortnox_unauthorized` (401),
`fortnox_forbidden` (403), `fortnox_not_found` (404), `fortnox_rate_limited` (429), and
`fortnox_request_failed` for other statuses. Fortnox `ErrorInformation` fields accept both documented casings (`message`/`code` and
`Message`/`Code`). The message is retained; the code, when present, is available as
`error.underlying.providerCode`. Raw error bodies are not
returned. Missing/invalid credentials, input validation, malformed success bodies, and transport
errors stay in the typed Effect error channel.

Hosts can classify failures from `underlying.providerCode` using Fortnox's
[documented error codes](https://www.fortnox.se/developer/guides-and-good-to-know/errors). The
connector does not map these codes itself. Codes relevant to these actions include:

| Code(s)                         | Fortnox meaning                                           |
| ------------------------------- | --------------------------------------------------------- |
| `2000310`, `2000311`            | Access token (or client secret) missing or incorrect      |
| `2001101`, `2001103`, `2000663` | No license for the scope or API, or no access to scope    |
| `2001399`                       | Invalid field name                                        |
| `2000106`, `2000108`, `2000134` | Value must be alphanumeric, numeric, or boolean           |
| `2000359`, `2000588`            | Value contains invalid characters; invalid parameter      |
| `2001304`                       | Account not found                                         |
| `2001302`, `2000428`            | Article not found                                         |
| `2000204`, `2000433`            | Customer not found                                        |
| `2000637`                       | Customer number already used or reserved by a deleted one |

Fortnox documents 25 requests per 5 seconds per access token. Hosts own throttling and retry policy;
the connector never retries automatically. A valid delta-seconds `Retry-After` header is exposed as
`retryAfterMs`; HTTP-date headers are not interpreted. A 403 may mean missing consent, license, or
permissions rather than an expired token.

## Expose agent tools

Wiring fragment; `HostConnectorLayer` is the host-provided layer described above:

```ts
import { makeConnectorToolModule } from '@yolk-sdk/connectors/agent'

const tools = makeConnectorToolModule(FortnoxConnector, {
  integration,
  layer: HostConnectorLayer
})
```

The adapter inherits each action's declared access metadata (`read`, `write`, or `destructive`);
explicit host access overrides still win. Require manual approval for `destructive` tools such as
`fortnox.email_offer` and `fortnox.bookkeep_invoice_payment`, or exclude them from the module.
Customer-invoice sending and booking are still not connector actions, so any host-owned outbound
action must keep its own approval gate.
See [Add connector tools](../integrations/connector-tool) for tool execution and authorization.

The cases need `FortnoxConformanceConfig` seed identities (never hard-coded account data) and the
connector ports; `@yolk-sdk/connectors/conformance` bridges an Effect `HttpClient` to those ports for
tests only. A missing seed fails the case with a `precondition:` mismatch before any request.

What the write cases guarantee differs:

- **Row and customer cases** read the original state first, always restore it afterwards (also after
  a failed assertion or an interruption), and verify the restore by reading back. The row case
  compares every written row field plus `VATCode`, and the invoice `Total`, `TotalVAT`, `Net`, and
  `Gross`, exactly. A failed restore fails the case with `FortnoxConformanceRestoreFailed`, which
  summarizes the original failure when the claim failed; check the account and restore it by hand
  if it still differs. A failed restore raised while the case is being interrupted is also handed,
  with its full message, to `ConformanceCleanupReporter` from `@yolk-sdk/connectors/conformance`
  (default: `Effect.logWarning`), since the interruption may replace it. The repository runner
  (`pnpm conformance:fortnox`) turns a first Ctrl-C into an interruption and prints these reports
  on stderr as `WARN` lines. Like the shared runners, it prints every line of a live run (the
  report, `WARN` lines, the run's own failure, staging output) with the live access token redacted,
  since Fortnox can echo it into a field a case reports. The rejection case and the email send do
  not report.
- **The rejection case** does not restore anything. It first confirms that the customer is absent: a
  404, or another 4xx with a customer-not-found `ErrorInformation` code (`2000204`, `2000433`).
  401, 403, and every other failure abort before the write. If Fortnox unexpectedly accepted the
  create, the case fails and names the invoice to cancel by hand.
- **The email case** reads the invoice first and aborts unless `EmailInformation.EmailAddressTo`
  equals the `emailRecipient` seed exactly and no CC or BCC address is set. It sends with
  `redirect: 'manual'` and `credentials: 'omit'`, and fails on any 3xx rather than treating it as
  sent. It is never automated.

The shipped fixtures are synthetic (`evidence: 'unverified'`). See
[Conformance APIs](../api-reference/conformance#connector-conformance) for the bridges.

For offline tests, the experimental [Fortnox emulator](../api-reference/emulators#fortnox-emulator)
(`@yolk-sdk/emulators/fortnox`) is a stateful stand-in that passes these cases and reproduces their
quirks.
