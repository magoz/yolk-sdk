# Connectors

`@yolk-sdk/connectors` defines Effect-native primitives for reusable external-system connectors.

## Boundaries

- No DB, encryption, token storage, refresh persistence, app auth, routes, UI, or product permissions.
- No user/team/org/workspace/project concepts; hosts own identity and lifecycle.
- No Promise facade; public APIs are Effect-native only.
- Do not repackage Effect HTTP/runtime adapters; expose ports and let hosts wire Effect layers.
- Raw secrets may flow through host-provided Effect services at invocation time, but integrations store only opaque credential refs.
- Provider modules may define vendor mechanics and schemas, not host policy.

## Public model

| Export area       | Purpose                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `connector`       | connector definition and action dispatch                                                                                       |
| `agent`           | optional adapter from connector actions to `@yolk-sdk/agent/tools` modules                                                     |

| `action`          | typed action definitions over Effect Schema                                                                                    |
| `config`          | required/optional string config helpers for integration config                                                                 |
| `credential`      | slots, bindings, host resolver service, runtime credential values                                                              |
| `http`            | host-provided HTTP request/response port; not a connector                                                                      |
| `result`          | value-level success/failure results for expected upstream failures                                                             |
| `error`           | typed package/runtime failures                                                                                                 |
| `afloat`          | Afloat remote MCP auth data action, API-key slot, endpoint, and protocol version                                               |
| `dropbox`         | Dropbox metadata/file-management actions, OAuth slot constants, and host-only download plus create/update                      |

| `figma`           | Figma remote MCP auth data action and OAuth constants                                                                          |
| `fortnox`         | Company/customer/invoice/supplier actions, including customer/invoice create/update, plus resource-scoped OAuth slot constants |

| `google`          | Gmail, Calendar, and Drive actions plus shared Google OAuth slot constants                                                     |

## Design rules

- Connector = reusable implementation; Integration = host-owned config that makes a connector invokable.
- Actions declare typed input/output schemas and optional `read`/`write`/`destructive` access metadata; action execution stays Effect-native. Agent adapter host overrides win, otherwise declared access is used.
- `defineAction` returns `TypedConnectorAction`: `execute`/connector `invoke` remain dynamic wire boundaries; `executeTyped` accepts decoded input and validates with `Schema.toType` without replaying encoding transforms. Implementations still validate external provider/host output; the generic executor does not automatically decode `outputSchema`.
- Reuse Fortnox's canonical identity schemas for file discovery and preview. Discovery `givenNumber` is `FortnoxGivenNumber`, not supplier `InvoiceNumber`; preview uses `FortnoxDocumentNumber` with complete-segment URL encoding, not the archive-specific `OpaqueId` restriction.
- `http.ts` is infrastructure: connectors emit typed requests; hosts provide `ConnectorHttpClient` and preserve headers/body content type. This complete-string port cannot enforce pre-buffer download limits: hosts cap actual streamed bytes, allow bounded base64/JSON expansion only for successful trusted attachment requests, and keep ordinary/error bounds separate. Decoded limits and canonical base64 checks remain host policy; provider sizes are not byte-length proof.
- `binary-http.ts` is a separate optional host-only port, not an adapter or action. Hosts enforce streamed actual-byte/error-body budgets, timeouts/cancellation, connection-time public DNS/IP policy, TLS, and no automatic redirects/cookie jars/ambient auth. SDK syntax screens and post-buffer checks do not prove network enforcement. See README host integration contract.
- Hosts provide credential resolution, storage, OAuth callbacks, refresh, auditing, and authorization.
- Use `ActionResult.failure` for expected provider/API failures; use Effect errors for missing config, credential, validation, or transport/runtime failures.
- Best-effort provider error-body detail parsing uses `Schema.decodeUnknownEffect(Schema.fromJsonString(Schema.Unknown)).pipe(Effect.result)`; never `try/catch`, raw `JSON.parse`, or sync Schema option decoders.
- If a provider failure builder performs Effect decoding, action executors must `yield*` it so non-2xx responses remain `ActionResult.failure` values.
- Fortnox actions share the `fortnox.oauth` binding; resource scopes (`companyinformation`, `customer`, `invoice`, `supplier`, `supplierinvoice`) grant read AND write at Fortnox, not read-only consent. Customer/invoice create and update actions are `write`; sending or booking is intentionally absent and remains host approval policy if added later. Hosts own licensing, OAuth lifecycle, and throttling. Keep `GivenNumber` distinct from supplier `InvoiceNumber`, preserve monetary wire types, decode JSON arrays separately from runtime Chunks, and accept both lowercase and PascalCase `ErrorInformation` fields (official guide/OpenAPI differ). Optional Fortnox response fields accept JSON null and preserve it. Customer and invoice write fields still reject null; invoice and supplier-invoice rows share the response schema and therefore also accept null. Lists require pagination metadata rather than silently assuming a final page.
- GitHub actions are scoped to integration config `owner`/`repo` (validated syntax; `requiredStringConfig`); inputs never carry owner/repo and org-level reads (`issue-types`, `issue-fields`) use `owner` as the org. `github.token` accepts bearer/API-key/OAuth credentials (installation token, PAT, OAuth). Send `X-GitHub-Api-Version: 2026-03-10` (no singular `assignee`, no `merge_commit_sha`). Outputs are normalized, long text is truncated with a sibling boolean flag (`bodyTruncated`, `patchTruncated`, `fragmentsTruncated`, file `truncated`), lists use `perPage`/`page` plus Link-header `hasNextPage`. Non-2xx map through `githubFailure` to `github_unauthorized|forbidden|not_found|rate_limited|validation|conflict|request_failed` (plus action-specific `github_not_mergeable`, `github_unsupported_content`); 403 with exhausted rate limit or `Retry-After` is `github_rate_limited` with `retryAfterMs`. Never put tokens, headers, or raw bodies in failures: `githubRequest` rebuilds host transport errors from their `cause` only and redacts echoed tokens from decoded error-body strings (including `\u`-escaped JSON). User-controlled path segments reject dot-only values (URL normalization would change the endpoint), and `compare_commits` rejects `:` refs (cross-fork).
- GitHub issue/code search prefixes `repo:{owner}/{repo}`, rejects any `repo:`/`org:`/`user:`/`owner:` qualifier (negated/grouped too, since GitHub ORs repeated `repo:`), and drops results from other repositories (a top-level user `OR` can still inflate `totalCount`/`hasNextPage`; items never leak). Sub-issue and dependency endpoints take the issue database `id`; actions accept issue numbers in the configured repo and resolve ids first. `set_issue_field_values` uses additive `POST` with at least one value (an empty array clears all fields; never use replace-all `PUT`). `merge_pull_request` is `destructive` and requires `expectedHeadSha` sent as `sha`.
- Google action-scoped OAuth slots share the `google.oauth` binding id; `requiredScopes` are consent hints, not separate storage slots.
- Google Calendar create/update boundaries are exclusive unions: exactly one non-empty `date` or `dateTime`, with optional `timeZone`; reject null, empty, missing, and dual-field boundaries before provider execution.
- Google Drive metadata reads use `drive.metadata.readonly`; folder creation, trash, and permanent deletion use the least-privilege `drive.file` scope, which only covers files created by or explicitly opened/shared with the app. Hosts that need arbitrary-drive writes own broader restricted-scope consent and verification policy. Drive list/search support shared drives through `driveId`, exclude trashed items by default, use opaque `pageToken` values, and forward optional file/parent resource keys through `X-Goog-Drive-Resource-Keys`. Binary upload/download stays outside the string/JSON HTTP port; host-only downloads/exports use the binary port.
- Google Drive action inputs require `parentId` with `parentResourceKey` and reject CR/LF in header-bound IDs and resource keys before HTTP. Provider list/search responses may omit an empty `files` field; normalize omission to an empty public `Chunk`.
- Dropbox action-scoped OAuth slots share the `dropbox.oauth` binding id; metadata reads require `files.metadata.read`, file-management writes require `files.content.write`, and the host-only download helper requires `files.content.read`. Binary upload and action-level download stay outside the string-body HTTP port; `dropbox/shared.ts` owns constants, slots, and token resolution so `download.ts` never imports the connector barrel.
- Dropbox HTTP 409 covers not-found and conflict cases; classify from `error_summary`, not status alone. Single-item `move_v2`/`copy_v2` return `{ metadata }`; async job unions belong to batch routes.
- `downloadDropboxFile` on the Dropbox subpath is host-only: it accepts one `/path`, `id:`, `rev:`, or `ns:` value (never share links; no control characters), sends a single `GET` to `content.dropboxapi.com/2/files/download` through the binary port with an ASCII-escaped `Dropbox-API-Arg`, and rejects every 3xx instead of following it. Served metadata comes from the `Dropbox-API-Result` header; require exactly one, verify bare `id:`/`rev:` identity (folder-ID-relative addresses return the child's own ID), and fail when the body length differs from metadata `size`. Classify 409 by `error_summary` (`not_found`, `not_file`, `unsupported_file`, `restricted_content`, `malformed_path`) and expose only the typed code, never bodies, URLs, or headers. Keep it out of `DropboxConnector` and generic agent serialization; hosts still need a materialization/read tool, network adapter, and format-specific reader. No path-root or select-user headers are sent.
- Generic email actions depend on the host-provided `EmailClient` port and never bundle socket, TLS, MIME, IMAP, POP3, or SMTP libraries. Message summaries/full messages may expose optional `isRead`/`isFlagged`; filtered list requests use optional `listMessagesFiltered` and never fall back to legacy `listMessages`. Reject POP3 filters before credentials and schema-validate successful list output.
- Generic attachment retrieval uses the incoming connection and credential through optional `EmailClient.getAttachment`, preserving existing host adapters. Hosts resolve metadata IDs and return decoded file bytes as `contentBase64`; the connector schema-validates successful host output before exposing it. Hosts own MIME parsing, size policy, storage, and scanning; POP3 may require fetching the whole UIDL-addressed message.
- Keep incoming and SMTP credential slots separate. POP3 rejects folders and drafts. IMAP draft adapters generate MIME, `APPEND` with `\Draft`, and, when no folder is provided, discover an advertised `\Drafts` SPECIAL-USE mailbox with a host-defined fallback. SMTP acceptance means submission only, not delivery. `email.send_message` carries optional `saveToSentItems` (default: save when possible) and `sentFolder`, passes IMAP `sentCopy` (connection plus incoming credential) with the SMTP request only for IMAP saving, and reports `sentCopy` status `saved | failed | skipped | unsupported`; legacy hosts that omit `sentCopy` get `unsupported` (requested) or `skipped` (disabled) synthesized, never `saved`. A Sent-save failure after acceptance never means resend.
- Preserve generic email port invariants in schemas: draft requests carry `EmailImapConnection`; folder names and draft IDs are branded non-empty values; UIDPLUS-derived opaque IDs include both UIDVALIDITY and UID. `email.get_message` requires `headers` name/value pairs (hosts fetch via `BODY.PEEK[HEADER]`); list summaries carry no headers.
- `unsubscribe.ts` is a pure RFC 2369/8058 `List-Unsubscribe` parser shared by all providers; execution stays host-owned and publisher URLs never go through `ConnectorHttpClient`.
- Generic email `set_read`, `set_flag`, `trash`, and `untrash` require IMAP and optional host `setRead`/`setFlag`/`trash`/`untrash` methods; preserve old adapters and schema-validate successful outputs. Hosts own UID `STORE`/safe UID moves, `\Trash` discovery, and partial-move reconciliation; never blanket-expunge or fabricate destination IDs. Restore defaults to INBOX, not the original folder; moved IDs must use destination UIDVALIDITY/UID when known.
- Generic email labels are IMAP keyword atoms only (RFC 3501 `atom`, never backslash system flags) through optional host `modifyLabels`; schema-validate entries, preserve unrelated flags with UID `STORE` `+FLAGS.SILENT`/`-FLAGS.SILENT`, check `PERMANENTFLAGS` first, and let removals win on overlap. There is no IMAP label catalog: assignment creates keyword usage, removal clears it; POP3/SMTP cannot persist labels.
- Generic email `move` relocates to a required `destinationFolder` through optional host `move`; default the source to INBOX, use UID `MOVE` when advertised else `COPY` plus a UID-scoped expunge, preserve flags, never blanket-expunge, and return destination UIDVALIDITY/UID mapping when known.
- Generic email batch actions are explicit per operation (`batch_set_read`, `batch_set_flag`, `batch_move`, `batch_trash`, `batch_untrash`, `batch_modify_labels`) with optional matching host methods, 1-100 unique nonempty IDs, one source folder, and root-object tool inputs. Outputs cover every requested ID in input order with succeeded/failed/unknown/not_attempted plus exact summary counts; expose only sanitized codes. Every succeeded move-shaped result requires destination `folder`; only `movedMessageId` is optional. Shared batch outcome shapes (`EmailBatchMessageIds`, `EmailBatchOperationStatus`, `EmailBatchResultCode`, `EmailBatchResultItem`, `EmailBatchSummary`, `EmailBatchOperationOutput`) live in internal `email-batch.ts` and are re-exported from `/email`, `/google`, and `/microsoft`; provider-native move outputs stay provider-side and IMAP move output stays under generic email.
- `email.delete_permanently` is a separate destructive batch-shaped action through optional `EmailClient.deletePermanently`. Hosts delete exactly the identified UID-scoped messages, never blanket-expunge, and do not claim backup/retention erasure; approval remains host policy.
- Outlook `set_read`/`set_flag` use Graph PATCH (`isRead`, follow-up `flagStatus`); `trash`/`untrash` use `/move` to Deleted Items/from Deleted Items. Restore defaults to inbox, not the original folder. `move_message` moves to a required `destinationFolderId` via `/move`; the source folder is not an input, so no same-folder check runs before dispatch. Preserve immutable-ID headers, return the provider message, and reuse draft-write permission selection and application mailbox guards.
- Outlook master-category lifecycle uses opt-in `MailboxSettings.Read`/`MailboxSettings.ReadWrite` slots, excluded from the combined slot, with no `.Shared` mailbox-settings scopes; application mode still requires an explicit `mailbox`. Single-category reads use the read slot; color-only updates PATCH through the write slot (`displayName` immutable). Message assignment uses category `displayName` strings, never master IDs, and never auto-creates catalog entries. `modify_categories` is a non-atomic GET-then-PATCH (remove wins, deduped, exact case-sensitive match) that must fail on an invalid read instead of erasing categories; hosts serialize competing updates with no retries or implied compare-and-swap.
- `outlook.create_reply_draft` is a multi-step write: POST `createReply` without a replacement body so Graph generates quoted history, reuse (or read back in the requested text/html format) the generated body, then PATCH the created draft with the reply prepended (inside the generated HTML body element; newline-joined for text). Post-creation read/save failures, including typed transport and decoding errors once the id is known, retain sanitized `underlying: { draftId, retryable: false, recovery: 'read_edit_existing_draft' }` with read/edit-instead-of-recreate guidance. HTTP failures use `outlook_create_reply_draft_partial` without `retryAfterMs` or generic status-code mapping; never retry creation or delete the draft. No post-write GET only for the return payload.
- Microsoft actions use Microsoft Graph v1.0, not the retired Outlook REST endpoint, direct Exchange APIs, or legacy OneDrive endpoints. Outlook and OneDrive action-scoped slots share the `microsoft.oauth` binding id; hosts own OAuth authority/tenant selection and token lifecycle.
- Outlook inputs default to `/me`; optional `mailbox` targets `/users/{id|userPrincipalName}` for Exchange Online mailboxes. Delegated mode selects `Mail.*.Shared`, except an explicit `mailbox` that case-insensitively equals the resolved `OAuthCredential.accountId` keeps ordinary `Mail.*` slots while preserving the `/users` path (same Graph ID or principal-name form; no trimming, alias resolution, or ID-to-UPN mapping); Bearer credentials, missing account identity, or any mismatch stay Shared. Identity resolution uses the scope-free `microsoft.oauth` binding slot and never authorizes the operation; the selected operation slot still enforces its scopes, so explicit-mailbox delegated actions resolve credentials twice. Integration config `mailboxAccessMode: 'application'` selects non-Shared application permission hints and requires `mailbox`. Exchange mailbox grants and application-token scoping remain host/admin policy.
- Outlook attachment listing is metadata-only and includes inline attachments. List `$select` stays on base attachment properties only (`contentId` is `fileAttachment`-derived and must not be selected across the polymorphic collection); explicit null `lastModifiedDateTime` values decode as null. List results do not promise `contentId`; individual file-attachment retrieval provides it for `cid:` mapping. File attachment retrieval requires Graph's file discriminator and validated `contentBytes`, then maps it to required `contentBase64`; item/reference attachments remain list-only metadata, and hosts own decoding, size policy, storage, and scanning.
- OneDrive inputs default to `/me/drive`; optional `driveId` targets `/drives/{driveId}`. Delegated mode uses least-privilege `Files.Read`/`Files.ReadWrite`; `oneDriveAccessMode: 'delegated_all'` selects `Files.*.All`, while `application` also selects `Files.*.All` and requires `driveId`. Binary upload/download and upload-session mechanics are outside the current string/JSON HTTP port.
- OneDrive move is a synchronous same-drive `PATCH` of `parentReference`; never offer a destination drive or imply copy-delete atomicity. Forward optional `If-Match`, require the root folder's actual ID instead of literal `root`, and return only Graph's updated item. Copy is asynchronous: `202` plus one validated monitor `Location` means accepted, never completed. Keep copy conflict modes to non-destructive `fail`/`rename`; do not expose Graph's destructive `replace` under a `write` action. Poll once per `onedrive.get_copy_status` call, recheck the write slot, send no credential to the capability URL, accept only canonical raw forms of the documented global-cloud OneDrive/SharePoint monitor shapes, and require `redirect: 'manual'` plus `credentials: 'omit'`. Treat a manual `303` as completed without decoding its body, following or exposing its `Location`; sanitize rejected monitor responses without provider bodies. Never expose `resourceLocation`; hosts own approval, cadence, expiry, retries, reconciliation, network enforcement, and secret-safe monitor URL handling.
- `downloadOneDriveItem` on the Microsoft subpath is host-only: it reuses the read slot/application guard, fetches bounded metadata through the binary port, resolves at most four remote targets, and follows at most five HTTPS content redirects with no original headers after the first content request. Metadata redirects fail. Return allowlisted source metadata and untouched bytes, never raw provider fields/signed URLs/wrapped errors. Dot-only IDs fail rather than undergo URL normalization. Keep it out of `MicrosoftConnector` and generic agent serialization; hosts still need an app-owned materialization/read tool (skills cannot download), network adapter, and format-specific reader. No source snapshot consistency is verified.
- Outlook search/list input schemas normalize null/blank optional strings and null page sizes to `undefined` before execution. `outlook.get_message` alone returns required `internetMessageHeaders` via its own select; list/draft/mutation responses stay on the base `OutlookMessage` because PATCH/POST responses never carry headers. Keep this in the shared action schemas so direct callers and agent adapters agree; do not trim real cursors or weaken mailbox/application and nextLink validation.
- Treat Graph `@odata.nextLink` as opaque and only replay links on the configured Graph origin and selected workload collection. Outlook send actions report accepted submission, not delivery.
- Afloat MCP auth actions are server-side connection helpers; never expose returned API keys through model-callable connector modules.
- Figma MCP `refreshToken`, `clientId`, and `clientSecret` come from the runtime
  `OAuthCredential`; never read them from integration config.
- Gmail MIME discovery omits malformed optional attachment sizes; present sizes are nonnegative integers, including zero. This best-effort normalization must not throw on bad optional size metadata.
- Gmail attachment discovery is metadata-only through `gmail.get_thread` or single-message `gmail.list_attachments`; neither exposes MIME-part content. `gmail.get_attachment` requires an `attachmentId`, preserves Gmail's validated base64url `data`, and adds standard-base64 `contentBase64`; inline parts without an attachment ID remain non-retrievable.
- Gmail label lifecycle (`create`/`get`/`update`/`delete`) reuses the existing `gmail.modify` slot for mutations and the readonly slot for reads; renames go through PATCH and require at least one updatable field. Deletes answer 204 with an empty body, so return typed output without JSON decoding; reject dot-only IDs before URL construction.
- Gmail reports `isRead` from `UNREAD` and `isFlagged` from `STARRED` only when `labelIds` are present (empty means read/unflagged; omitted means unknown; provider lookalikes are ignored) on `get_message`, thread messages, and `set_read` output. `gmail.search`/`gmail.list` accept optional `isRead`/`isFlagged` booleans composed into one grouped `q` value. Explicit `gmail.set_read` plus batch `batch_set_read`/`batch_set_starred`/`batch_modify_labels`/`batch_trash`/`batch_untrash` use individually addressed sequential requests (never bulk endpoints) with complete per-ID outcomes, exact counts, sanitized codes, and stop-after-auth/throttle/transport/5xx semantics; label deltas dedupe with removal winning and cap at 100 entries each. `gmail.delete_permanently` is destructive, issues individual `DELETE` requests (only 204 confirms success), and requires the opt-in `GoogleGmailFullMailOAuthCredentialSlot` (`https://mail.google.com/`), which stays out of the combined slot. Permanent Gmail deletion is immediate and claims no backup erasure.
- Outlook messages report `isFlagged` normalized from Graph `flag.flagStatus` (`flagged` true; `notFlagged`/`complete` false; otherwise unknown) wherever `flag` is selected, and `outlook.list_messages` accepts optional `isRead`/`isFlagged` booleans composed into `$filter` with grouped raw filters; fresh typed filters cannot combine with `nextLink`. Explicit batch actions (`batch_set_read`, `batch_set_flag`, `batch_move`, `batch_trash`, `batch_untrash`, `batch_modify_categories`, `delete_permanently`) use Graph JSON batching (`mail-batch.ts`: at most 20 subrequests per sequential envelope, unique correlation IDs, per-subrequest immutable-ID preference, outer auth only, responses matched by correlation ID) with the same per-ID outcome/count/code contract. Move-shaped results require provider-returned message identity and actual `parentFolderId`; category reads that fail leave that message `not_attempted` instead of erasing categories. `permanentDelete` moves items into Recoverable Items/Purges, so retention/holds may still preserve them. Gmail labels, Outlook flags/folders/categories, and IMAP flags/keywords/folders are provider-native models that must never be presented as identical.
- `gmail.get_thread` is a bounded normalized boundary: require an explicit format, decode message text with plain text preferred over HTML, retain selected headers and attachment metadata, and never expose raw MIME or attachment content. Text/nested attachment parts must not enter the message body.
- Agent adapters require a host-provided Effect layer for connector dependencies; adapters must not construct HTTP or credential services themselves.

## Host-only file transfers

- New byte APIs reuse existing provider subpaths, never action arrays/agent serialization. Keep existing GET-only `ConnectorBinaryHttpClient`, Dropbox/OneDrive download signatures/errors, base64 attachment actions, and R2 presigner compatible. `ConnectorBinaryWriteHttpClient` is separate; success means complete HTTP 200/201 metadata with streamed bounds. `transfer-internal.ts` owns shared validation, bounded JSON, code-only errors and single-hop reads/writes; no authenticated arbitrary-URL fetch API.
- `ConnectorFileTransferBudget` is trusted host configuration. Validate runtime envelopes/IDs/bytes/budgets before credentials/network; handle cross-realm Uint8Arrays. Host streaming/header/cancellation/DNS/socket/TLS enforcement remains essential; syntax and post-buffer checks prove none of it. Never log provider URLs (especially Telegram tokens), credentials or byte bodies. No automatic write retry; ambiguous outcomes need reconciliation.
- Dropbox raw create/update are strict add/revision modes with `strict_conflict:true`, `autorename:false`; OneDrive create uses conflictBehavior=fail, update requires explicit acknowledgeOverwrite and is unconditional, NOT CAS. Provider single-request caps are conservative 150MB/250MB; oversized uploads need sessions, not silent truncation/fallback. R2 requires atomic absent/concrete ETag conditions through `R2ObjectClient`; never HEAD-then-PUT or extend conditional guarantees to multipart.
- Drive download/export uses drive.file by default, explicit host-only drive.readonly opt-in. Metadata-only scopes do not authorize bytes. Validate resource keys, caller-specific canDownload and source/export compatibility; role flags alone do not prove caller restrictions. Reject blob-mode native docs/folders/shortcuts; exports max10MB, no Vids long-running API. Content restrictions still apply at the provider request.
- Fortnox file discovery filters supplierinvoicenumber by GivenNumber, uses connectfile, and requires pagination metadata. Preview uses GET /invoices/{DocumentNumber}/preview (not /print; does not mark Sent), archive uses GET /archive/{id}. invoice/connectfile/archive scopes grant read AND write; new file slots are opt-in, not added to existing combined consent. Preview is generated PDF; archive OpenAPI modeling is imperfect.
- Notion file objects require trusted host URL policy; external opt-in; no bearer forwarded, no file_upload-ID download. Refresh expired URLs by owning page/block/property. New downloads reject redirects except Todoist's known-host five-hop loop (no reauth); existing OneDrive behavior stays unchanged.
- Gmail byte helper consumes bounded JSON/base64url through binary port and validates canonical pad bits, decoded size and cap. Outlook checks discriminator before /$value, permits encoded opaque Graph IDs including slash, preserves immutable IDs/shared/application guards, rejects item/reference. Optional EmailClient.getAttachmentBytes reuses incoming guards/auth, bounds raw decoded bytes, preserves adapters and no base64 roundtrip; host preserves IMAP flags, releases MIME streams and bounds POP3 full-message fetches.
- Telegram hosted getFile/download only, <=20MB, strict relative path, no local filesystem, no fabricated original filename/MIME. Todoist comments expose metadata without attachment URLs; host attachment read by commentId allows files.todoist.com auth only on first content request, known CDNs unauthenticated, validated 301/302/303/307/308 redirects only.
- GitHub host-only helpers stay out of `GithubConnector.actions`: `createGithubAppInstallationToken` signs an RS256 App JWT with WebCrypto only (PKCS#8 or PKCS#1 wrapped in code, literal `\n` normalized, iat now-60, exp now+540) and returns `{ token, expiresAt }` without caching; errors are code-only `GithubAppTokenError`. `uploadGithubAttachment` uses the undocumented, unstable `uploads.github.com/user-attachments/assets` endpoint through `ConnectorBinaryWriteHttpClient` with the optional `github.upload_token` user token (installation `ghs_` tokens are rejected before network; GitHub 404s them), image/video allowlist, 10 MB/100 MB caps that hosts may only lower, and strict `github.com/user-attachments/` URL validation before building markdown.
- Afloat/Figma file operations reuse dynamically discovered remote MCP contracts, not duplicate wrappers. Afloat one-hour grants and receipt/logo intent completion, Figma asset download/upload/design editing are documented in the file guide; no whole .fig file claim or claim that write-capable MCP tools are read-only.
