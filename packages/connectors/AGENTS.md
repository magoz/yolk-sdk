# Connectors

`@yolk-sdk/connectors` defines Effect-native primitives for reusable external-system connectors.

## Boundaries

- No DB, encryption, token storage, refresh persistence, app auth, routes, UI, or product permissions.
- No user/team/org/workspace/project concepts; hosts own identity and lifecycle.
- No Promise facade; public APIs are Effect-native only.
- Do not repackage Effect HTTP/runtime adapters; expose ports and let hosts wire Effect layers.
  - Named exception: `@yolk-sdk/connectors/conformance` (`src/conformance/index.ts`) bridges an Effect `HttpClient` to `ConnectorHttpClient`/`ConnectorBinaryHttpClient`/`ConnectorBinaryWriteHttpClient` (including `uploadSession`) and provides `staticCredentialResolverLayer` plus `ConformanceCleanupReporter` (a `Context.Reference`, default `Effect.logWarning`, receiving cleanup problems a write case raises while being interrupted), for conformance and tests only (replay, emulators, live-by-hand practice runs). It enforces NO streamed byte limits, redirect, DNS/IP, timeout, or TLS policy (binary limits are checked only after buffering), maps transport failures to code-only errors without URL/headers/body, and must never be documented or used as a production adapter or credential store. The write bridge refuses (sends nothing for) bad methods/status lists/limits and over-`maxUploadBytes` bodies, and `uploadSession` also refuses `authorization`/`cookie`/`proxy-authorization` headers and DELETE bodies; session URLs are secret capabilities that never appear in errors. `TracerPropagationEnabled=false` still records `url.full`/`url.query` on client spans, so session requests and requests without `authorization` also set `HttpClient.TracerDisabledWhen` (ORed with the host's predicate, never replacing it).
- Raw secrets may flow through host-provided Effect services at invocation time, but integrations store only opaque credential refs.
- Provider modules may define vendor mechanics and schemas, not host policy.
- Only `src/agent.ts` may import `@yolk-sdk/agent`; `@yolk-sdk/conformance` (wire and port fixtures) may be imported only under a `src/**/conformance/` directory; nothing imports `@yolk-sdk/emulators`. `scripts/check-package-boundaries.ts` enforces all three.

## Design rules

- Connector = reusable implementation; Integration = host-owned config that makes a connector invokable.
- Actions declare typed input/output schemas and optional `read`/`write`/`destructive` access metadata; action execution stays Effect-native. Agent adapter host overrides win, otherwise declared access is used.
- `defineAction` returns `TypedConnectorAction`: `execute`/connector `invoke` remain dynamic wire boundaries; `executeTyped` accepts decoded input and validates with `Schema.toType` without replaying encoding transforms. Implementations still validate external provider/host output; the generic executor does not automatically decode `outputSchema`.
- Reuse Fortnox's canonical identity schemas for file discovery and preview. Discovery `givenNumber` is `FortnoxGivenNumber`, not supplier `InvoiceNumber`; preview uses `FortnoxDocumentNumber` with complete-segment URL encoding, not the archive-specific `OpaqueId` restriction.
- `http.ts` is infrastructure: connectors emit typed requests; hosts provide `ConnectorHttpClient` and preserve headers/body content type. This complete-string port cannot enforce pre-buffer download limits: hosts cap actual streamed bytes, allow bounded base64/JSON expansion only for successful trusted attachment requests, and keep ordinary/error bounds separate. Decoded limits and canonical base64 checks remain host policy; provider sizes are not byte-length proof.
- `binary-http.ts` is a separate optional host-only port, not an adapter or action. Hosts enforce streamed actual-byte/error-body budgets, timeouts/cancellation, connection-time public DNS/IP policy, TLS, and no automatic redirects/cookie jars/ambient auth. SDK syntax screens and post-buffer checks do not prove network enforcement. See README host integration contract.
- Hosts provide credential resolution, storage, OAuth callbacks, refresh, auditing, and authorization.
- Use `ActionResult.failure` for expected provider/API failures; use Effect errors for missing config, credential, validation, or transport/runtime failures.
- Best-effort provider error-body detail parsing uses `Schema.decodeUnknownEffect(Schema.fromJsonString(Schema.Unknown)).pipe(Effect.result)`; never `try/catch`, raw `JSON.parse`, or sync Schema option decoders.
- If a provider failure builder performs Effect decoding, action executors must `yield*` it so non-2xx responses remain `ActionResult.failure` values.
- Fortnox actions share the `fortnox.oauth` binding; resource scopes (`companyinformation`, `customer`, `invoice`, `supplier`, `supplierinvoice`) grant read AND write at Fortnox, not read-only consent. Customer/invoice create and update actions are `write`; sending or booking is intentionally absent and remains host approval policy if added later. Hosts own licensing, OAuth lifecycle, and throttling. Keep `GivenNumber` distinct from supplier `InvoiceNumber`, preserve monetary wire types, decode JSON arrays separately from runtime Chunks, and accept both lowercase and PascalCase `ErrorInformation` fields (official guide/OpenAPI differ). Optional Fortnox response fields accept JSON null and preserve it. Customer write inputs omit read-only `Country` and list-only `Phone`; the customer create/update actions close them over a Struct of the Class fields (unknown keys fail validation on `execute` and `executeTyped`, not stripped; `Schema.toType` skips key checks on existing Class instances). Invoice write inputs intentionally still strip unknown keys on `execute` (`executeTyped` trusts existing invoice Class instances). Responses keep `Country`/`Phone`. Customer and invoice write fields still reject null; invoice and supplier-invoice rows share the response schema and therefore also accept null. Lists require pagination metadata rather than silently assuming a final page.
- Fortnox conformance (`src/fortnox/conformance/`; case table in `apps/docs/content/docs/connectors/fortnox.mdx#conformance-cases`): cases run the real actions/helpers over the ports plus `FortnoxConformanceConfig` seeds, never hard-coded account data. Mutation cases restore through `withRestore` and verify every written field exactly (no null-hiding); never swallow a failed restore. The rejection case must prove absence (404 or a not-found `ErrorInformation` code; never 401/403) before writing, and names anything it unexpectedly creates. The email case stays write-irreversible, aborts unless the recipient equals the `emailRecipient` seed, and sends through `getFortnoxResponse` with `redirect: 'manual'`/`credentials: 'omit'`, failing on any 3xx; connector actions never set those flags. Fixtures stay synthetic; `--record` only stages to a new run directory under gitignored `.conformance-recordings/` (temp directory plus one rename), and promoting recordings (scrub first) updates `test/fortnox-conformance.test.ts` and `scripts/test/run-fortnox-conformance.test.ts` in the same change; a promoted payment-filter recording also needs `atTestNow` moved past the recorded `DueDate`.
- Microsoft conformance (`src/microsoft/conformance/`; case table in `apps/docs/content/docs/connectors/microsoft.mdx#conformance-cases`): Outlook/OneDrive cases run the real actions over the ports plus `MicrosoftConformanceConfig` seeds, never hard-coded account data. The connector has NO calendar actions: calendar cases send raw Graph v1.0 requests through internal `calendar.ts` (`ConnectorHttpClient`, `resolveMicrosoftAccessToken`, `microsoftProviderFailure`; its `Calendars.*` slot hints and instant helpers stay unexported) and say so in their `docs`; adding calendar actions is a separate decision.
- Microsoft write cases are all write-reversible: each owns a `yolk-conformance` event/draft/folder removed through `withOwnItem` (events via DELETE, drafts via `outlook.delete_permanently`, folders via `onedrive.delete_item`). Mask every create or move together with its decode and id registration (before any assertion), and keep ids pending until the 404 check passes. An id-less create fails `MicrosoftConformanceRestoreFailed`; an ambiguous create (transport/decoding failure, no status, or 5xx) fails `MicrosoftConformanceActionFailed` with `createOutcome: 'unknown'`; both carry manual-recovery advice. Never swallow a failed restore; never send mail or invitations (no attendees/recipients).
- Shared write-safety helpers live in internal `src/conformance/cleanup-reporter.ts`: `classifyWriteExit` (a 4xx other than 408 is a definitive rejection; transport/decoding failure, no status, 408, or 5xx is ambiguous, as in the Gmail and Outlook write paths; the Notion and Microsoft conformance cases still keep their own copies that treat 408 as a rejection, a known follow-up) and `failReporting` (report through `ConformanceCleanupReporter` when interrupted, then fail). Dropbox, Todoist, and the Telegram send use them; change the classification there, once.
- Dropbox conformance (`src/dropbox/conformance/`; case table in `apps/docs/content/docs/connectors/dropbox.mdx#conformance-cases`): cases run the real actions and the host-only `createDropboxFile`/`updateDropboxFile` over the ports plus `DropboxConformanceConfig` seeds, never hard-coded account data. Write cases work only inside their own `yolk-conformance-<runId>-<case>` folder under `workFolderPath` via `withOwnFolder`; the `runId` seed makes that namespace invocation-unique (fixtures use `run-synthetic`, the live runner generates a fresh random id per invocation and never accepts one), and concurrent runs are supported ONLY through distinct run ids. Prove the path absent first (nothing written otherwise); mask the create request, its decode, and the id registration together. A definitive create rejection (4xx other than 408, e.g. `path/conflict`) deletes NOTHING; an ambiguous one (transport/decoding failure, no status, 408, 5xx), including either duplicate create of the conflict case, is always reported as `createOutcome: 'unknown'` naming the exact attempted path (one absence check is never reconciliation). Mask every write inside `use` (copy, move, upload, delete) with `Effect.uninterruptible`. Clean up by the created entry's id; skip the path fallback when the id delete answers not-found, otherwise fall back to the owned path; then require `get_metadata` not-found; never adopt a returned path outside the case folder (`DropboxConformanceCleanupRefused`); never swallow a failed restore (`DropboxConformanceRestoreFailed`, naming the path). Replay matches by method + URL only and every RPC route is a fixed `POST` URL, so a drill that stops a case early must drop the exchanges it no longer reaches. A cleanup failure or unknown-outcome create raised while the case is being interrupted is also handed to `ConformanceCleanupReporter` (via `failReporting`) before leaving the mask, since an interruption may replace it. `RunId` requires the `run-` prefix so `findDropboxConformanceLeftovers` (read-only listing of `yolk-conformance-run-*` under `workFolderPath`; a missing work folder holds none) sees every run; it backs the runner's leftover warnings and never deletes. Fixtures stay synthetic; `--record` stages only to `.conformance-recordings/dropbox/` (recordings keep `dropbox-api-arg`); promoting updates `test/dropbox-conformance.test.ts` and `scripts/test/run-dropbox-conformance.test.ts` in the same change.
- Notion conformance (`src/notion/conformance/`; case table in `apps/docs/content/docs/connectors/notion.mdx#conformance-cases`): cases run the real actions over the ports plus `NotionConformanceConfig` seed ids, never hard-coded account data, and claim only what the connector relies on; sub-claims no live run has settled carry "(unverified: ...)" in `wire`. The pinned-version case observes the outgoing `Notion-Version` by wrapping the `ConnectorHttpClient` port (no raw requests). Untyped action outputs are decoded in the case with local schemas; a shape mismatch is a `ConformanceMismatch`. The property-paging case requires a `%XX`-escaped property id read from the page, so it exercises the connector's second percent-encoding. The write case owns a `yolk-conformance` page (create and id registration uninterruptible); any response showing `archived` or `in_trash` true, or a not-found read after a successful archive, counts as trashed (an archive response showing a flag clears pending at once; a not-found read after a successful archive is accepted later, in the restore), so a false readback claim is a claim failure, never a restore failure; otherwise the restore trashes the page through `notion.update_page` `archived: true`. Ambiguous creates report `createOutcome: 'unknown'`; failed restores `NotionConformanceRestoreFailed`. A failed restore or unknown-outcome create raised while the case is being interrupted is also handed to `ConformanceCleanupReporter`. `findNotionConformanceLeftovers` (read-only, best-effort search for untrashed `yolk-conformance page` pages) backs the runner's leftover warnings; it never trashes. Fixtures stay synthetic; `--record` stages only to `.conformance-recordings/notion/` (recordings keep `notion-version`); promoting updates `test/notion-conformance.test.ts` and `scripts/test/run-notion-conformance.test.ts` in the same change.
- Todoist conformance (`src/todoist/conformance/`; case table in `apps/docs/content/docs/connectors/todoist.mdx#conformance-cases`): cases run the real actions over the ports plus `TodoistConformanceConfig` seed ids, never hard-coded account data, and claim only what the connector relies on; guessed sub-claims carry "(unverified: ...)" in `wire` and are listed on the docs page. Write cases work only inside their own `yolk-conformance-<runId>-<case>` project under `workProjectId` via `withOwnProject` (fixtures use `run-synthetic`; the live runner generates a fresh id per invocation and never accepts one). Mask the project create, its decode, and the id registration together, and every later write (task create/update/close, project delete). A definitive create rejection (4xx other than 408) deletes NOTHING; an ambiguous one (transport/decoding failure, no status, 408, 5xx) fails `createOutcome: 'unknown'` naming the exact project or task; never delete by name (names are not unique). Clean up by project id, then require `todoist.get_project` not-found; never adopt a project without the requested name or with a seeded project's id, nor a task outside the case project (`TodoistConformanceCleanupRefused`); `parent_id` is the parent-id case's claim, not an ownership rule (a fresh project under another parent is still deleted by id); the cleanup verifies project absence only (task removal with the project is the delete case's unverified claim); the due case claims the outgoing `due_date`/`due_datetime` mapping and that each answer carries a `due` object whose `date` starts with the requested day (so an ignored field fails it), never the due's representation (the connector never reads `due`); the delete case's leftover-task mismatch names the task id; never swallow a failed restore (`TodoistConformanceRestoreFailed`, naming project and id). Cleanup problems raised while interrupted also go to `ConformanceCleanupReporter`. `findTodoistConformanceLeftovers` (read-only, bounded listing of active `yolk-conformance-run-*` projects) backs the runner's leftover warnings. Fixtures stay synthetic; `--record` stages only to `.conformance-recordings/todoist/`; promoting updates `test/todoist-conformance.test.ts` and `scripts/test/run-todoist-conformance.test.ts` in the same change.
- Telegram conformance (`src/telegram/conformance/`; case table in `apps/docs/content/docs/connectors/telegram.mdx#conformance-cases`): cases run the real actions and host-only `downloadTelegramFile` over the ports plus `TelegramConformanceConfig` seeds. The Telegram actions read only HTTP statuses (`downloadTelegramFile` decodes the `getFile` result), so Bot API body claims are observed by wrapping `ConnectorHttpClient` / `ConnectorBinaryHttpClient` (no raw requests) and reduced to `ok`, the only field that says whether a call succeeded; the error case checks a 4xx status with `ok: false` (never `200`, not 5xx), and the file case makes a reported `file_size` a seed precondition and compares it only when present; the error-envelope case swaps the `CredentialResolver` for one synthetic invalid token. `telegram.send_message` cannot be undone, so the send case stays `write-irreversible` (exact-id opt-in only), names the per-invocation `runId` in its text, masks the send together with decoding its observed answer, reports an ambiguous send (transport/decoding failure, no status, 408, 5xx, or a 2xx without `ok: true`; `sendOutcome: 'unknown'`, also through `ConformanceCleanupReporter` when interrupted) with the text to look for, and has no cleanup or leftover lookup. Fixture URLs carry only `telegramConformanceReplayBotToken` (or the synthetic invalid token); the token is in every Bot API URL path, so failures never carry URLs, and `--record` scrubs the live token from recorded URLs (`scrubRecording` / `replayAccessToken` in the shared runner, whose token guard then refuses, before any file or checklist is built, a recording in which the token or its secret part survives in URLs, headers, decoded base64, reassembled chunks, or unescaped JSON strings, or that holds a body outside its inspectable allowlist: strict UTF-8 text without NUL characters; binary, compressed, and UTF-16 bodies are refused, so the `fileId` seed must be a plain UTF-8 text file). The live runner prints the run id before any case when the send is enabled, and its interruption advice points at `yolk-conformance run-` messages in the chat. Promoting updates `test/telegram-conformance.test.ts` and `scripts/test/run-telegram-conformance.test.ts` in the same change.
- Email conformance (`src/email/conformance/`; case table in `apps/docs/content/docs/connectors/email.mdx#conformance-cases`): port-level cases run the real email actions over `EmailClient` plus `CredentialResolver` and `EmailConformanceConfig` seeds, never hard-coded account data, and never parse host ids. Claims that need a particular host (a legacy host without `listMessagesFiltered` or `sentCopy`, call logging for POP3) wrap the provided `EmailClient` with a port-level shim and say so in `wire`. Write cases own a `yolk-conformance` draft (create and location tracking uninterruptible, moves re-register the destination id) and permanently delete it through `email.delete_permanently`, or restore the seeded flags; never swallow a failed restore (`EmailConformanceRestoreFailed`). The move case needs the host-port convention `emailMessageNotFoundCode` (`getMessage` of an id that addresses no message answers `ActionResult.failure` code `message_not_found`); any other failure fails it. The POP3 case covers every mutation action (single-message, labels, six batch, `delete_permanently`); a new mutation action joins its rejection table. Send cases stay `write-irreversible` and send only to the `recipient` / `undeliverableRecipient` seeds. Fixtures are synthetic `PortFixture`s (one call each, credential-free requests, `example.test` data); `@yolk-sdk/emulators/email` keeps a verbatim copy, so changing a fixture updates `packages/emulators/src/email-fixtures.ts` in the same change. `backend.ts` is conformance/testing only: `emailClientFromBackend` decodes responses with each method's output schema, maps `failure` to `ActionResult.failure` / `ConnectorError`, and fails `notEmulated` closed; it bridges no `getAttachmentBytes`. Connectors never import `@yolk-sdk/emulators` (boundary-enforced).
- Microsoft fixtures stay synthetic (`example.test` users, `synthetic-my.sharepoint.com` hosts) with the `prefer` headers the connector sends. `--record` stages only to `.conformance-recordings/microsoft/` (recordings lose `prefer`); promoting updates `test/microsoft-conformance.test.ts` and `scripts/test/run-microsoft-conformance.test.ts` in the same change, and changed shared seeds (`mailbox`, `calendarId`, `driveId`) invalidate other committed fixtures.
- GitHub actions are scoped to integration config `owner`/`repo` (validated syntax; `requiredStringConfig`); inputs never carry owner/repo and org-level reads (`issue-types`, `issue-fields`) use `owner` as the org. `github.token` accepts bearer/API-key/OAuth credentials (installation token, PAT, OAuth). Send `X-GitHub-Api-Version: 2026-03-10` (no singular `assignee`, no `merge_commit_sha`). Outputs are normalized, long text is truncated with a sibling boolean flag (`bodyTruncated`, `patchTruncated`, `fragmentsTruncated`, file `truncated`), lists use `perPage`/`page` plus Link-header `hasNextPage`. Non-2xx map through `githubFailure` to `github_unauthorized|forbidden|not_found|rate_limited|validation|conflict|request_failed` (plus action-specific `github_not_mergeable`, `github_unsupported_content`); 403 with exhausted rate limit or `Retry-After` is `github_rate_limited` with `retryAfterMs`. Never put tokens, headers, or raw bodies in failures: `githubRequest` rebuilds host transport errors from their `cause` only and redacts echoed tokens from decoded error-body strings (including `\u`-escaped JSON). User-controlled path segments reject dot-only values (URL normalization would change the endpoint), and `compare_commits` rejects `:` refs (cross-fork).
- GitHub issue/code search prefixes `repo:{owner}/{repo}`, rejects any `repo:`/`org:`/`user:`/`owner:` qualifier (negated/grouped too, since GitHub ORs repeated `repo:`), and drops results from other repositories (a top-level user `OR` can still inflate `totalCount`/`hasNextPage`; items never leak). Sub-issue and dependency endpoints take the issue database `id`; actions accept issue numbers in the configured repo and resolve ids first. `set_issue_field_values` uses additive `POST` with at least one value (an empty array clears all fields; never use replace-all `PUT`). `merge_pull_request` is `destructive` and requires `expectedHeadSha` sent as `sha`.
- Google action-scoped OAuth slots share the `google.oauth` binding id; `requiredScopes` are consent hints, not separate storage slots.
- Google Calendar create/update boundaries are exclusive unions: exactly one non-empty `date` or `dateTime`, with optional `timeZone`; reject null, empty, missing, and dual-field boundaries before provider execution.
- Google Drive metadata reads use `drive.metadata.readonly`; folder creation, trash, and permanent deletion use the least-privilege `drive.file` scope, which only covers files created by or explicitly opened/shared with the app. Hosts that need arbitrary-drive writes own broader restricted-scope consent and verification policy. Drive list/search support shared drives through `driveId`, exclude trashed items by default, use opaque `pageToken` values, and forward optional file/parent resource keys through `X-Goog-Drive-Resource-Keys`. Binary upload/download stays outside the string/JSON HTTP port; host-only downloads/exports use the binary port.
- Google Drive action inputs require `parentId` with `parentResourceKey` and reject CR/LF in header-bound IDs and resource keys before HTTP. Provider list/search responses may omit an empty `files` field; normalize omission to an empty public `Chunk`.
- Dropbox action-scoped OAuth slots share the `dropbox.oauth` binding id; metadata reads require `files.metadata.read`, file-management writes require `files.content.write`, and the host-only download helper requires `files.content.read`. Binary upload and action-level download stay outside the string-body HTTP port; `dropbox/shared.ts` owns constants, slots, and token resolution so `download.ts` never imports the connector barrel.
- Dropbox HTTP 409 covers not-found and conflict cases; classify from `error_summary`, not status alone. Single-item `move_v2`/`copy_v2` return `{ metadata }`; async job unions belong to batch routes.
- `downloadDropboxFile` on the Dropbox subpath is host-only: it accepts one `/path`, `id:`, `rev:`, or `ns:` value (never share links; no control characters), sends a single `GET` to `content.dropboxapi.com/2/files/download` through the binary port with an ASCII-escaped `Dropbox-API-Arg`, and rejects every 3xx instead of following it. Served metadata comes from the `Dropbox-API-Result` header; require exactly one, verify bare `id:`/`rev:` identity (folder-ID-relative addresses return the child's own ID), and fail when the body length differs from metadata `size`. Classify 409 by `error_summary` (`not_found`, `not_file`, `unsupported_file`, `restricted_content`, `malformed_path`) and expose only the typed code, never bodies, URLs, or headers. Keep it out of `DropboxConnector` and generic agent serialization; hosts still need a materialization/read tool, network adapter, and format-specific reader. No path-root or select-user headers are sent.
- Generic email actions depend on the host-provided `EmailClient` port and never bundle socket, TLS, MIME, IMAP, POP3, or SMTP libraries. Message summaries/full messages may expose optional `isRead`/`isFlagged`; filtered list requests use optional `listMessagesFiltered` and never fall back to legacy `listMessages`. Reject POP3 filters before credentials and schema-validate successful list output.
- Generic attachment retrieval uses the incoming connection and credential through optional `EmailClient.getAttachment`, preserving existing host adapters. Hosts resolve metadata IDs and return decoded file bytes as `contentBase64`; the connector schema-validates successful host output before exposing it. Hosts own MIME parsing, size policy, storage, and scanning; POP3 may require fetching the whole UIDL-addressed message.
- Keep incoming and SMTP credential slots separate. POP3 rejects folders and drafts. IMAP draft adapters generate MIME, `APPEND` with `\Draft`, and, when no folder is provided, discover an advertised `\Drafts` SPECIAL-USE mailbox with a host-defined fallback. SMTP acceptance means submission only, not delivery. `email.send_message` carries optional `saveToSentItems` (default: save when possible) and `sentFolder`, passes IMAP `sentCopy` (connection plus incoming credential) with the SMTP request only for IMAP saving, and reports `sentCopy` status `saved | failed | skipped | unsupported`; legacy hosts that omit `sentCopy` get `unsupported` (requested) or `skipped` (disabled) synthesized, never `saved`. A Sent-save failure after acceptance never means resend.
- Preserve generic email port invariants in schemas: draft requests carry `EmailImapConnection`; folder names and draft IDs are branded non-empty values; UIDPLUS-derived opaque IDs include both UIDVALIDITY and UID. `email.get_message` requires `headers` name/value pairs (hosts fetch via `BODY.PEEK[HEADER]`); list summaries carry no headers.
- `unsubscribe.ts` is a pure RFC 2369/8058 `List-Unsubscribe` parser shared by all providers; execution stays host-owned and publisher URLs never go through `ConnectorHttpClient`.
- Generic email `set_read`, `set_flag`, `trash`, and `untrash` require IMAP and optional host `setRead`/`setFlag`/`trash`/`untrash` methods; preserve old adapters and schema-validate successful outputs. Hosts own UID `STORE`/safe UID moves, `\Trash` discovery, and partial-move reconciliation; never blanket-expunge or fabricate destination IDs. Restore defaults to INBOX, not the original folder; moved IDs must use destination UIDVALIDITY/UID when known.
- Generic email labels are IMAP keyword atoms only (RFC 3501 `atom`, never backslash system flags) through optional host `modifyLabels`; schema-validate entries, preserve unrelated flags with UID `STORE` `+FLAGS.SILENT`/`-FLAGS.SILENT`, check `PERMANENTFLAGS` first, and let removals win on overlap. There is no IMAP label catalog: assignment creates keyword usage, removal clears it; POP3/SMTP cannot persist labels.
- Generic email `move` relocates to a required `destinationFolder` through optional host `move`; default the source to INBOX, use UID `MOVE` when advertised else `COPY` plus a UID-scoped expunge, preserve flags, never blanket-expunge, and return destination UIDVALIDITY/UID mapping when known.
