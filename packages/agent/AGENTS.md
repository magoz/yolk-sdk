# Agent Package

`@yolk-sdk/agent` is the main package for building and running agents. Root export stays intentionally empty; use explicit subpaths.

## Structure

`package.json` is the export source of truth. See `patterns/PACKAGE_ARCHITECTURE.md` for the public
subpath catalog, dependency direction, physical layout, and tree-shaking constraints.

## Boundaries

- Core subpaths have no React, Next.js, app imports, auth, storage drivers, provider SDKs, or product concepts.
- `src/react` and `src/voice/react.ts` are the only React-using areas; React is an optional peer.
- Provider subpaths own vendor mechanics only; hosts still own token storage/refresh and app policy.
- Provider wire fixtures live under `src/providers/<vendor>/conformance/`; only agent `src` code there may import `@yolk-sdk/conformance/*` (tests may import it). The rule is stated once in `patterns/PACKAGE_ARCHITECTURE.md` (Dependency Direction) and boundary-enforced. `providers/vercel/conformance` exports verified live Gateway recordings (`evidence: 'verified'`, `account: 'synthetic'`, recorded 2026-09-30; the DeepSeek one with the default reasoning model `deepseek/deepseek-v4.1-flash`) for plain text, DeepSeek-style reasoning, split tool-call deltas, and an error envelope; `pnpm conformance:gateway --live --owner-approved --account <label>` (synthetic, non-identifying label) is the only path that may re-record them: it runs the Gateway conformance cases live through the wire recorder and writes nothing unless the new fixtures pass the same cases on replay, so new wire claims belong in `cases.ts`, not the script. Re-recording also means updating `liveObservation` (account and date) in `cases.ts` by hand: the script does not touch it, and the tests require each case's `observed` to match its fixtures' `account` and `recordedAt`. Fixture prompts and labels stay synthetic: no credentials, customer data, or private references. Gateway streaming tests replay these fixtures through `ReplayHttpClient` instead of hand-written SSE.
- `providers/vercel/conformance/cases.ts` defines four `read` Gateway conformance cases (plain text, DeepSeek reasoning order, tool-call delta assembly, error envelope) that need only `HttpClient` + `VercelAiGatewayConformanceConfig`, assert claims from `LLMProvider` events (never the replay ledger, which exists only under replay), carry `observed` from the owner-approved live probe that recorded the fixtures (`synthetic`, 2026-09-30), and are run through `@yolk-sdk/conformance/runner` in `test/providers/vercel/ai-gateway-conformance-cases.test.ts` with disagreement drills.
- `providers/openai/conformance` mirrors it for the generic OpenAI-compatible chat provider (`makeOpenAiProviderLayer`, default endpoint and `max_completion_tokens`) against OpenAI Chat Completions: four synthetic fixtures and four `read` cases (streamed plain text, tool-call delta assembly, the error envelope, and non-streamed JSON plain text) that need only `HttpClient` + `OpenAiConformanceConfig`. Claims must hold live too (no delta counts; the error case rejects 401/403 and `auth`). `pnpm conformance:openai --live --owner-approved --account <label>` (needs `OPENAI_API_KEY`) is the only path that may replace the fixtures, with the same replay-verified write gate. Tests: `test/providers/openai/openai-chat-conformance-cases.test.ts` (replay, ledger request claims, drills over parsed SSE/JSON).
- `providers/anthropic/conformance` covers Anthropic Messages with five synthetic fixtures and five `read` cases (streamed plain text without thinking, forced `tool_choice: { type: 'tool', disable_parallel_tool_use: true }` input-fragment assembly, thinking before text, the 404 error envelope, and `stop_reason: max_tokens` as a non-retryable `invalid_response` without `Done`) that need only `HttpClient` + `AnthropicConformanceConfig`. They run native Messages through the same private layer OpenCode Go `messages` uses (`anthropic-messages-provider-internal.ts`, identity `anthropic_messages`, `x-api-key`, default `https://api.anthropic.com/v1/messages`), not the Claude subscription provider (OAuth-only, subscription fingerprint); `tool_choice` and `thinking` go through that layer's internal `extraBody` (lowered fields win; OpenCode Go never sets it). The native layer does not surface the envelope `error.type`, so besides status 404, not `auth`, non-retryable, and a sanitized message, the error case wraps its own `HttpClient` (conformance-local; the provider is unchanged) to read the 404 body and requires `{ type: 'error', error: { type: 'not_found_error', message } }`. `pnpm conformance:anthropic --live --owner-approved --account <label>` (needs `ANTHROPIC_API_KEY`, a native API key) is the only path that may replace the fixtures, with the same replay-verified write gate; thinking signatures and `redacted_thinking` `data` are redacted in text chunks only (never re-chunked), and a value left in a base64 chunk or split across chunks, a non-string value, or a repeated key refuses the write (checked on every occurrence in the reassembled wire, never through `JSON.parse`), as does any SSE `data:` payload or body the member scanner cannot fully scan (only `[DONE]` is exempt). Tests: `test/providers/anthropic/anthropic-messages-conformance-cases.test.ts` (replay, ledger request claims, drills over parsed SSE).
- The Responses-based subscription providers share one conformance case shape, built by the private `providers/openai/conformance/responses-cases-internal.ts` (inside a conformance directory, so it may import `@yolk-sdk/conformance/*`). `providers/openai/conformance` adds four Codex cases (`openai.codex.stream.*`) through the public `makeOpenAiCodexProviderLayer` (default `https://chatgpt.com/backend-api/codex/responses`), and `providers/xai/conformance` (the vendor-owned home for Grok, since the Grok provider lives under `providers/xai`) adds four Grok cases (`xai.grok.stream.*`) through the public `makeXAiGrokProviderLayer` (default CLI proxy, host `clientVersion`, `maxOutputTokens`); each has four synthetic unverified fixtures and needs only `HttpClient` + `OpenAiCodexConformanceConfig` / `XAiGrokConformanceConfig` (OAuth token, models, and for Grok the client version and output limit). Cases: streamed plain text (text, one Done(stop), Usage), `function_call` argument assembly (at least one call, all `lookup_weather` with distinct ids and a non-empty `city`, one Done(tool_use); the providers cannot force `tool_choice`, so no exactly-one claim; the providers read only completed items, so the case also tees the body and requires the `response.function_call_arguments.delta` fragments joined per `item_id` to equal every completed copy's `arguments`, with no fragment-count claim), the unknown-model error (non-retryable 400/404, not `auth`, status-only message, and a JSON error body with a message read by a conformance-local `HttpClient` wrapper), and the terminal event (the success body, teed chunk for chunk by that wrapper, ends with exactly one `response.completed` whose status is `completed`). Tests replay both families with ledger request claims (Codex: `originator`, reasoning `{ effort: 'low', summary: 'auto' }`, never `max_output_tokens`; Grok: `X-XAI-Token-Auth`, model override, client version, `max_output_tokens`, no `reasoning`) and structural drills that pin Grok's required terminal event and Codex's EOF-completion compatibility (`test/providers/responses-conformance-cases.test.ts`). `pnpm conformance:codex` / `pnpm conformance:grok` are dry-run probes; live runs need subscription OAuth tokens (`OPENAI_CODEX_ACCESS_TOKEN`, optional `OPENAI_CODEX_ACCOUNT_ID`; `XAI_GROK_ACCESS_TOKEN` plus `--client-version`), the repository owner's approval (`--owner-approved`; `--live` is refused whenever `CI` is set to any non-empty value, `0` and `false` included), and the same replay-verified write gate.
- `providers/opencode/conformance` covers OpenCode Go through the public `makeOpenCodeGoProviderLayer` and `fetchOpenCodeGoSubscriptionUsage` (default `https://opencode.ai/zen/go/v1`): five synthetic unverified fixtures and five `read` cases needing only `HttpClient` + `OpenCodeGoConformanceConfig` (redacted API key, positive `maxOutputTokens`, one model id per protocol; the defaults `synthetic-go-*` are placeholders). Streamed plain text per protocol (`chat-completions`: Bearer, `max_tokens`, `stream_options.include_usage`; `messages`: `x-api-key`, `anthropic-version`, no OAuth fingerprint, required `message_stop`; `responses`: Bearer, `max_output_tokens`, required `response.completed`) claims text, one Done(stop), and Usage; `opencode.go.responses.stream.commentary-replay` reads the request at its own `HttpClient` boundary and requires the replayed turn in order (user, assistant text with `phase: "commentary"`, `function_call`, `function_call_output` with the same `call_id`, no other phase) and an accepted stream with one Done; `opencode.go.usage.snapshot` is the Go usage case below. Tests: `test/providers/opencode/go-conformance-cases.test.ts` (replay, ledger request claims, structural drills). `pnpm conformance:opencode` is a dry-run probe; live runs need `OPENCODE_API_KEY`, `--owner-approved`, `--account`, and real Go model ids for every protocol (`--chat-model`, `--messages-model`, `--responses-model`), are refused whenever `CI` is non-empty, and use the same fail-closed redaction (`scripts/fixture-probe-internal.ts`) and replay-verified write gate.
- Subscription-usage cases share one shape (private `providers/openai/conformance/subscription-usage-cases-internal.ts`): `anthropic.claude.usage.snapshot` (`providers/anthropic/conformance`, `AnthropicClaudeUsageConformanceConfig`), `openai.codex.usage.snapshot` (`providers/openai/conformance`, `OpenAiCodexUsageConformanceConfig`, token with `accountId`), `xai.grok.usage.snapshot` (`providers/xai/conformance`, `XAiGrokUsageConformanceConfig` with the real `xAiUserId` and truthful `clientVersion`), and `opencode.go.usage.snapshot`, each exported apart from the model-route case arrays (`*UsageConformanceCases` / `*UsageConformanceFixtures`). Each calls the public fetcher at its default URL and requires the vendor provider id, at least one window with distinct known ids in vendor order, and, from the raw body read at its own `HttpClient` boundary by a case-local reader, one window per wire window with a valid percentage with the same id, percentage, and reset instant (none fabricated, none dropped). Tests: `test/providers/subscription-usage-conformance-cases.test.ts` (replay, ledger request claims, structural drills, and tampered-snapshot drills). `pnpm conformance:usage --family claude|codex|grok` is a dry-run probe (live: `ANTHROPIC_CLAUDE_ACCESS_TOKEN`; `OPENAI_CODEX_ACCESS_TOKEN` + `OPENAI_CODEX_ACCOUNT_ID`; `XAI_GROK_ACCESS_TOKEN` + `XAI_GROK_USER_ID` + `--client-version`; owner approval, never in CI, account identifiers redacted fail-closed); Go usage is recorded by `pnpm conformance:opencode`.
- `@yolk-sdk/agent/classification` is the provider-neutral classifier model contract (`docs/adr/0003-classifier-models.md`): Effect Schemas for questions (`boolean`, `choice` with 2-255 options, `score` with 2-10 levels), answers, `ClassificationRequest` (`state` is a string, JSON object, or JSON array; an array is one state), `ClassificationResult`, usage, the `ClassifierModel` service, the typed `classify` helper (a choice answer's `choice` is the union of its option keys), and typed errors. It never imports Node, React, or provider code (boundary-enforced, relative paths included). Every answer is checked against its question through the shared `decodeClassifierAnswers` (missing, unexpected, type mismatch, non-finite or out-of-range probability/confidence, unknown choice: typed `ClassificationResponseInvalid` keeping the billed `usage`); probabilities are kept as returned, never renormalized. Use "classifier" names everywhere; "evaluation" is only the AI Gateway wire name. Classification is a read; host policy owns authorization.
- `providers/vercel/ai-gateway-classifier` calls AI Gateway `POST {baseUrl}/v1/evaluate` (default `https://ai-gateway.vercel.sh`, model `typesafe-ai/jev`) with the shared Gateway credential config (`ai-gateway-credential-internal.ts`: `AI_GATEWAY_API_KEY`, else `VERCEL_OIDC_TOKEN`, redacted). It passes `providerOptions` through unchanged, maps `providerMetadata.gateway.cost` (decimal US dollars) to `usage.costUsd`, keeps `x-ai-gateway-evaluation-fallback-*` headers in `providerMetadata.evaluationFallbackHeaders`, and reads `choice`/`score` confidence from the answer or, when absent there, `providerMetadata.typesafe.confidence[questionId]` (the live Gateway sends both; confirmed 2026-10-02). Non-2xx answers become `ClassificationProviderError` with a status-only message, classified from the status and the Gateway `error_type` (or OpenAI-style `error.type`/`error.code`); never copy body text or credentials into errors. It retries 408, 429, 5xx, and transport failures (no status, kind `network`) up to `maxRetries` (config, default 2) through an Effect `Schedule` with full-jitter exponential backoff (base 250 ms, cap 4 s, `Random`) or `Retry-After`/`retry-after-ms` capped at 10 s (HTTP dates read against `Clock`, passed as `nowMs` to `classifyProviderFailure`); never other 4xx or `ClassificationResponseInvalid` (decode failures). The final error is the last attempt's, unchanged. Chat providers leave retries to the loop; the classifier owns them because it has no loop. Tests drive delays with `TestClock` (`it.effect`), so tests of failing statuses set `maxRetries: 0` or advance the clock.
- `providers/vercel/conformance` also exports four classifier `read` cases (`vercel-ai-gateway.classify.{boolean,choice,score,error-envelope}`, config `VercelAiGatewayClassifierConformanceConfig`) and their synthetic unverified fixtures, apart from the chat arrays (`vercelAiGatewayClassifierConformanceCases` / `vercelAiGatewayClassifierConformanceFixtures`), so the verified chat suite and `pnpm conformance:gateway` are unchanged. No case is observed live yet; the live probe that would record them is not wired. Claims must hold live (score claims a value in the zero-based level range; live scores are probability-weighted and may be fractional). Tests: `test/providers/vercel/ai-gateway-classifier-conformance-cases.test.ts` (replay, ledger request claims, drills).
- Subscription-usage adapters expose best-effort snapshots from private provider endpoints. Each fetcher defaults to its exported URL constant and accepts an optional `url` override for trusted proxies or local emulators only (the credential is sent there). They accept fresh host-owned credentials (`OAuthAccessToken` for Claude/Codex/Grok, a redacted API key for OpenCode Go) and an Effect `HttpClient`, force manual Fetch redirect handling, and reject non-2xx redirects; hosts own polling, persistence, stale-data rules, labels, alerts, billing interpretation, and UI. Grok usage additionally requires the actual authenticated xAI `user_id` and a truthful host client version as explicit options; never infer `x-userid` from generic `OAuthAccessToken.accountId` or impersonate an official Grok version.
- Client depends on protocol + Effect HTTP/Stream. HTTP helpers are runtime-portable; attachment helpers require `Blob`/`File` and may use `FileReader`, while Cloudflare WebSocket transport constructs the global `WebSocket` when its stream runs. Browser globals are never read at import time.
- `makeWebSocketVoiceTransport` needs a host `Socket.WebSocketConstructor` layer.
- `voice/browser` is the only WebRTC-using area; it accesses browser globals lazily at transport creation, never at import time, and exposes a `WebRtcVoiceRuntime` seam for fakes. Client attachment/WebSocket helpers also use browser APIs as described above.
- Voice tools execute server-side only: the client `makeVoiceController` forwards provider tool calls to a host endpoint (`VoiceSessionToolCallRequest` in, `VoiceToolCallOutcome` out); `handleVoiceToolCall` applies `ToolDef.approval` policy before the executor and never runs approval-gated tools without a matching approved response.
- Voice HITL supports tool approval only in v1; question, generalized input, and action-backed interaction tools are denied, and `submitHitlResponse` ignores all three response types.
- If a voice session ends while awaiting approval, the approval stays pending host-side and the event stream completes; durable resume is host/session-log policy.
- One-shot speech contracts live in voice: `VoiceSpeechSynthesizer`, `VoiceTranscriber`, `VoiceSpeechRequest`, and `speechResultToAudioPart`. `VoiceSpeechRequest.instructions` is delivery-style steering only (tone, pacing), not model-visible content instructions.
- `providers/openai/speech` is host/server integration: it requires runtime `FormData`/`Blob`, an
  Effect `HttpClient`, and a secret API key. Do not invoke it directly from browsers.
- `projectVoiceEvent` keeps assistant drafts per segment key (`itemId`, falling back to `responseId`): a delta for a new segment flushes the previous draft, and finals for already-flushed keys project nothing. Providers emit transcript finals per output item, duplicate final event families, and back-to-back responses; response-level keying wipes later items of the same response, key-less/global drafts concatenate or duplicate.
- `voiceSeedTextsFromMessages` seeds visible text only; pass `{ includeAuthors: true }` to prefix user seeds with author display names for multi-user transcripts (assistant seeds never carry names).
- Segment finals with empty transcripts keep the streamed draft text (truncated/interrupted segments must never lose text the user already heard).
- Voice session logs are host-persisted: `VoiceSessionLogState` is the versioned serializable fold state and `foldStoredVoiceEvents` is the pure, replay-safe batch fold; hosts run it inside their storage transaction and append the returned messages. Bump `VOICE_SESSION_LOG_STATE_VERSION` on breaking state-shape changes.
- Tool lifecycle events use deterministic per-call ids (`voiceToolEventId`); `storedVoiceToolEvents` splits requested batches per call and `storedToolEventsFromOutcome` lets tool endpoints log server-witnessed activity that dedupes against client outbox replays.
- `makeVoiceEventOutbox` (and the `useYolkVoice` `eventLog` option) is client transport mechanics only: at-least-once batching with boundary flushes and a scope-close drain; hosts own the flush endpoint, auth, and storage, and should flush with keepalive-capable transport.
- `@yolk-sdk/agent/tools` owns the domain-free `subagent` tool contract for subagents; host apps provide subagent execution, available model/reasoning choices, prompts, provider layers, and tool policy. Optional subagent runtime selections inherit host settings when omitted.
- `@yolk-sdk/agent/tools` owns the domain-free `question` HITL tool contract; loop intercepts enabled questions before executor dispatch. If omitted from `tools`, even provider-emitted/replayed questions return unavailable results without HITL or executor dispatch.
- `@yolk-sdk/agent/tools` exposes `makeTool` for Effect-Schema-backed registrations; avoid hand-written JSON Schema when validation schema can be the source of truth.
- Model-produced tool/interaction/input call arguments decode through `Schema.toCodecJson(schema)` (`tools/arguments.ts` `decodeToolArguments`; the loop `question` decode uses the codec directly because loop cannot import tools), matching the advertised `ToolDef.parameters`, with `onExcessProperty: 'error'` because objects are advertised closed (never silently strip a key the model believes it set); non-finite decoded numbers are validation errors. `resolveTools` is the single boundary that drops `null` only on declared optional properties whose own schema rejects `null` (`omitNullOptionalToolArguments`; never undeclared keys, so it cannot lose meaning) for every registration, including raw/MCP, background business calls, and interaction/input `validateCall`; receipts and approvals keep the original call. User responses, results, and persistence keep their own decoders. See `patterns/AI_TOOL_SCHEMAS.md#tool-arguments`.
- Argument validation errors are model-facing: append `withToolArgumentsErrorHint` (`protocol/tool-argument-hints.ts`, re-exported from `@yolk-sdk/agent/tools`) so unknown keys are named with the allowed keys; the loop uses it for `question` and interaction/input call errors.
- `ModelVisibleToolError` is for recoverable, model-visible tool failures; `makeTool` returns `ToolResult.isError` with structured `{ type, tool, reason, message, details? }` content.
- `makeInputTool` owns original call/response schema validation; hosts pass `ResolvedToolSet.inputs` into loop/runtime configs alongside serializable `ToolDef.input` metadata. Inputs collect JSON data, never authorize actions or directly execute. Missing handlers and approval/background combinations fail closed. Keep the first valid submission/cancellation on replay while allowing corrections after invalid attempts.
- `makeInteractionTool` is opt-in action-backed HITL, not an input or permission. Hosts authenticate and atomically accept one immutable slot across all actions/cancellation in the active session/run/generation before SDK execution. Pass both `ResolvedToolSet.interactions` and `interactionHost` to loop/runtime configs; direct durable preflight first loads `loadInteractionReceipts` and supplies `interactionReceipts`. `prepareToolBatch` never reads storage or dispatches. `claim(ref)` only advances existing accepted records; neither raw responses nor IDs/brands grant authority. Replay settled receipts before current schemas/actions; missing handlers cannot start work. JSON-changing transforms/defaults are unsupported. Escaped post-dispatch errors are unknown, not definite failure; preserve defects/interruption and never take over started slots. `InteractionSubmitted` stays active and local submit must not synthesize acceptance. See `patterns/AGENT_HITL.md` and the generic fake host in `test/tools/interaction-host.ts`.
- Tool approval is host-enforced policy on normal tools, not a model-callable permission tool; v1 approvals are per-call, no persistent allow-always rules.
- Use `EmptyToolParams` for no-arg `makeTool` tools instead of `Schema.Struct({})` when author intent is no parameters.
- v1 subagents may use normal tools but must not receive the `subagent` tool recursively unless a future explicit capability enables it.
- The `subagent` registration is `access: 'read'`, but `defaultToolLedgerPolicy` ledgers it by name: a re-executed step would otherwise re-run the whole child run, whose tool calls get fresh ids (fresh ledger keys). `makeSubagentToolRegistration` forwards `idempotencyKey` to `SubagentExecutionInput`. Hosts with their own delegation tools must add them through `isLedgered`.
- Protocol owns `SubagentStarted`/`SubagentCompleted` and `makeSubagentRunId`; loop emits lifecycle events around `subagent` calls while preserving generic tool lifecycle as the source of truth.

## Protocol/loop rules

- `AgentReasoningEffort` is protocol-only request config; app/provider layers choose and pass through values.
- Anthropic Claude lowers `low`, `medium`, `high`, and `xhigh` reasoning efforts to `output_config.effort`; omit `minimal` and an absent effort because Anthropic does not support that value and must not receive an empty output config.
- Anthropic tool schemas require a provider compatibility projection because Claude subscription OAuth rejects valid JSON Schema constructs that Effect Schema can emit, including `anyOf`, `oneOf`, `allOf`, and tuple-only `prefixItems`. The projection is model guidance only: preserve the original Effect Schema as the execution validator, recursively remove unsupported constructs only in schema positions, keep literal data (`enum`, `const`, defaults, examples) opaque, and widen unrepresentable constraints rather than narrowing the set of originally valid calls. See `patterns/AI_TOOL_SCHEMAS.md`.
- `AgentMessage` envelope fields are optional and model-visible: `createdAtMs`, `author.displayName`, and JSON `annotations`; preserve them through protocol round-trips.
- Provider lowering renders message envelopes via `messageContextText` + `prependMessageContextToContent`; annotations are context only, not instructions.
- `Content = string | ContentPart[]`; parts include text, image, document, and audio. Media parts carry `InlineBase64`, `Url`, or host-owned `Ref` sources. Use protocol helpers (non-exhaustive: source factories, text/preview/parts, emptiness/append, hydration, document inference, attachment accessors) instead of app-local duplication.
- `resolveMessageAttachmentSources` / `resolveMessagesAttachmentSources` reuse content resolution across user, assistant text, nested provider tool results, and host tool results; opaque tool/provider payloads stay untouched. Resolution does not add vendor media capabilities. For fresh signing, hosts put resolution inside overflow retry (retry → resolve → transport), not solely in a `ContextTransformer`; compaction and durable history keep refs.
- OpenAI Codex lowering preserves text, image, and document `ToolResultMessage` content as native function output blocks. Anthropic Claude preserves text, images, inline text documents, and URL/base64 PDFs as nested tool-result blocks. Audio and unresolved `Ref` sources remain unsupported.
- Keep semantic `ImagePart`/`DocumentPart`/`AudioPart` over generic file parts; capability checks, provider lowering, validation, and UI rendering branch by media kind. Add generic file content only when arbitrary non-media files become first-class.
- `AgentModelCapabilities` is protocol-only; app/provider config chooses input media support, and loop rejects unsupported input before provider calls.
- Loop stays stateless: no persistence, sessions, WebSockets/SSE, compaction policy, app context, or provider SDKs.
- Loop composition is four Layers (`LLMProvider`, `ToolExecutor`, `ContextTransformer`, `LoopConfig`) plus `run` / `runModelTurn` / `runToolBatch`. Interception is decorating a service (`decorateLLMProvider`), not hooks. Durable hosts fold model-turn streams with `collectModelTurn`. Partial-failure collection (output-started, retained deltas, sink vs stream errors) is `collectModelTurnAttempt`; `collectModelTurn` remains the success-only wrapper.
- Model-produced text is untrusted input: `replaceLoneSurrogates` / `replaceLoneSurrogatesDeep` in protocol harden lone UTF-16 surrogates (unencodable UTF-8); provider request lowering and the realtime client codec apply them to outbound payloads. Storage-specific constraints (e.g. Postgres rejecting NUL) remain host sanitization policy.
- Provider adapters classify retryable failures, attach safe provider metadata, and normalize raw
  usage. Rebuild `LLMError` with explicit fields, not object spread: native Error's `cause` is non-enumerable on Effect 4, so `{ ...error }` silently loses the required typed cause and defects during Schema construction. `LLMUsage` events are additive deltas; convert vendor cumulative snapshots before emitting.
  Loop owns retry/usage aggregation. Optional `LLMError.responseIssue` is kernel-only: `missing_done` is set solely when a provider stream ends with zero `Done` events. It stays `invalid_response` / `retryable: false`. Multiple `Done`, mismatched `Done`, content-filter, length, and max_tokens terminals must not set it.
- Provider subscription usage is distinct from protocol `AgentUsage`: it reports consumer subscription allowance percentages and reset windows, not per-request token counts. Keep provider labels and alert eligibility in the host.
- Anthropic prompt-too-long signals normalize to non-retryable `context_overflow`; generic loop retry must not retry them. `makeContextOverflowRetryProvider` is the explicit exception and may compact and retry once per provider stream, only before published output. Shared overflow primitives (`applyOverflowCompaction`, `overflowCompactionMayRun`) do not persist transformer checkpoints. Durable persist-then-retry is a host/harness step; do not treat the silent in-process retry as that step.
- Anthropic `stop_reason: "max_tokens"` is a non-retryable `invalid_response` in JSON and SSE responses; never emit `LLMDone` or report normal completion for a truncated turn.
- OpenAI-compatible JSON Chat Completions, including Vercel AI Gateway, treat `finish_reason: "length"` and `"content_filter"` as non-retryable `invalid_response`; never report truncated or filtered output as normal completion.
- OpenAI-compatible chat, Vercel AI Gateway, Anthropic, and Grok providers require host-owned output-token limits; never infer model limits or add hidden fallbacks. ChatGPT subscription Codex does not expose or send an output-token limit because its endpoint rejects the vendor `max_output_tokens` field; the optional deprecated `maxOutputTokens` config field is ignored for compatibility.
- Vercel AI Gateway defaults to JSON Chat Completions; factory `streaming: true` opts into SSE and `reasoningContent: true` preserves compatible reasoning output and assistant replay (which spends input tokens). Both default to false. It uses the endpoint at `https://ai-gateway.vercel.sh/v1/chat/completions` and lowers the host limit to Gateway `max_tokens`. It forwards request `reasoningEffort` as `{ reasoning: { effort } }` by default; `reasoningEffortFormat: 'reasoning-effort'` sends the literal field instead (e.g. for DeepSeek-style hosts, with an optional `thinking` toggle merged into the request body). Hosts must offer only efforts supported by the selected model. Model ids remain opaque `provider/model` strings; optional fallback models and provider routing are host policy. Routing is emitted under `providerOptions.gateway`, with official `sort` literals `cost`, `ttft`, and `tps`. Authentication accepts an AI Gateway API key or Vercel OIDC token as Bearer auth, required auth/content-negotiation headers override extras, and custom endpoint URLs are trusted credential-bearing proxies.
- OpenAI-compatible native PDF lowering covers user-message PDF parts and tool-result PDF attachments (lowered to labeled supplementary user content after the complete tool-result block, never between assistant tool calls and sibling results). Tool-result images and readable text documents use that same supplementary-user lowering. Other document formats, audio, and unresolved references fail before any network call. Generic chat opts in with `supportsPdfAttachments`; Gateway defaults it on and can disable it. URL-backed PDFs are fetched and buffered by the host-provided `HttpClient`, not by Gateway. Hosts authorize destinations and redirects, enforce streamed limits/timeouts, keep provider credentials off attachment requests, and sanitize logs; validated inline bytes avoid this transport boundary.
- The Grok subscription provider defaults to the fixed xAI CLI proxy, not the developer API-key origin. Every request sends Bearer auth, `X-XAI-Token-Auth: xai-grok-cli`, the selected model in `x-grok-model-override`, and the required host-owned `clientVersion` in `x-grok-client-version` because the proxy version-gates requests with HTTP 426; custom response URLs are trusted-proxy configuration because they receive the bearer.
- OpenCode Go exposes `providers/opencode/go-provider` with explicit host-selected `chat-completions`, `messages`, or `responses` protocol, opaque unprefixed API model IDs, redacted API key, and required positive `maxOutputTokens`. Default base is `https://opencode.ai/zen/go/v1`; custom bases are trusted credential-bearing proxies. Chat uses JSON `max_tokens`/`reasoning_effort` and preserves provider `reasoning_content`; Messages uses native system/tool names and `x-api-key`, without Claude OAuth fingerprints; Responses uses Bearer auth and `max_output_tokens`. Responses parsing preserves output-item order for JSON fallback and completion-only SSE as well as streamed deltas; item text takes precedence over aggregate `output_text` when present. Responses replay preserves ordered text/`function_call` segments and tags only assistant text that precedes a later host `function_call` with `phase: commentary`; trailing and final-answer text omit phase. Required headers override case-insensitive extras. Go sanitizes streamed provider error text, and Messages/Responses require terminal events. JSON fallback requires a non-empty Messages `stop_reason` or Responses `status: completed`; incomplete JSON must not emit `Done`. Subscription-provider JSON compatibility remains unchanged.
- Go usage (`providers/opencode/usage`) uses `GET https://opencode.ai/zen/go/v1/usage` by default (optional trusted `url` override) with Bearer API key, not console cookies/OAuth. Normalize `usage.rolling/weekly/monthly` `{ percent, resetsAt }` to `five-hour`/`seven-day`/`monthly`; trust provider reset instants, never infer calendar-month boundaries or fill missing windows with zero. The local reference checkout may lack this route: verified upstream implementation is `anomalyco/opencode` commit `9f8db119fcbd4999379129ac7734375ac23460fb`, `packages/console/app/src/routes/zen/go/v1/usage.ts`.
- Claude and native Go Messages share lowering/parser mechanics in `src/providers/anthropic-provider-internal.ts`; Claude's public wrapper preserves its existing typed API and default compatibility behavior. Native Messages disables OAuth system relocation, tool-name rewriting, and Claude-only schema projection. Messages `content_filter`, like `max_tokens`, is non-retryable `invalid_response`; frames after `message_stop` are ignored before JSON decoding. Claude keeps EOF-completion compatibility (a stream ending without `message_stop` completes; tracked in #120), while native Messages requires the terminal event; do not change either without a changeset.
- Codex, Grok, and Go share the private OpenAI Responses lowering/stream parser in `src/providers/openai-responses-provider-internal.ts`; public vendor wrappers supply their own endpoint, required auth headers, output-limit policy, provider id, and display name, and own vendor-named request/reasoning types so generated declarations never reference the private module. Commentary-phase tagging is opt-in on that private helper and enabled only for Go Responses, which preserve ordered text/`function_call` segments; Codex and Grok keep flattened untagged assistant messages.
- The shared Responses SSE parser treats the first `response.completed` as terminal and ignores later frames. Grok requires an explicit terminal event; Codex retains EOF-completion compatibility.
- Compaction is host-owned through `ContextTransformer`. Persist the raw transcript and host-owned compaction payload, not the synthetic `UserMessage` returned by `makeCompactionCheckpointMessage`; use `compactionSummarySourceMessages` to exclude the previous leading checkpoint when summarizing again.
- `@yolk-sdk/agent/compaction` provides pure planning/estimation, checkpoint formatting, ordered rich transcript formatting, and per-stream one-shot context-overflow retry helpers; hosts own thresholds, summary wording, LLM summarization, durable storage, and active-run guards.
- Built-in token estimates are provider-neutral heuristics. `countTextTokens` improves selected message text/reasoning/host-call estimates only; exact provider-request accounting must also include non-message input and vendor framing. Hosts may inject a whole-transcript `estimateTokens`, reuse one estimator across warnings/planning/before-after checks, and keep tokenizer dependencies outside the package.
- Only preserve provider-supplied reasoning summaries (`LLMReasoningDelta` / assistant reasoning parts); never fabricate reasoning.
- Durable replay may use `LLMTextDelta.textSoFar` / `LLMReasoningDelta.reasoningSoFar`; chat projection prefers snapshots and de-dupes by `eventId`.
- `UserMessageEvent` is the replay-safe durable-stream projection for host-promoted user input. Hosts own queue/promotion policy and must supply a stable `eventId`.
- `accumulateAssistantMessage` preserves ordered assistant parts: text, reasoning, host tool calls, provider tool calls/results.
- Same-turn sibling tool calls are native parallelism: providers emit normal tool calls, loop runs them concurrently within `toolConcurrency`, and dependent work waits for the next model turn.
- OpenAI Codex streaming preserves every sibling function call and deduplicates `response.completed` replays by call id before parsing replayed arguments; a malformed replay of an already-emitted call must not invalidate unseen sibling calls.
- Tool executor `ToolError`s are model-visible failed tool results, not stream failures; every host tool call must have a matching `ToolResultMessage` before the next provider request.
- Use `validateNoDanglingHostToolCalls` before provider lowering and `repairDanglingHostToolCalls` only for persisted/replayed transcripts that already have gaps.
- HITL semantics live in `patterns/AGENT_HITL.md`: approvals/questions/typed inputs pause with `AgentAwaitingInput`; responses resume through `hitlResponses`/typed client inputs.
- Question resume content must be model-visible text with selected answer labels plus structured answers; never replay only `answered`.
- React input submission stays pending until server acceptance: never synthesize replayable input results optimistically. Replay `AgentAwaitingInput.requests` into pending tool states, including when no separate request event was observed.
- Use SDK HITL helpers for durable apps: `plainHitlResponse`, `questionResponseStructuredContent`, `hitlResponseEvent`, and `toolRunsFromHitlRequests`.
- Client HTTP transport treats `AgentEnd`/`AgentError`/`AgentAwaitingInput` as logical end, but only pre-terminal consumer cancellation should abort the body.
- HTTP callback producers forward failed exits to their output queues with the original Cause. Typed-only catches strand consumers when host callbacks or cleanup defect; preserve defects rather than wrapping them as recoverable transport errors.
- Use `isTerminalAgentEvent` as the canonical protocol helper for `AgentEnd`/`AgentError`/`AgentAwaitingInput` checks.
- Client durable-run helpers are transport-only: they follow NDJSON continuation chunks via run/tail headers, poll empty non-terminal chunks without advancing `startIndex`, require outbound `startIndex >= 0`, and do not own Workflow hook tokens, route auth, run ownership, or HITL request matching.

## Code mode tool contract

See `docs/adr/0002-code-mode.md`. `@yolk-sdk/agent` owns the contract only; it never imports code mode.

- `makeTool({ output })` lowers an Effect Schema into declaration-only `ToolDef.outputSchema` with the same lowering as `parameters`. It is never sent to providers and never validates results. Connector registrations pass action `outputSchema` through; MCP defs pass a plain-object MCP `outputSchema` through and omit anything else.
- A tool with `output` must return, on successful results, `structuredContent` that is the JSON encoding of it (`Schema.toCodecJson(output)`); `makeTool` never encodes or validates, so raw `Chunk`/`DateTime`/class values would reach code mode scripts as their raw JSON instead of the declared shape. Error results (`isError`) keep their own `structuredContent` (the `model_visible_tool_error` envelope, an encoded connector `ProviderFailure`); never force errors into the success schema.
- Exposure is `ToolDef.callableBy` (`all` default, `model`, `codemode`) plus `discovery` (`listed` default, `search`) only for `codemode`; `makeTool` options type it as the `ToolExposure` union. `isCodeModeCallable`, `isCodeModeFailClosed`, `providerToolDefs`, and `toolDiscovery` in protocol are the single source of the rules.
- Fail-closed set: `approval`, `input`, `interaction`, `execution: 'background-v1'`, and the `question`/`subagent` names never run from code mode; `all` on them behaves as `model`. `resolveTools` rejects `codemode` on them (also on activated background, registration-level approval, and nested-access registrations) with `codemode_unsupported_tool`, and `discovery` without `codemode` with `invalid_tool_exposure`. It logs a warning when codemode-only tools resolve without any nested-access registration.
- Codemode-only definitions stay in `ResolvedToolSet.tools`/`metadata` but never reach providers: the loop sends `providerToolDefs(config.tools)` (`run`, `runModelTurn`, capability checks) and realtime session builders filter the same way. Provider-issued calls fail closed as `Tool is not configured: <name>`: `prepareToolBatch` returns a synthetic error result without dispatch, `ResolvedToolSet.execute` fails `not_found`, and voice denies before approval. Hosts calling providers directly must use `providerToolDefs`.
- `nestedToolAccess: true` registrations receive `nested: NestedToolExecutor` in their execute input (raw and `makeTool`; wrappers must forward it). `nested.tools` lists code-mode-callable registrations except nested-access ones (no recursion) with their `moduleId`. `nested.execute` uses the same registration path as `ResolvedToolSet.execute` (decoding, resolution-time `isEnabled`, registration wrappers, same host context) and never fails: unknown/disabled tools become `not_found`, non-callable ones `unavailable` model-visible error results, and `ToolError`s become error results. Executor decorators outside the resolved set do not see nested calls. Callers assign nested ids as `<parentToolCallId>/<seq>`; each registration's `nested` is bound to its own call, so nested calls are ledgered with that call id as `parentKey`. An optional registration `describe({ tools })` hook (also a `makeTool` option) computes the resolved definition's description from `nested.tools` for nested-access registrations only (built with explicit field selection, never a spread `ToolDef`); the static `def.description` stays the fallback, and the hook is ignored without `nestedToolAccess`. `@yolk-sdk/codemode` uses it to list callable tools.
- `ToolResult.nestedCalls` (bounded `NestedToolCalls`) and summed `ToolResult.usage` are host/UI audit data, not model-visible: `toolResultMessageFromResult` drops them, so transcripts and providers never see them, and the loop does not add `usage` to run usage. Build them only with `recordNestedToolCall` + `nestedToolCallResultFields` over `makeNestedToolCallRecorder({ maxCalls })` (default `nestedToolCallMaxCalls` = 256; size it to the caller's own call limit), which enforce `maxCalls` calls, 8 KiB compact-JSON args per call, 32 KiB args total (cut args or dropped calls mark `complete: false`), and 500-character errors, and keep per-status `counts` over every call, dropped ones included (optional in the Schema for older records). Never pass extra arguments to the fold: it is used directly as an `Array.reduce` callback. Nested results are never stored.

## Durable tool ledger

- `@yolk-sdk/agent/tools` owns the ledger contract (`tools/ledger.ts`; ADR 0002 "Durable tool-call ledger"): `ToolLedgerStore` (host storage scoped by `scope`: atomic `claim` → `ToolLedgerClaim` `Fresh | Completed | InFlight | Abandoned`, `heartbeat`, `complete` once, `list(parentKey)`), the persisted `ToolLedgerEntry` Schema (outcome `ToolLedgerSucceeded` with a bounded wire-safe `ToolResult` from `toolLedgerResult`, or `ToolLedgerFailed` with `ToolError` fields only), `classifyToolLedgerEntry` for host `claim` implementations, and the reference `makeInMemoryToolLedgerStore` (not durable).
- It is an explicit `resolveTools(..., { ledger })` option, like `interactionHost`, not an Effect service: it is resolution-scoped (one step/run scope) and keeps `ResolvedToolSet.execute` free of requirements. Absent means unchanged behavior; never add an implicit in-memory fallback.
- The only seam is `executeRegistration` in `registry.ts`, shared by `ResolvedToolSet.execute` and every `nested.execute`; never add a second dispatch path that skips it. Interaction (receipt-backed) and input tools are not ledgered. Keys: `call.id`; nested `<parentCallId>/<seq>` with `parentKey`. Policy `isLedgered` defaults to `defaultToolLedgerPolicy` (access not `read`, plus the built-in `subagent` tool by name; hosts add custom delegation tools).
- Semantics: `Fresh` runs with a heartbeat fiber and completes with the outcome; `Completed` replays (stored `ToolError`s re-fail identically); `InFlight` polls `claim` on `Clock` until completed/abandoned or `maxWaitMs`/`deadline` (non-finite deadlines ignored), each poll bounded by the remaining wait (`timeoutOption`) and the last sleep shortened so one final poll runs within the wait, then returns a model-visible `timeout` result; `Abandoned` never re-runs and returns `abandonedToolCallResult` or the registration's `abandonedResult({ call, entry, nested })` (code mode uses it; `nested` is `undefined` when `list` fails, and must then be reported as unavailable, never empty). A different tool name or `argsDigest` under the same key is a model-visible conflict: `toolLedgerArgs` returns the 8 KiB `args` preview, `argsTruncated`, and `argsDigest` (lower-case hex SHA-256 of the UTF-8 canonical JSON of the raw `call.params`: compact, keys sorted by UTF-16 code units; a stable format hosts persist, so never change the canonical form); never compare the preview. `tools/sha256.ts` (`sha256HexSync`) is a synchronous runtime-neutral non-security fingerprint so `toolLedgerArgs` stays pure and synchronous with no failure path before `claim` and no async work hidden from `TestClock`; keep its FIPS/`node:crypto` tests. Claim failures, polls included, fail closed (`ToolError` `unavailable`); heartbeat/completion failures are logged and leave the entry claimed; each heartbeat and each `complete` attempt is bounded by `toolLedgerCompleteTimeoutMs` (completion inside the uninterruptible region). These timeouts only cut interruptible store work: the `ToolLedgerStore` contract requires interruptible operations, and docs must keep that condition wherever they call timings bounded. `deadline` bounds only the duplicate wait; completion can add about 15 s after it. The call runs under `uninterruptibleMask` with only `execute` restored, so every success or `ToolError` exit is recorded before an interruption takes effect (a `ToolError` also when its cause carries interruptions); defects, and interruption without a `ToolError`, never complete an entry (unknown outcome). The stored copy is built lazily and a defect while building or recording it is only logged, never masking the live result. `toolLedgerResult` measures the serialized UTF-8 JSON and reduces media, then `nestedCalls`, then `structuredContent`, then cuts text. Model-visible ledger results carry `structuredContent.details` `{ type: 'tool_ledger', state, key }`.
- Executors receive `idempotencyKey` (`toolIdempotencyKey(scope, key)`) whenever a ledger is configured, ledgered or not; `makeTool` and wrappers must forward it with `nested`.
- Clocks: `claim` (`ToolLedgerClaimRequest`) and `heartbeat` (`ToolLedgerHeartbeatRequest`) always carry both `leaseMs` (stores on their own clock, for example database `now()`) and the caller's `Clock` times `nowMs`/`leaseExpiresAtMs` (clock-agnostic stores, the in-memory one). Keep both; a store uses one clock for every lease.
- `onLedgerDecision` (`ToolLedgerDecisionEvent`) is called once per ledgered call, after any wait and before running or returning (`fresh`, `completed`, `in_flight_wait`, `in_flight_timeout`, `abandoned`, `conflict`; `waitedMs` when the first claim was in flight). It goes through `reportDecision`: never awaited, throws and rejected promises only logged. Not called when the claim fails.
- Bounded text (`utf8ByteLength`, `truncateUtf8`, `truncateCodePoints`, `compactToolArguments`, `boundNestedToolCallArgs`) lives in `protocol/bounded-text.ts` and `protocol/nested-tool-calls.ts`; the ledger (relative imports) and code mode reuse them, never local copies. `@yolk-sdk/agent/protocol` exports only what code mode imports (`truncateCodePoints`, `boundNestedToolCallArgs`, `nestedToolCallRecordLimit`, `makeNestedToolCallRecorder`); keep the byte-level helpers internal. `nestedToolCallRecordLimit` clamps every record's `maxCalls` to `nestedToolCallMaxRecordedCalls` (4096).
- Tests: `test/tools/ledger.test.ts` (TestClock for waits, leases, heartbeats, and decisions).

## Background tool calls

- `ToolDef`/`makeTool`/`ToolRegistration` `background: true` is an inert capability flag; `resolveTools(modules, context, { backgroundHost })` activates it. A `BackgroundToolHost` asserts a real lifecycle owner; never supply one from a request-scoped detached task.
- Activated definitions carry `execution: 'background-v1'` and a required `{ execution, arguments }` envelope built by `backgroundToolDef` (original schema under `arguments`, `$defs` at the root). Activated definitions are advertisements only; re-registering one fails with `background_definition_already_active`.
- Activation only supports document-root `#/$defs/...` pointers without percent-encoded fragments. Other `$ref` forms and resource/anchor keywords fail with `background_unsupported_schema`; traverse schema positions only, never business defaults/examples/const/enum data. Do not turn this narrow guard into a reference compiler.
- Activated definitions are unsupported in voice/realtime, including foreground envelope calls: synchronous realtime mappers throw `VoiceToolBridgeError`, while the `toOpenAiRealtimeToolEffect`, `makeOpenAiRealtimeSessionConfigEffect`, and `openAiRealtimeSessionConfigFromVoiceEffect` counterparts return it in the typed error channel (use these in Effect programs); voice decisions deny before approval matching (even replayed approvals), and the private fiber-local `VoiceToolDispatch` marker fences direct low-level bridge dispatch in the activated registry before validation/admission/inline effects. Do not expose the marker as public API or infer activation from business params. Resolve ordinary voice toolsets without a host.
- `executeBackgroundTool` decodes the protocol `BackgroundToolInput` envelope exactly, applies the registry's `businessCall` argument normalization, runs the registration `validate` (schema-only, no business effects), strips control fields, then executes inline or calls `host.accept` and returns `makeBackgroundToolAcceptedResult`. Raw registrations without `validate` fail closed (`background_validation_required`); `question`/`subagent` fail closed (`background_unsupported_tool`).
- `makeTool` invalid business arguments remain structured `model_visible_tool_error` results in both activated execution modes, with no business/admission effects. Envelope errors and raw-registration/host `ToolError`s retain their typed failure semantics.
- Use protocol `toolResultMessageFromResult(result, envelope?)` for receipt-preserving result-to-message conversion; it adds no implicit message context. Reverse projection must explicitly select result fields: `Schema.Class.make` retains excess own keys, so never pass a message instance directly to `ToolResult.make`.
- Loop emits `ToolExecutionAccepted` for results carrying `acceptance`; never `ToolExecutionCompleted`/`SubagentCompleted` and never usage. Client `AgentToolRun`, chat `ChatToolState`, and `ToolRunState` have a distinct `Accepted` tag that is inactive, non-error, and not completed. Preserve the whole accepted call across active and mixed assistant-message replays without dropping siblings or moving acknowledged calls into another message; retain acknowledged runs through turn cleanup. Both batch projection and the hook's `HydrateMessage` reducer must settle transcript receipts, with result message context kept separately in `Accepted.resultEnvelope` for round-trip serialization.
- Approval ids for activated calls are `approval:<callId>:background-v1:<canonical JSON of name/execution/arguments>`; legacy ids stay `approval:<callId>`. `prepareToolBatch` rejects malformed envelopes with a synthetic `isError` result before prompting or launching. IDs intentionally include the full canonical payload without truncation/hashing: hosts must accommodate these opaque, potentially long IDs or enforce input bounds before admission.
- Tests live in `test/tools/background.test.ts`, `test/loop/background-tools.test.ts`, `test/react/background-tools.test.ts`, `test/client/background-tools.test.ts`, and `test/voice/background-tools.test.ts`.
