A replayed request no longer reopens a settled call in the chat projections (#346). In `applyAgentEventToChatProjection`, the `useAgentChat` reducer and `applyAgentEventToChatMessages`, a `ToolApprovalRequested`, `QuestionRequested`, `InputRequested` or `InteractionRequested` event (or an `AgentAwaitingInput` request) that reached a call already answered, cancelled, denied or finished set it back to pending with an actionable card, for example a replay without event id landing on an earlier turn's call. Such a request now leaves the part as it is when it names the same call (id, name and arguments), with or without event id, and the `useAgentChat` reducer keeps its status when a replayed `AgentAwaitingInput` names only such calls (it no longer blocks the run with no card to answer). The loop asks for a call only until it has a result or used an answer, so a legitimate re-pend still shows: a running call has no result, so after an abort the next run that resumes it asks again and the card shows; an invalid input answer re-pends the same request while the part is still pending (the server emits `InputSubmitted` only for a valid payload and the chat never applies an input answer locally), a pending request is still replaced by a newer one (a recomputed approval preview), and a later turn reusing the call id asks on its own part. Hosts must not re-ask a call whose question answer or approval denial the client already applied locally: reject the response and keep the pause pending instead.
