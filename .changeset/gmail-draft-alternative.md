Stop Gmail web from hard-wrapping drafts at about 70 columns when a person opens one and clicks Send. `gmail.draft_compose`, `gmail.draft_update`, and `gmail.draft_reply` used to write a single unencoded `text/plain` part, which Gmail web opens in its plain-text composer. A plain-text body is now sent as 7-bit `multipart/alternative` with `MIME-Version: 1.0`: a text/plain part with the body (line breaks as CRLF) and a text/html part derived from it (HTML-escaped, `<br>` per line break, runs of spaces kept, `http(s)` URLs linked to themselves, inside one `<div dir="ltr">`), both `charset=UTF-8` quoted-printable with lines of at most 76 characters, under the constant boundary `=_yolk-draft-alternative`. Recipients see the HTML with paragraphs unwrapped; on send, Gmail web still regenerates the text/plain alternative and wraps it at about 76 columns. The three actions take an optional `contentType: 'text' | 'html'` (`text` when omitted, as on the Outlook draft actions; new export `GmailDraftContentType`); `html` sends the body as one quoted-printable text/html part. Their descriptions now tell the model to write each paragraph as one line. `gmail.get_thread` no longer applies a part's `Content-Transfer-Encoding` to `body.data` again (Gmail answers it already transfer-decoded), which corrupted quoted-printable text holding `=XX` (such as `?date=2026`) and dropped base64-encoded bodies. `gmail.send_message` is unchanged. The synthetic draft conformance fixture and `@yolk-sdk/emulators/google` follow the new draft MIME (the draft payload is `multipart/alternative`, its metadata `body.size` 0); the emulator answers only the recorded text drafts, so `contentType: 'html'` drafts are not emulated.
