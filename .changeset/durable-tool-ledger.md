Add a durable tool-call ledger: a re-executed step never runs a ledgered tool call (by default every non-`read` tool plus the built-in `subagent` tool) again under the same ledger key.

- `@yolk-sdk/agent/tools`: `resolveTools(modules, context, { ledger: { store } })` takes a host-implemented `ToolLedgerStore` (scoped by the host, for example the Workflow run id: atomic `claim` returning `ToolLedgerClaim` `Fresh | Completed | InFlight | Abandoned`, `heartbeat`, `complete`, `list(parentKey)`). Ledgered calls (`defaultToolLedgerPolicy`: every non-`read` tool plus the built-in `subagent` tool, whose child run would otherwise repeat its writes; override with `isLedgered`, and add custom delegation tools there) run at most once per key, top-level (`call.id`) and nested code mode calls (`<parentCallId>/<seq>`) alike, through the one registry seam both share. A fresh claim runs the call while heartbeating its lease and records the outcome; a completed one returns the stored result (or fails with the stored `ToolError`) without executing; an in-flight one waits until it completes or `maxWaitMs`/`deadline` passes, then returns a model-visible timeout result; an abandoned one (lease expired, no result) is never re-run and returns a model-visible result saying it may already have been applied. The same key holding a different tool name or arguments is a model-visible conflict, decided by `argsDigest` (SHA-256 of the full arguments' canonical JSON), never by the bounded preview. Claim failures, including polls while waiting, fail closed; each poll is bounded by the remaining wait. Each `complete` attempt is bounded (`toolLedgerCompleteTimeoutMs`, 5 s, three attempts); an outcome that cannot be recorded leaves the entry to read as abandoned. Every result or `ToolError` the call returns is recorded before an interruption takes effect (a `ToolError` also when its cause carries interruptions, for example of the tool's own sibling work); defects, and interruption without a `ToolError`, never record an outcome. Without `ledger`, behavior is unchanged.
- Stores choose one clock for leases: `claim` (`ToolLedgerClaimRequest`) and `heartbeat` (`ToolLedgerHeartbeatRequest`) receive the lease length `leaseMs`, for stores that use their own clock (for example a database `now()`, avoiding clock skew between instances), as well as the caller's `Clock` times `nowMs` and `leaseExpiresAtMs` for clock-agnostic stores.
- `onLedgerDecision({ key, parentKey?, toolName, decision, waitedMs? })` in the `ledger` options reports each ledgered call's decision (`ToolLedgerDecision`: `fresh`, `completed`, `in_flight_wait`, `in_flight_timeout`, `abandoned`, `conflict`) for logs and metrics, for example to prove replays happen. It never affects execution: throws and rejected promises are logged and ignored.
- Store contract: `ToolLedgerClaimRequest` and `ToolLedgerEntry` carry `args` (compact JSON preview cut to 8 KiB, audit only), `argsTruncated` (whether the preview was cut), and `argsDigest` (lower-case hex SHA-256 of the full arguments' canonical JSON). Host stores must persist all three on a fresh claim and return them on every entry; stores that persist the whole entry through `Schema.toCodecJson(ToolLedgerEntry)` get this automatically, column-based stores need two new columns. `toolLedgerArgs(params)` returns `{ args, argsTruncated, argsDigest }`.
- New exports: `ToolLedgerEntry` (persisted Schema; persist it with `Schema.toCodecJson`), `ToolLedgerOutcome`, `ToolLedgerSucceeded`, `ToolLedgerFailed`, `ToolLedgerFailure`, `ToolLedgerClaim`, `ToolLedgerError`, the `ToolLedgerClaimRequest`, `ToolLedgerHeartbeatRequest`, `ToolLedgerDecision`, and `ToolLedgerDecisionEvent` types, `classifyToolLedgerEntry`, `toolLedgerResult` (bounded, wire-safe stored results, default 1 MiB, measured on the serialized JSON; `nestedCalls` is dropped before `structuredContent`), `toolLedgerArgs`, the `ToolLedgerArgs` type, `toolLedgerCompleteTimeoutMs`, `sortToolLedgerEntries`, `makeInMemoryToolLedgerStore` (reference store, not durable), `toolIdempotencyKey`, `defaultToolLedgerPolicy`, `abandonedToolCallResult`, and the default timing constants.
- Tool executors receive `idempotencyKey` (`<scope>:<ledger key>`) in `ToolExecutionInput` whenever a ledger is configured; `makeTool` forwards it, and custom wrappers must forward it like `nested`. Registrations (and `makeTool`) accept `abandonedResult` to describe an abandoned call; its `nested` input is `undefined` when the store cannot list the nested entries (report them as unavailable, never as an empty list). `SubagentExecutionInput` gains `idempotencyKey`, forwarded by the built-in subagent registration.
- `@yolk-sdk/agent/protocol`: `NestedToolCalls` gains optional per-status `counts` (`NestedToolCallCounts`) covering every call, dropped ones included, and `makeNestedToolCallRecorder({ maxCalls })` sizes the record (default `nestedToolCallMaxCalls`, 256, clamped by `nestedToolCallRecordLimit` to at most `nestedToolCallMaxRecordedCalls`, 4096; byte budgets unchanged). The helpers code mode shares with nested-call records are exported: `truncateCodePoints` and `boundNestedToolCallArgs` (the per-call and total argument budgets); the byte-level helpers stay internal.
- `@yolk-sdk/codemode`: with a ledger, the `codemode` call itself is ledgered, so a re-executed call never re-runs its script: it returns the stored result, waits for the running execution, or, when the earlier execution was abandoned, returns an interrupted error result (`structuredContent.codemode.interrupted: true`) listing that script's ledgered nested calls as applied, failed, or unknown and stating they were not undone. The same entries reach hosts as `structuredContent.codemode.interruptedCalls` (`CodeModeInterruptedCalls`: `{ calls: [{ key, toolName, args, status }], complete, counts }`, plain JSON bounded like `nestedCalls`; `complete` is also false when the ledger already cut a call's arguments), so hosts can render them without reading the ledger. When the store cannot list them, the result stays interrupted, says they may already have been applied, and sets `interruptedCallsUnavailable: true` instead. The `nestedCalls` record is now sized from `limits.maxNestedCalls` instead of a fixed 256, so hosts allowing more calls (for example 768) no longer lose later calls from the record, and it carries per-status counts. New `afterNestedCall({ call, outcome, durationMs, context, result? })` hook reports `success`, `failure`, or `interrupted` for each admitted nested call; a failing hook is logged and never changes the call's result.
- `@yolk-sdk/vercel-workflows`: documents that tool-batch steps are at-least-once (redelivered after crashes and concurrently with a running execution, even with `noWorkflowStepRetry`) and that hosts must supply a durable ledger where their step resolves tools. No API change.

Host migration for stores written against earlier builds of this ledger:

- Persist `argsDigest` and `argsTruncated` from each fresh claim and return them on every `ToolLedgerEntry`; entries without them no longer decode. Never compare `args` for conflicts; the SDK compares `toolName` and `argsDigest`.
- `ToolLedgerAbandonedInput.nested` may be `undefined` (listing failed); custom `abandonedResult` hooks must handle it.
- The default policy now ledgers `subagent` calls. Hosts with their own delegation tools add them through `isLedgered`, for example `input => defaultToolLedgerPolicy(input) || input.call.name === 'delegate'`.
