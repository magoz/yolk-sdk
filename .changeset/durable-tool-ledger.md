Add a durable tool-call ledger so re-executed steps never repeat tool writes.

- `@yolk-sdk/agent/tools`: `resolveTools(modules, context, { ledger: { store } })` takes a host-implemented `ToolLedgerStore` (scoped by the host, for example the Workflow run id: atomic `claim` returning `ToolLedgerClaim` `Fresh | Completed | InFlight | Abandoned`, `heartbeat`, `complete`, `list(parentKey)`). Ledgered calls (default every non-`read` tool, override with `isLedgered`) run at most once per key, top-level (`call.id`) and nested code mode calls (`<parentCallId>/<seq>`) alike, through the one registry seam both share. A fresh claim runs the call while heartbeating its lease and records the outcome; a completed one returns the stored result (or fails with the stored `ToolError`) without executing; an in-flight one waits until it completes or `maxWaitMs`/`deadline` passes, then returns a model-visible timeout result; an abandoned one (lease expired, no result) is never re-run and returns a model-visible result saying it may already have been applied. Claim failures fail closed. Without `ledger`, behavior is unchanged.
- Stores choose one clock for leases: `claim` (`ToolLedgerClaimRequest`) and `heartbeat` (`ToolLedgerHeartbeatRequest`) receive the lease length `leaseMs`, for stores that use their own clock (for example a database `now()`, avoiding clock skew between instances), as well as the caller's `Clock` times `nowMs` and `leaseExpiresAtMs` for clock-agnostic stores.
- `onLedgerDecision({ key, parentKey?, toolName, decision, waitedMs? })` in the `ledger` options reports each ledgered call's decision (`ToolLedgerDecision`: `fresh`, `completed`, `in_flight_wait`, `in_flight_timeout`, `abandoned`, `conflict`) for logs and metrics, for example to prove replays happen. It never affects execution: throws and rejected promises are logged and ignored.
- New exports: `ToolLedgerEntry` (persisted Schema; persist it with `Schema.toCodecJson`), `ToolLedgerOutcome`, `ToolLedgerSucceeded`, `ToolLedgerFailed`, `ToolLedgerFailure`, `ToolLedgerClaim`, `ToolLedgerError`, the `ToolLedgerClaimRequest`, `ToolLedgerHeartbeatRequest`, `ToolLedgerDecision`, and `ToolLedgerDecisionEvent` types, `classifyToolLedgerEntry`, `toolLedgerResult` (bounded, wire-safe stored results, default 1 MiB), `toolLedgerArgs`, `sortToolLedgerEntries`, `makeInMemoryToolLedgerStore` (reference store, not durable), `toolIdempotencyKey`, `defaultToolLedgerPolicy`, `abandonedToolCallResult`, and the default timing constants.
- Tool executors receive `idempotencyKey` (`<scope>:<ledger key>`) in `ToolExecutionInput` whenever a ledger is configured; `makeTool` forwards it, and custom wrappers must forward it like `nested`. Registrations (and `makeTool`) accept `abandonedResult` to describe an abandoned call.
- `@yolk-sdk/agent/protocol`: `NestedToolCalls` gains optional per-status `counts` (`NestedToolCallCounts`) covering every call, dropped ones included, and `makeNestedToolCallRecorder({ maxCalls })` sizes the record (default `nestedToolCallMaxCalls`, 256; byte budgets unchanged).
- `@yolk-sdk/codemode`: with a ledger, the `codemode` call itself is ledgered, so a re-executed call never re-runs its script: it returns the stored result, waits for the running execution, or, when the earlier execution was abandoned, returns an interrupted error result (`structuredContent.codemode.interrupted: true`) listing that script's ledgered nested calls as applied, failed, or unknown and stating they were not undone. The same entries reach hosts as `structuredContent.codemode.interruptedCalls` (`CodeModeInterruptedCalls`: `{ calls: [{ key, toolName, args, status }], complete, counts }`, plain JSON bounded like `nestedCalls`), so hosts can render them without reading the ledger. The `nestedCalls` record is now sized from `limits.maxNestedCalls` instead of a fixed 256, so hosts allowing more calls (for example 768) no longer lose later calls from the record, and it carries per-status counts. New `afterNestedCall({ call, outcome, durationMs, context, result? })` hook reports `success`, `failure`, or `interrupted` for each admitted nested call.
- `@yolk-sdk/vercel-workflows`: documents that tool-batch steps are at-least-once (redelivered after crashes and concurrently with a running execution, even with `noWorkflowStepRetry`) and that hosts must supply a durable ledger where their step resolves tools. No API change.
