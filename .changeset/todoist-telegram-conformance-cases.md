Add the experimental `@yolk-sdk/connectors/todoist/conformance` and `@yolk-sdk/connectors/telegram/conformance` subpaths. Todoist: seven cases (filtered task list cursor paging, the HTTP 404 error body, task labels as label names, the create/get/update/close task lifecycle, `due_date` / `due_datetime` due shapes, project `parent_id`, and project delete then not-found) with `TodoistConformanceConfig` seed ids. Write cases work only inside an invocation-unique `yolk-conformance-<runId>-<case>` project under `workProjectId` (the live runner generates a fresh run id each time): a definitive create rejection deletes nothing, an ambiguous create is reported with the exact project or task to check by hand, successful creates are deleted by id and verified, and a project without the requested name or a task outside the case project is never deleted. `findTodoistConformanceLeftovers` lists leftover `yolk-conformance-run-*` projects read-only. Telegram: four cases (`telegram.validate` as one `getChat`, the `{ ok: false, error_code, description }` envelope on a 4xx status, `getFile` for `downloadTelegramFile`, and `telegram.send_message`) with `TelegramConformanceConfig` seeds; the connector reads only HTTP statuses, so body claims are observed at the ports. The send case is write-irreversible (a sent message cannot be deleted through the connector) and runs only when requested by its exact id; an ambiguous send is reported with the text to look for in the chat. Both ship synthetic replay fixtures (Telegram URLs carry the synthetic `telegramConformanceReplayBotToken`); no case is observed live yet.
