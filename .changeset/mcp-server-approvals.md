`makeMcpToolServer` can ask the user before a tool runs, through MCP form elicitation over multi round-trip requests (`2026-07-28`). A tool with an `approval` policy (`McpServerApprovalTool`; `McpServerTool` is now `McpServerDirectTool | McpServerApprovalTool`) answers its first call with an `input_required` result: one form elicitation under `approvalInputKey` (`'approval'`, one required approve/deny choice, the policy's `message`) and a `requestState` signed with the SDK's `createRequestStateCodec`, bound to the server's `name`, the new `approvals.principal` and the method, and expiring after `approvals.ttlSeconds` (default 600). Only a retry that accepts a state verified for the same principal, tool and arguments runs `execute(call, { approvalId })`; a decline or a cancel answers an error result, and a state that does not verify, belongs to another call, or comes without a decision asks again. The server keeps no state, so hosts key once-only execution on `approvalId`. Approval tools are offered only on `2026-07-28` requests and only with `approvals` (`key`: at least 32 bytes, the same on every instance); a request that does not declare form elicitation gets a tool error result (not `-32021`), and unusable `approvals` (a short key, an empty principal, a `ttlSeconds` that is not a positive integer) leave approval tools listed but answering an error result that names the problem. Tools may also carry `annotations` (`McpServerToolAnnotations`: `title` and the four hints), now listed on both the SDK and the header-less JSON paths. New exports: `approvalInputKey`, `declaresFormElicitation`, and the types `McpServerApprovalOptions`, `McpServerToolApprovalPolicy`, `McpServerToolApproved`, `McpServerApprovalTool`, `McpServerDirectTool` and `McpServerToolAnnotations`.
