A replayed earlier turn's event no longer lands on a later turn's call reusing its id in the chat projections (#361). After turn 1 settled `call_0` (`deploy { env: 'prod' }`) and turn 3 asked another `call_0` (`deploy { env: 'staging' }`), a replay without event id (or under a new one) of turn 1's request, `AgentAwaitingInput`, `ToolExecutionStarted`/`Completed`/`Error`, or answer acted on turn 3's part in `applyAgentEventToChatProjection` and the `useAgentChat` reducer: the pending staging card became the prod call (pending again, running, completed or answered), and the status (`useAgentChat`, `stepAgentChatProjection`'s `statusEvent`) blocked on the prod request or moved to running. The latest turn's part now gives way to the last earlier part holding the event's exact call (id, name and arguments; an answer: its request id) when it is known not to be the one: another call, or, for an answer, a part holding another request or its result; the earlier settled part keeps its state, and the later card and the status blocked on it stay. A later turn's own request still asks on its own part, a pending request re-pended with a new preview still replaces it, a part still streaming its input keeps the event, and with no earlier part holding the call a request or tool-batch event acts on the latest turn's part as before. A question, input or interaction answer that reaches a part holding another request, when no part holds its own (a stale answer, for example after hydration), now changes nothing in the chat projections (in `applyAgentEventToChatMessages` too); it used to answer that other request. The chat reads a part's request as `reduceAgentEvents` reads a run's: an answered or cancelled part by its response's request id (also when it kept no request: an answer applied before its request, or a snapshot run holding only its response), and a denied part by the approval request it denies (`ChatToolState.Denied` gains an optional `request`, kept from the pending approval). In both the chat projections and `reduceAgentEvents`, an answer reaching a part or run with its result (completed, accepted, errored or provider-completed) is a replay (the loop asks only before a result): it acts on an earlier part or run holding its request, else changes nothing, instead of turning the finished call into an answered one (which for an accepted background call dropped its fence); a running call still takes an answer that precedes its request. Approval denials still deny the pending approval they reach. Request ids are built from the tool name and call id, so a later turn's call of the same tool reusing the id still cannot tell an earlier turn's replayed answer or denial from its own: dedupe answers by `eventId`. A replay that gives way to an earlier part still acknowledges the latest turn's provisional call with the same id (execution routing matches ids), so a superseded execution of that turn no longer discards that call.
