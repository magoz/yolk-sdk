`reduceAgentEvents` no longer merges two turns' tool runs when a provider reuses a call id across turns (#343). It kept one `toolRuns` entry per call id, so a later turn's `call_0` replaced the earlier turn's run, and a later call reusing the id of an accepted (background) call was taken for a replay of it: its input, approval and start were ignored and its result replaced the `Accepted` run (within a run), or all its events were dropped (after the transcript acknowledged the earlier call, for example across a pause or in the next run).

- `AgentClientState` records where the latest model turn's runs start (`turnStart`, new `AgentClientTurnStart` type: `streamId`, `turn`, `firstRun`, `closed`), at each `LLMStreamStart`, tagged or not; a start of the same stream and turn with no terminal event or user message since retries the turn and keeps its runs. `AgentStart` and `submitAgentUserMessage` clear it. Carry `turnStart` with `toolRuns` when you keep client state yourself.
- The model's events (input, provider results) act only on the latest turn's runs, so a later turn's call gets a run of its own. Host events act on the latest turn's run first, else, as a replay without event id or a late tool-batch event: a request or tool-batch event on the last earlier run holding the same call (id, name and arguments equal), an answer on the last earlier run holding the request it answers (a denial: a pending approval); an answer for a call id another run holds under another request changes nothing.
- The background-replay fences stay: a replayed start or request of an accepted call leaves its `Accepted` run alone, and the transcript's acknowledgement still fences replays of that call; with a turn start known it fences only events naming the acknowledged call, never a later call reusing its id or the model's events of the latest turn.
- A replayed request no longer reopens a settled run (as #346 does for the chat projections): a `ToolApprovalRequested`, `QuestionRequested`, `InputRequested` or `InteractionRequested` event that reaches a run past its request (denied, answered, cancelled, submitted, running, completed, accepted, errored or provider-completed) and names the same call (id, name and arguments equal), with or without event id, leaves the run as it is. A request for another call with the id, or for a call still pending (an invalid input re-pends it), applies. `Denied` runs now keep the approval request they deny (`request`, optional, as answered runs keep theirs: absent when the event carried none) for this check.
- When the latest turn's run is known to be another call (or to hold another request) than the one a host event names, and an earlier run holds that call (or request), the event acts on the earlier run: a replayed answer or start of an earlier turn's call no longer lands on a later turn's call reusing the id.
- A superseded or uncommitted execution's tool runs are removed or restored within its own turn, not in other turns holding the id.
- `toolRuns` keeps its type (`Denied` only gains the optional `request`). It can now hold one run per turn for a reused call id, in call order: read a call's run by id with the last match, as `buildAgentChatMessages` does. Until a start is seen, and for states built before `turnStart`, tool events act on the last run holding a call id, as before.
