Add durable MCP form elicitation (multi round-trip requests, protocol `2026-07-28`) to the remote client. `McpClientOptions.elicitation: { form: true }` is the host opt-in: only then do `listRemoteMcpServerTools` and the new resumable call functions declare `elicitation.form` in the per-request `_meta` client capabilities of a modern connection (never in a legacy `initialize`). `callRemoteMcpServerToolResumable` answers a Schema-backed `McpToolCallOutcome`: `Complete` (the adapted `ToolResult`) or `InputRequired` (`McpInputRequired`: bounded, decoded form elicitations with `key`, `message` and `requestedSchema`, plus the opaque `requestState`), which the host persists and decides on later. `resumeRemoteMcpServerToolCall` re-sends the same tool call on a new JSON-RPC id with the exact `requestState` and the decisions (`accept` with content, `decline`, `cancel`) as `inputResponses`, checked against the forms before sending. Failures are typed: `McpInputRequiredError` (`malformed`, `too_large` past 64 KiB or 16 requests by default, `unsupported_request` for URL mode, sampling, roots or input without the opt-in, `invalid_responses`, `unsupported_era`) and `McpClientCapabilityRequiredError` for MCP `-32021`. Complete results are still validated against the listed `outputSchema` (the official client wrongly validates an `input_required` answer as output, so the resumable call validates itself). Legacy-era server-initiated elicitation is not supported. `callRemoteMcpServerTool` is unchanged and never declares the capability. `@yolk-sdk/mcp/conformance` adds the opt-in `mcpElicitationDeclarationCase` with `mcpConformanceElicitationFixtures`, outside the default suite.
